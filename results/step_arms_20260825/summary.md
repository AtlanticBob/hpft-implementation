# 发送端律、接收端归因与 RDMA 执行面的组件验证：加入/退出阶跃场景十一臂 + 最终 incast8（2026-08-25）

分支 `vq-sched`。上一轮（`results/vq_demo_20260824/`）确认了虚拟调度器在稳态下成立；这一轮回答三个问题：发送端该用哪种律（对数一阶跳步 vs 纯乘因子 MIMD，后者带三种门控）、加入/退出这种阶跃场景里哪个组件是收敛的瓶颈、以及 RDMA 执行面修好之后还剩多少（执行面本身的测量与修法在 `../executor_20260825/summary.md`）。

## 判断（按组件）

**1. 发送端律：保留对数一阶跳步，否决纯乘因子 + 门控。**纯乘因子的三种门控没有一项赢过 vq 律：TCP 下行 40/350/413 ms 对 60 ms，上行 126–661 ms 对 24 ms，稳态抖动 0.2 对 0.1。门控是负收益，原因在离线检查 `mimd_check.py` M3 里已经说明：因子来自精确信号的乘性更新是幂等的（$R\cdot g/R = g$），本来就不会叠加，"每周期只动一次"这道保险没有对象；随机 sparse MI 只是把同一道保险变成有长尾的版本。更要紧的是图里的现象：三个 MIMD 臂里加入者 RDMA 在加入后 2–3 s 一直跑在 30G（份额的近 3 倍），因为它**一步跳到了一个暂时错高的份额提示**；vq 律的平滑逼近让同一个错误提示只造成很小的伤害。这就是"跳步而不赋值"的实证理由。缩短测量窗（w4）也没有换来更快，只换来稳态抖动翻倍。信心高。

**2. 接收端归因：两处必改。**（a）拆分先验必须是份额提示不是服务速率——服务速率等于拆分给它的到达量，做先验会把错误的拆分锁死；改后 RDMA 加入收敛从 2.2 s 降到 0.2–0.3 s，这是本轮最大的一处改进。（b）发送端自报的发送量做拆分比例（提案 §1.5）：在这个场景里 RDMA 在位者数值上略好于 (a)（227 对 306 ms），并把 TCP 冷启动从 696 ms 拉回 60 ms，且原理上不再依赖 1 s 缓存的流表计数——保留为最终配置。信心高。

**3. 队列记忆上限：对收敛无关紧要，保留 50 ms 即可。**把上限从 200 ms 压到 50 ms 没有缩短 RDMA 加入（451 对 227 ms，差别在轮次噪声内），说明剩余的时间不在队列里。信心高。

**4. RDMA 执行面修好之后，RDMA 比 TCP 还快。**执行面的三处问题（管道积压、未知流线速放开、QP 计数漏数）在 `../executor_20260825/summary.md` 里逐一测量并修复；对应的三个臂里 RDMA 在位者下行从 227 ms 到 145 ms、加入者从 598 ms 到 206 ms、上行从 150 ms 到 105 ms，共享稳态抖动从 0.06G 到 0.01G。TCP 侧（EDT 即写即生效）保持 60–390 ms（慢启动随机）与 0.12G。控制环的滞后现在由 RDMA 执行面的 13 ms 邮箱决定，这是固件下限。信心高。

**5. 一个未解释的小项。**开启发送端自报拆分的各臂里，加入者退出后在位者 RDMA 回到 22.05–22.2G 而不是 22.7G（TCP 回到 22.95 不变）；st_vq_prior 没有这个现象（22.67）。疑似发送端自报拆分在对端 QP 残留期间的处理，待查。

## 与提案的对照

- 发送端律：提案 §2 的两条优化（跳步、按排队时长砍速）成立；用户要求的"纯乘因子 + sparse MI"经实测否决，理由是幂等性与错误提示放大，应写进设计文档作为反面论证。
- 接收端：提案 §1.5（发送端自报拆分）确认必要；§1.3/1.4 加上一轮的积压保持；本轮再加"拆分先验 = 份额提示"。
- 最终参数：$k=20$，$\varepsilon=2\%$，$D_r=150$ ms，$\varphi_{\min}=0.5$，hold 50 ms，d_clip 50 ms，split_by_sender 开；执行面：rdma_push_ms 5，rdma_unknown_rate_bps 5G/QP。
