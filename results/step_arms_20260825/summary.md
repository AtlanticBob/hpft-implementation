# 发送端律与接收端归因的组件验证：加入/退出阶跃场景七臂 + 最终 incast8（2026-08-25）

分支 `vq-sched`。上一轮（`results/vq_demo_20260824/`）确认了虚拟调度器在稳态下成立；这一轮回答两个问题：发送端该用哪种律（对数一阶跳步 vs 纯乘因子 MIMD，后者带三种门控），以及加入/退出这种阶跃场景里哪个组件是收敛的瓶颈。

## 场景

| 项 | 值 |
|---|---|
| 接收端 | sgpu02，$C'=184$G，4 个目的 VM 各上限 50G、等权、类权重 1:1 |
| 在位者 | sgpu01：4 对 RDMA + 4 对 TCP（vf_n→vf_n），0–90 s |
| 加入者 | sgpu03：同样 8 对，约 32 s 加入；TCP 约 62 s 退出、RDMA 约 65 s 退出（两类生成器结束时刻不同） |
| 份额 | 每流集合 23.0G（单发送端）→ 11.5G（两发送端）→ 23.0G |
| 判据 | "收敛"= 该组该类全部流集合连续 100 ms 进入新份额 ±10%；稳态抖动 = 20 ms 采样的标准差 |
| 运行器 | `tools/tests/step_regression.sh`，分析 `analyze_step.py`，逐臂 `run_arm.sh` |

## 判断（按组件）

**1. 发送端律：保留对数一阶跳步，否决纯乘因子 + 门控。**纯乘因子的三种门控没有一项赢过 vq 律：TCP 下行 40/350/413 ms 对 60 ms，上行 126–661 ms 对 24 ms，稳态抖动 0.2 对 0.1。门控是负收益，原因在离线检查 `mimd_check.py` M3 里已经说明：因子来自精确信号的乘性更新是幂等的（$R\cdot g/R = g$），本来就不会叠加，"每周期只动一次"这道保险没有对象；随机 sparse MI 只是把同一道保险变成有长尾的版本。更要紧的是图里的现象：三个 MIMD 臂里加入者 RDMA 在加入后 2–3 s 一直跑在 30G（份额的近 3 倍），因为它**一步跳到了一个暂时错高的份额提示**；vq 律的平滑逼近让同一个错误提示只造成很小的伤害。这就是"跳步而不赋值"的实证理由。缩短测量窗（w4）也没有换来更快，只换来稳态抖动翻倍。信心高。

**2. 接收端归因：两处必改。**（a）拆分先验必须是份额提示不是服务速率——服务速率等于拆分给它的到达量，做先验会把错误的拆分锁死；改后 RDMA 加入收敛从 3.4 s 降到 1.5 s，这是本轮最大的一处改进。（b）发送端自报的发送量做拆分比例（提案 §1.5）：在这个场景里数值上和 (a) 持平（1.46 对 1.54 s），但它把 TCP 冷启动从 696 ms 拉回 60 ms，且原理上不再依赖 1 s 缓存的流表计数——保留为最终配置。信心高。

**3. 队列记忆上限：对收敛无关紧要，保留 50 ms 即可。**把上限从 200 ms 压到 50 ms 没有缩短 RDMA 加入（1.68 对 1.46 s），说明剩余的 1.5 s 不在队列里。信心高。

**4. 剩余瓶颈是 RDMA 执行面，不是控制环。**st_vq_split 的逐条记录显示：加入者 RDMA 的预算 $R$ 在加入后 0.2 s 内就到 11.7G，而线上速率从 7 G 按每 13 ms 一步爬到 11.2G 用了 1 s（RP 的 12.5%/步爬坡）；在位者被加入者那 100 ms 线速冲击记入 130 ms 的虚拟队列，按 $D_r$ 还清也用了约 0.7 s。两件事都在执行面：加入者在首条预算到达前无约束（需要 RP 对未知 flowtag 的保守默认预算），以及水位赋值后的爬坡（ops_notes 已知长尾）。TCP 侧（EDT 即写即生效）冷启动 60 ms，说明控制环本身能做到这个量级。要动 DPA 设备码，本轮不做。

**5. 一个未解释的小项。**st_vq_split / st_vq_clip 里加入者退出后，在位者 RDMA 回到 22.06G 而不是之前的 22.71G（TCP 回到 22.95 不变）；st_vq_prior 没有这个现象（22.67）。疑似发送端自报拆分在对端 QP 残留期间的处理，待查。

## 与提案的对照

- 发送端律：提案 §2 的两条优化（跳步、按排队时长砍速）成立；用户要求的"纯乘因子 + sparse MI"经实测否决，理由是幂等性与错误提示放大，应写进设计文档作为反面论证。
- 接收端：提案 §1.5（发送端自报拆分）确认必要；§1.3/1.4 加上一轮的积压保持；本轮再加"拆分先验 = 份额提示"。
- 最终参数：$k=20$，$\varepsilon=2\%$，$D_r=150$ ms，$\varphi_{\min}=0.5$，hold 50 ms，d_clip 50 ms，split_by_sender 开。

## 补记（2026-08-25 晚）：分析器修正与执行面修复之后

分析器原来把"加入"定在 TCP 加入者出现的时刻，而 RDMA 加入者（perftest 建连）比 TCP（iperf）晚约 1.2 s 才发第一个包，所以上表里 RDMA 的"1.5 s"绝大部分是这个时间差。按各自第一个包重算（`analyze_step.py` 已改为按类取加入时刻），并加上执行面的修复（见 `../executor_20260825/summary.md`）：

| 臂 | 在位者下行 RDMA / TCP | 加入者冷启动 RDMA / TCP | 在位者上行 RDMA / TCP | 共享稳态 sd RDMA / TCP |
|---|---|---|---|---|
| st_vq（首版，先验 = 服务速率） | 2242 / 60 ms | 2137 / 60 | 24 / 24 | 0.09 / 0.11 |
| st_vq_split（先验 = 份额提示 + 自报拆分） | 227 / 60 | 598 / 60 | 150 / 125 | 0.06 / 0.11 |
| st_vq_exec2（+ 管道最新优先、未知流上限每 QP 5G、5 ms 推送） | 125 / 60 | 266 / 60 | 105 / 66 | — |
| st_vq_exec3（+ QP 计数按 8 ms 窗口） | 125 / 370 | 186 / 390 | 86 / 65 | 0.14 / 0.12 |
| **st_vq_exec4（+ 窗口内两次出现才算活跃，最终）** | **145 / 349** | **206 / 389** | **105 / 65** | **0.01 / 0.12** |

TCP 的 60 与 350–390 ms 之间的差别是 TCP 自己慢启动的随机性（同一配置不同轮次都出现过两种值），不是设计变化。RDMA 侧从首版的 2.2 s 到最终的 0.15–0.2 s，其中约 2 s 是归因先验的问题（第二轮修），剩下的从 0.2–0.6 s 到 0.15–0.2 s 是执行面三处修复；共享稳态 RDMA 抖动 0.01G，已经低于 TCP。`fig_step.png` 已按最终臂重绘。
