# 同 dst 多 RDMA 流：v1 遗留观察的复测（2026-07-28）

2026-07-13 在 v1 栈上记过一条"移交控制域的遗留观察"：同 dst 的两条 RDMA
流在 RP 层严重不公平，第二条加入把在位流从 44G 压到 ~2G，离开 5s 后只
恢复到 12.5G。此后一直没复测。进实验环节前先确认它在 v2 下是否还活着。

## 结论

**还活着，但性质和记录的不一样，而且根因不在 RP。**

| 假设 | 判定 | 依据 |
|---|---|---|
| 跨对流的预算没生效 | **排除** | vf3→vf0 单独跑 29.14G，vf3→vf3 对照 29.07G，都守 30G 上限 |
| 两条流走同一条接收路径打架 | **排除** | dst 上限抬到 60G 后两条各 29.3G 稳定共存（合计 58.9G） |
| 争夺同一个 VM 上限时份额判据翻烧饼 | **已排除（见更正）** | θ=0 冻结判据后振荡照旧 |
| 执行面在两条流各持 15G 预算时赢家通吃 | **成立** | 见更正一节 |

不是"在位流被永久压死"：v1 记的"离开后只回到 12.5G"在 v2 下**没有**——
B 离开后 A 在 1 拍内回到 29.31G，无需求闩锁。取而代之的是**两条流在
多秒尺度上轮流坐庄**的极限环。

## 更正：判据不是驱动因素

上面"份额判据双稳态"的机制说明**是错的**，由第三臂推翻。

把 `backlog_theta` 设为 0，`r ≥ θ·ŝ` 对任何 r>0 恒真，所有活跃流集合恒判
积压，分配退化成纯政策的固定 15/15，判据动力学被完全冻住。振荡**照旧**：

```
theta=0，dst 上限 30G
  t(s)   vf0(G)   vf3(G)     合计
  29.5    11.07    29.31    40.38
  30.6     0.01    29.29    29.30
  31.6     0.01    21.88    21.89
  33.6    29.33     0.05    29.38
  36.7     0.06    29.32    29.38
  44.8     1.28    15.73    17.02
共存段(32-44s)  A 12.47±11.15   B 12.33±11.15
```

比 θ=0.5 时更深（落败方到 0.01G）。判据洗清了。

## 真正的签名

冻结判据后剩下的事实很窄，也因此很有指向性：

- **合计守规矩**：多数时刻总量 ~29.3G ≈ 2×15G 两份预算之和，上限没被突破；
- **切分完全不守**：不是 15/15，而是 29/0 赢家通吃，几秒一换庄；
- 两个 flowtag 确实不同（vf0>vf0 = 0x74249a41，vf3>vf0 = 0xb61f934b），
  不是已知的 vf1/vf2 碰撞；
- 各自单独跑都精确守 30G（29.14 / 29.07G）。

即：**两份独立预算在总量上生效、在个体上不生效**。一条流能吃掉另一条的
额度，而两条之和仍被约束住。这个形状指向 RDMA 执行面（PCC RP）对同一
dst 的两个 flowtag 的处理，不指向分配器——分配器全程只发了 15/15。

## 原机制说明（已作废，保留以备对照）

积压判别有两个入口：份额判据 `r_f ≥ θ_b·ŝ_f`，和 **root** 拥塞。这个
场景的瓶颈是 **VM 上限**，不是 root——root 利用率只有 30/97 = 31%，离
95% 的进入阈值远得很，所以拥塞入口全程不响，只剩份额判据。

于是形成一个双稳态：某条流的线上速率一旦掉到 θ_b·ŝ 以下，就被判为不积压，
需求估计塌成 `r(1+δ)`，它的份额被让给对手；对手的天花板升到 ~29G，把它
压得更低。反向翻转由虚拟队列完成——对手超出 30G 上限后被打标、被折扣，
让出空间，原来那条爬回来，然后角色互换。周期约 4 秒，比律的 50ms 时间
常数慢两个数量级，所以**这不是律的振荡，是判据的振荡**。

换句话说：**当绑定约束是树的中间节点（VM 上限）而不是 root 时，积压判别
没有对应的拥塞入口**。`vmlayer_run.sh` 当初正是为"份额判据是否还需要"
建的，它验证的是份额判据能看见 root 看不见的层；这里暴露的是反面——
份额判据独自撑不住这一层。

## 影响

- 直连对互不相干的拓扑（incast8 那种，四个 dst 各一条）**不受影响**，
  Jain 仍是 1.000。
- 任何**多发送方打同一个接收方**的 RDMA 实验会被它污染，而且看起来会
  像公平性算法失效——经典 incast 正是这个形状。

# 修复（2026-07-28 下半场）

三个缺陷，前两个已修并验证，第三个已隔离到设备侧尚未修。

## 缺陷一：类内多发送方归属把一条流的流量记在另一条头上

`HybridRates` 用 megaflow 字节比例把 dst 的精确总量分摊给各发送方，而
megaflow dump 有硬件缓存，新发送方的字节要数秒才出现。窗口里没有它的字节
被当成"它没在发"，于是它的全部流量被记到同伴头上。实测：两条各 ~29G 的
流被报成 **58.3G / 0.00G**。

这个错值同时喂给需求估计**和** RP 的 `remote_rx_rate`，后者让被冤枉的那条
读到远超预算，把自己的水位挖到 0——这就是"赢家通吃、几秒换庄"的来源。

**修法**：分摊的尺子分两种。所有成员都测到字节时用字节比（测量优先）；
只要有一个成员没测到，就改用**上一拍的额度**作先验分摊。这个先验天然处理
两种情况：给过份额的发送方假定它在用，而真正空闲的流集合其额度本身就
≈0，所以仍然分到 ≈0，不需要额外规则。新出现、上一拍额度表里没有的成员，
按同组已知成员的均值计——默认成 0 会原样复现本缺陷（这个洞我第一版就踩了，
是 lab 数据抓出来的）。

## 缺陷二：积压判别缺一个结构性入口

判别原本只有两个入口：份额判据 `r ≥ θ_b·ŝ`，和 **root** 拥塞。这个场景
的瓶颈是 dst 的 VM 上限，root 利用率只有 31%，拥塞入口全程不响。

后果不是"判据翻烧饼"（θ=0 冻结判据后振荡照旧，那条归因已作废），而是更
基本的：`ê_f` 是"自身需求置无穷"的上界，两条流各自算出 ~30G 天花板，同时
用满就是 2× 上限。虚拟队列的折扣被 γ=0.25 封顶，claw 不回来。让 ê 等于
**联合**公平份额的唯一机制就是积压判别，而它当时判不出来。

**修法**：`NodeSaturation`——树上任一节点满载，其下所有流集合即为竞争中。
root 拥塞一直就是这条判据在某一个特定节点上的特例，现在把它向下推广到
dst VM 层。关键性质：**这条判据不需要分摊**。分摊再错，各估计之和仍然是
精确的 vport 总量（分摊是对它的划分），所以拿这个和与节点容量比是精确的。

这也正面回答了"θ 判据不好"：θ 判据的坏处在于它对**接收端唯一无法精确
测量的量**（每发送方速率）做阈值判断，把估计误差放大成政策。结构性判据只
用精确量，是更合适的取代物。份额判据保留，但在这类场景里不再承重。

## 验证

|---|---|---|---|---|
| 修前 | 15.64±12.10 | 13.69±12.20 | 29.33 | 0.617 |
| 全部修复后 | 11.31±12.96 | 10.17±13.04 | 21.48 | 0.819 |

两条流现在**逐拍同步**（29.3/29.3 → 15.7/14.9 → 0/0），不再赢家通吃。
分配器读数也已正确：B 加入后 200ms 内两条的 pace 都是 11.25G。
离线 26/26 通过（含 G1–G5、H1–H5 覆盖新语义）。

## 缺陷三（未修，已隔离）：RP 水位控制对大幅降预算的响应

控制面正确之后剩下的事实很干净：

```
   t  |    A_u   A_pace     A_r |    B_u   B_pace     B_r
 29.6 |  11.25    11.25   ...   |  15.00    15.00   ...
 31.6 |  11.25    11.25   29.17 |  11.25    11.25   29.33
```

**额度 11.25G，线上 29.3G，持续约 2 秒**；随后水位被挖穿到 0，两条流一起
断流约 3 秒，再回到 29.3G，周期约 8 秒。单流场景看不到这一层，是因为律的
输出每次只动几个百分点，预算从不发生大幅阶跃。

方向：`level` 是每 QP 的、均衡值 = budget/N，而挖掘的停止判据是聚合
`rs ≤ bud>>2`，本身就把聚合停在预算的 25%；叠加遥测链路的传输延迟，积分
会冲过头。要定的是这一步的阻尼，和 v2 其余部分一样应当做成无标度的。

# 收尾：水位改为直接赋值（同日）

## 缺陷四：RP 的水位是在"搜索"一个已经可以算出来的量

`results->rate = min(cc_rate, level)` 按 pair 的每个 QP 施加，所以 pair 上
线的聚合是 N × level，能交付预算的水位就是 **budget / N**。两项都是已知量：
预算从 mailbox 来，N 可以从事件流数出来。没有任何东西需要搜索。

原实现用积分控制去逼近它，于是需要步长、截幅、一个阻止无限下挖的地板、
以及一个防止对未跟上的测量积分的 settle-hold——四个参数、四条绕组路径。
大幅降预算正好把它们全部激发：预算 11.25G，线上 29.3G 维持约 2 秒，随后
水位穿过目标一路挖到下限，两条流一起停摆约 3 秒，周期 8 秒。

**改法**：`level = budget / N`，直接赋值。赋值没有状态，也就没有绕组，
这一整类故障无处存身。同时删掉 settle-hold、比例前馈和挖掘地板——它们
存在的唯一理由是保护那个积分。这与响应律上游是同一个动作：目标已知时，
算出来胜过收敛过去。

`cc_rate` 保留，它响应的是真实的 fabric 拥塞，属于自己的时间尺度，
`min()` 让更紧的一方生效。

**N 怎么数准**：`qp_count` 原本只在 `0xB48E` mailbox 路径自增，而 agent 只
发 `0xB47C`，所以它在生产路径上恒为 0——`(cc>>6)/nqp` 的流数归一化是死
代码，4 QP 的流退让强度是设计值的 4 倍。改为从事件流学习，并**按 epoch
计数**（每个 QP 槽记录上次被计入的 epoch），停发的 QP 自动淘出。实测读数
稳定为 4，与实际一致。

## 最终结果

| | 共存段 A | B | 合计(上限30) | 断流 | Jain | B 走后 A |
|---|---|---|---|---|---|---|
| 最初 | 15.64±12.10 | 13.69±12.20 | 29.33 | 0/11 | 0.617 | 29.31 |
| 全部修复 | 13.42±1.16 | 13.70±1.15 | 27.12 | 0/11 | **0.999** | 29.32 |

稳态逐秒读数 A 14.12 / B 14.35，连续 10 秒不动一位小数；上限守住
（28.47 < 30）；对端离开后 A 在约 4 秒内回到 29.32G。标准差里的 ±1.16
全部来自加入后约 4 秒的收敛过程，不是稳态抖动。

四个缺陷回顾：归属（把一条流的流量记到另一条头上）、判据（缺 VM 上限
节点的饱和入口）、`qp_count`（归一化死代码）、水位（用搜索代替赋值）。
前两个在接收端控制面，后两个在 RDMA 执行面。
