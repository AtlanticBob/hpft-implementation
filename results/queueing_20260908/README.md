# HyperFront 对交换机排队的影响（2026-09-08）

一个问题：HyperFront 本质是发送端的整形器，它有没有减少交换机的排队？答案是有，而且幅度很大——同一负载下接收端口的出向排队时延从 99.8% 的包超过 133 µs 变成 81% 的包在 18 µs 以内，应用可见的往返探针从 1057 µs 变成 6.7 µs，代价是 4% 的吞吐。

## 环境

| 项 | 取值 |
|---|---|
| 拓扑 | sgpu01、sgpu03、sgpu04 三台各 4 个 VM 打 sgpu02 的 4 个 VM，单交换机 sn5600，四个 p1 口 200 G，接收端口 `swp37s0` 是 3:1 超订的瓶颈 |
| 负载 | `validation/scenarios/q_v1.spec`：24 个流集合，12 个 RDMA（每个 4 QP，WRITE，MTU 1024）+ 12 个 TCP（每个 4 条 Cubic 连接，不开 ECN），12 秒，两臂完全相同 |
| 每 VF 上限 | 50 G（发送端 devlink + 接收端 OVS meter） |
| 交换机 QoS | 六个口绑 `hpft_ecn`：ECN K_min 800 KB、K_max 3.2 MB、P_max 20%；出向队列门限动态 `alpha_1`（一个拥塞队列最多占 70.47 MB 共享池的一半、35.2 MB）；PFC 关；全部流量走 TC0 |
| 租户拥塞控制 | RDMA 是执行面里的 DCQCN（`0xccd 2`），TCP 是 Cubic |
| 重传 | SR |

**两个臂只差整形器。**

| 臂 | 含义 |
|---|---|
| `hpft` | 缺省态：接收端账本给每个流集合许可速率 $R$，发送端执行面按令牌桶整形（`run/run.sh hpft`） |
| `cc` | 只有租户拥塞控制：RDMA 执行面忽略预算（`0xcce 1 12`），发送端代理停掉，TCP 速率表清空（`run/run.sh cc`） |

## 测什么

**交换机自己的直方图是主证据。** sn5600 的 ASIC 每 1024 ns 采样一次接收端口的出向缓冲占用与出向排队时延，每秒写一份快照到 `/var/run/cumulus/histogram_stats_<n>`。开法（跑完要关）：

```
nv set interface swp37s0 telemetry histogram egress-buffer traffic-class 0
nv set interface swp37s0 telemetry histogram latency traffic-class 0
nv set system telemetry histogram egress-buffer bin-min-boundary 4096
nv set system telemetry histogram egress-buffer histogram-size 4194304   # 16 档，每档 256 KB
nv set system telemetry histogram latency bin-min-boundary 2048
nv set system telemetry histogram latency histogram-size 163840          # 16 档，每档 10.24 µs
nv set system telemetry snapshot-interval 1
nv set system telemetry enable on
```

交换机走 HKT、主机走 UTC，快照的时间戳只能在交换机上过滤，`run.sh` 就是这么做的。

**另外三样。** 应用可见的探针：`ib_write_lat` 在一对空闲 VF（sgpu01/vf4 → sgpu02/vf4）上打 2 字节的往返，经过同一个出向队列，在负载中段跑 8 秒；交换机的 ECN 标记帧与队列丢帧增量；每个流集合的应用净荷，用来确认时延的改善不是拿吞吐换的。

## 结果

图：`fig/queueing.png`，两条曲线都是交换机自己的直方图画成的累积分布：左图读作"队列不深于 x 的时间占比"（每 1024 ns 一次采样），右图读作"排队不超过 x 的包占比"（每个包一次采样）。交换机把数据分好了档，所以曲线是阶梯，标记落在档的边界上；最高一档没有上界，图例注明了各自还剩多少落在它里面。数据：`data/queueing.csv`。原始：`results/<臂>/`。

**出向缓冲占用**（采样点占比，越低越好）：

| 门限 | 只有拥塞控制 | HyperFront |
|---|---|---|
| ≥ 4 KB | 41% | 36% |
| ≥ 400 KB | 41% | 9.2% |
| ≥ 800 KB（ECN 起标） | 41% | 3.8% |
| ≥ 1.6 MB | 41% | 1.2% |
| ≥ 3.1 MB（≈ 满标） | 41% | 0.05% |

只有拥塞控制时队列是两态的：要么空，要么直接顶到 3.1 MB 以上，中间几乎没有采样点——41% 的时间队列深过 3.1 MB。加了 HyperFront，超过 800 KB 的时间只剩 3.8%，超过 3.1 MB 的只剩万分之五。

**出向排队时延**（同一窗口，采样点占比）：

| 门限 | 只有拥塞控制 | HyperFront |
|---|---|---|
| ≥ 2 µs | 100% | 86% |
| ≥ 18 µs | 100% | 19% |
| ≥ 35 µs | 100% | 8.4% |
| ≥ 68 µs | 100% | 2.2% |
| ≥ 133 µs | 99.8% | 0.07% |

**应用可见的代价与收益：**

| 量 | 只有拥塞控制 | HyperFront |
|---|---|---|
| 2 字节 RDMA 往返探针（同一队列，空载 2.8 µs） | 1057 µs | 6.7 µs |
| 24 个流集合的应用净荷合计 | 182.2 G | 174.8 G |
| 12 秒里接收端口的 ECN 标记帧 | 593 万 | 73 万 |
| 队列丢帧 | 0 | 0 |

## 为什么会这样

**账本分配的是 $(1-h)\cdot C$，不是 $C$。** 接收端把端口容量乘 0.92 之后才分给各流集合，所以所有许可速率之和按构造低于端口速率。发送端把每个流集合整形到它的许可速率，端口的到达率就恒在容量之下，没有持续积压的理由。余量 $h$ = 8% 正是为这件事留的（设计 4.3 节）。

**拥塞控制单独运行时，它的工作点就是一段常驻队列。** DCQCN 与 Cubic 都靠拥塞信号找工作点，而信号只有在队列积起来之后才出现：ECN 要队列过 800 KB 才开始标记，Cubic 要丢包或时延变化。所以它们的平衡点必然是"队列深到能持续产生信号"，实测就落在 K_max 3.2 MB 之上——1 ms 的 200 G 正好是 25 MB 量级，与探针量到的 1057 µs 一致。这不是拥塞控制没调好，是反馈式拥塞控制的构造使然。

**逐 QP、逐连接的整形还去掉了突发。** 执行面把每个 QP 的速率写进硬件整形器、每条 TCP 连接有自己的发车时钟，到达是平滑的，而不是窗口型传输那种一次放一窗的脉冲。所以即使平均速率相同，瞬时排队也更小。

**这四个百分点的吞吐就是余量的代价。** 182.2 G 对 174.8 G，差 4.1%，与 $h$ = 8% 在内层字节口径上的折算一致（184 G 内层字节 ÷ 1.073 的 RoCE 头部开销 ≈ 171 G 净荷，TCP 那半边开销更小，合起来 175 G）。要换更低的时延，把 $h$ 调大；要换更高的吞吐，把 $h$ 调小，队列会相应长一点。这是设计里唯一一个直接的时延与吞吐取舍旋钮。

## 对论文的意义

这是公平性之外的第二条收益，而且是同一个机制自然带来的：一个把总量压在容量之下的整形器，让共享这个端口的所有流量都拿到低时延，不需要为时延敏感的应用单独划队列或改拥塞控制。可以直接支撑两类论述：与时延相关的应用指标（小流的完成时间、请求响应类工作负载的尾时延）在不改租户任何东西的前提下改善两个数量级；以及"为什么不能只靠租户自己的拥塞控制"——它们的工作点按构造就是一段常驻队列。

**还没做的**：小流完成时间（FCT）的直接测量。本轮的探针是固定大小的往返，能证明排队时延，但不等于 FCT 曲线；要写进论文应当补一组不同大小的短流，在两臂下量它们的完成时间分布。

## 复原

跑完把交换机的遥测关掉，它是常驻采样：

```
nv set system telemetry enable off
nv unset interface swp37s0 telemetry histogram
nv config apply -y
```
