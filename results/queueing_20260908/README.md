# HyperFront 对交换机排队的影响（2026-09-08）

一个问题：HyperFront 本质是发送端的整形器，它有没有减少交换机的排队？答案是有，而且幅度很大——同一负载下接收端口的队列中位深度从 62.9 MB 降到 201 KB，出向排队时延的中位数从 2.10 ms 降到 10.2 µs，应用可见的往返时延中位数从 2124 µs 降到 10.9 µs（快 195 倍），代价是 2.8% 的吞吐。

## 环境

| 项 | 取值 |
|---|---|
| 拓扑 | sgpu01、sgpu03、sgpu04 三台各 4 个 VM 打 sgpu02 的 4 个 VM，单交换机 sn5600，四个 p1 口 200 G，接收端口 `swp37s0` 是 3:1 超订的瓶颈 |
| 负载 | `validation/scenarios/q_v1.spec`：24 个流集合，12 个 RDMA（每个 4 QP，WRITE，MTU 1024）+ 12 个 TCP（每个 4 条 Cubic 连接，不开 ECN），12 秒，两臂完全相同 |
| 每 VF 上限 | 50 G（发送端 devlink + 接收端 OVS meter） |
| 交换机 QoS | 六个口绑 `hpft_ecn`：ECN K_min 800 KB、K_max 3.2 MB、P_max 20%；出向队列门限动态 `alpha_1`（一个拥塞队列最多占 70.47 MB 共享池的一半、35.2 MB）；PFC 关；全部流量走 TC0 |
| 租户拥塞控制 | RDMA 是执行面里的 DCQCN（`0xccd 2`），TCP 是 Cubic |
| 重传 | SR |

**两个臂只差整形器。**

| 臂 | 含义 |
|---|---|
| `hpft` | 缺省态：接收端账本给每个流集合许可速率 $R$，发送端执行面按令牌桶整形（`run/run.sh hpft`） |
| `cc` | 只有租户拥塞控制：RDMA 执行面忽略预算（`0xcce 1 12`），发送端代理停掉，TCP 速率表清空（`run/run.sh cc`） |

## 测什么

**交换机自己的直方图是主证据。** sn5600 的 ASIC 采样接收端口的出向缓冲占用（字节）与出向排队时延（纳秒），每秒写一份快照到 `/var/run/cumulus/histogram_stats_<n>`。开法与复原见文末。两个限制决定了怎么用它：

- **档数是固定的**（一个下溢档、八个中间档、一个上溢档），只有量程可调。所以同一份负载按量程跑了好几遍——`run.sh <臂> <量程>`，量程有 `low`（缓冲 49 KB 一档、时延 2 µs 一档）、`mid`、`high`、`top`、`top2`、`top3`——再把各遍的累积分布在共享的档边界上拼起来。拼接不是假设：`data/stitch_check.csv` 给出两遍在同一个边界上的最大分歧，HPFT 侧 1.8%，只有拥塞控制那侧缓冲 4.3%、时延 8.5%（后者是"完全不排队的那一小撮包"的占比在几遍之间的浮动，与主体无关）。量程一直往上加到上溢档为空为止，所以曲线不需要假设任何天花板。
- **采样窗口必须只盖住负载**。快照是每秒一份，而运行脚本记录的窗口一直延伸到 quick.sh 收尾，多出来的空载秒数会全部落进"队列为空"那一档（未修正前两臂都读到约 60%）。蒸馏时按时间排序只取前 11 份，即那 12 秒负载。

交换机走 HKT、主机走 UTC，快照的时间戳只能在交换机上过滤，`run.sh` 就是这么做的。

**应用可见的探针。** `ib_write_lat` 在一对空闲 VF（sgpu01/vf4 → sgpu02/vf4）上打 2 字节的往返，经过同一个出向队列，用 `-H` 把**每一个样本**都吐出来（这个选项只在固定次数模式下有效，所以次数按各臂的时延预估定，两臂都覆盖约 5 秒）。**perftest 报的是一次往返的一半**，本文所有探针数字都已乘二还原成完整往返：这不是假设——只有拥塞控制时交换机独立测得队列 53 到 63 MB、排队 2.0 到 2.2 ms，而工具报 1.06 ms，恰是一半，且反向路径不拥塞，所以完整往返只能是交换机测到的那 2.1 ms。

**另外两样。** 交换机的 ECN 标记帧与队列丢帧增量；每个流集合的应用净荷，用来确认时延的改善不是拿吞吐换的。

## 结果

图：`fig/queueing.png`，三条累积分布，每条都从 0 走到 100%。左图是交换机出向队列的深度（每 128 ns 采一次样，读作"队列不深于 x 的时间占比"），中图是同一端口的出向排队时延（每个包一次，读作"排队不超过 x 的包占比"），右图是应用可见的往返时延（探针的每一个样本，不分档）。数据：`data/queueing.csv`，拼接自检：`data/stitch_check.csv`。

| 分位 | 只有拥塞控制 | HyperFront |
|---|---|---|
| 队列深度 中位 / 90% / 99% | 62.9 MB / 62.9 MB / 62.9 MB | 201 KB / 1.18 MB / 2.76 MB |
| 队列为空（< 4 KB）的时间 | 0.0% | 11.5% |
| 排队时延 中位 / 90% / 99% | 2.10 ms / 2.23 ms / 2.23 ms | 10.2 µs / 51.2 µs / 100.4 µs |
| 应用往返 中位 / 99% / 99.9% | 2124 µs / 2176 µs / 2187 µs | 10.9 µs / 43.6 µs / 191 µs |
| 应用净荷合计 | 182.2 G | 177.1 G |
| 12 秒里的 ECN 标记帧 | 591 万 | 83 万 |

只有拥塞控制时，队列在整个负载期间**一次都没有空过**，中位深度 62.9 MB、排队时延 2.1 ms，而且分布极窄（90% 与 99% 分位几乎相同）——它稳稳地坐在交换机缓冲的顶上。加了 HyperFront，中位深度 201 KB，还有 11.5% 的时间队列是空的；ECN 起标线 800 KB 以上只占约一成的时间。应用往返的中位数从 2.12 ms 降到 10.9 µs，**快 195 倍**，尾部（99.9%）从 2.19 ms 降到 191 µs。

## 为什么会这样

**账本分配的是 $(1-h)\cdot C$，不是 $C$。** 接收端把端口容量乘 0.92 之后才分给各流集合，所以所有许可速率之和按构造低于端口速率。发送端把每个流集合整形到它的许可速率，端口的到达率就恒在容量之下，没有持续积压的理由。余量 $h$ = 8% 正是为这件事留的（设计 4.3 节）。

**拥塞控制单独运行时，它的工作点就是一段常驻队列。** DCQCN 与 Cubic 都靠拥塞信号找工作点，而信号只有在队列积起来之后才出现：ECN 要队列过 800 KB 才开始标记，Cubic 要丢包或时延变化。所以它们的平衡点必然是"队列深到能持续产生信号"，实测落在 62.9 MB——远在 K_max 3.2 MB 之上，一直顶到这块芯片给一个拥塞队列的缓冲上限。62.9 MB 在 200 G 上正是 2.5 ms，与交换机测到的 2.1 到 2.2 ms 排队时延、探针测到的 2.12 ms 往返彼此印证。这不是拥塞控制没调好，是反馈式拥塞控制的构造使然：不把队列积到能持续产生信号的深度，它就不知道该退。

**逐 QP、逐连接的整形还去掉了突发。** 执行面把每个 QP 的速率写进硬件整形器、每条 TCP 连接有自己的发车时钟，到达是平滑的，而不是窗口型传输那种一次放一窗的脉冲。所以即使平均速率相同，瞬时排队也更小。

**这几个百分点的吞吐就是余量的代价。** 182.2 G 对 177.1 G，差 2.8%，与 $h$ = 8% 在内层字节口径上的折算同量级（184 G 内层字节 ÷ 1.073 的 RoCE 头部开销 ≈ 171 G 净荷，TCP 那半边开销更小，合起来 175 到 178 G）。要换更低的时延，把 $h$ 调大；要换更高的吞吐，把 $h$ 调小，队列会相应长一点。这是设计里唯一一个直接的时延与吞吐取舍旋钮。

## 对论文的意义

这是公平性之外的第二条收益，而且是同一个机制自然带来的：一个把总量压在容量之下的整形器，让共享这个端口的所有流量都拿到低时延，不需要为时延敏感的应用单独划队列或改拥塞控制。可以直接支撑两类论述：与时延相关的应用指标（小流的完成时间、请求响应类工作负载的尾时延）在不改租户任何东西的前提下改善两个数量级（往返中位数 2124 µs 降到 10.9 µs）；以及"为什么不能只靠租户自己的拥塞控制"——它们的工作点按构造就是一段常驻队列，实测顶在芯片缓冲的上限上。

**还没做的**：小流完成时间（FCT）的直接测量。本轮的探针是固定大小的往返，能证明排队时延，但不等于 FCT 曲线；要写进论文应当补一组不同大小的短流，在两臂下量它们的完成时间分布。

## 复原

跑完把交换机的遥测关掉，它是常驻采样：

```
nv set system telemetry enable off
nv unset interface swp37s0 telemetry histogram
nv config apply -y
```
