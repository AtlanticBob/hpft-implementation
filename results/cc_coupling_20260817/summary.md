# CC 耦合：执行面只读 CC，不改 CC（2026-08-17 起，本版 2026-08-19）

## 约束

HPFT 对拥塞控制的介入限定为三步——**读取并记录 CC 的速率、与自己的份额合成出
应有的真实速率、下发这个速率做整形**。CC 一行不改，RDMA 与 TCP 同一实现方式。

## 问题

执行面原本用 `rate = min(cc_rate, level)` 合并两个数：`level` 是接收端算出的
政策份额，`cc_rate` 是 CC 对拥塞信号的反应。取小值等于给 CC 一票否决权，而一个
恢复目标是"自己上次被砍前速率"的 CC 会用掉这一票：每次砍都把目标一起拉下来，
连续几次就把流棘轮到 0，且只要队列还被标记就回不来。在与 TCP 共享的边缘瓶颈上
这会自我维持——RDMA 让出份额、TCP 扩张进来把队列顶住、RDMA 每次恢复都在完成前
被标记。对 WRITE 是丢几秒到几十秒吞吐，对 READ 是连接死亡（被限速的是 responder，
requester 在等响应，超过重试预算即 RC 终态）。

## 设计

**合成方式是被约束推出来的，不是选出来的。** 要求"不拥塞时输出必须等于份额"，
而 CC 的速率是相对**链路**标定的、且会棘轮，所以它的绝对值不携带任何关于"这条
流该拿多少"的信息；任何读它电平的合成方式都会继承棘轮。CC 的速率真正携带的是
它的**下降**——每一次都是那个 CC 用自己的单位做出的"网络要我让"的判断。

于是执行面累积下降、自己拥有回升：

$$rate = d\cdot level,\quad d\in[f,1]$$
$$d \leftarrow d\cdot\frac{cc}{cc_{prev}}\ \text{（CC 降速时）},\qquad
  d \leftarrow \frac{1+d}{2}\ \text{（其余，每个回升周期一次）}$$

只读比值还带来一个性质：**采样不需要标定**。"我们采到的数"与"CC 会 pace 到的
速率"之间任何常数因子都会在比值里约掉——这正是同一个合成器能同时坐在 DPA 上的
定点速率和 TCP 侧的 `cwnd×mss` 之上的原因。

**归因。** 让 CC 自由运行带来一个新回路：我们自己的整形造成排队，CC 把它读成
拥塞而降速，若照单接受就会整形得更狠。判据在本地——这条流是被**我们**卡住，
还是被**网络**卡住？

- **被我们卡住**（实发 ≈ 已下发，TCP 侧即 EDT 时间戳已在未来）：CC 反应的那个
  队列是我们压着它造成的，而份额本身就是对它的回答。这次降速**不计入**。
- **够不到已下发的速率**：限制它的是我们看不见也分不了的东西，这正是执行面无权
  处理的情形。这次降速**全额计入**。

这条规则自限（d 一降下来流又变回被我们卡住，降速不再计入，d 自己回到 1），所以
下界 f 是兜底而不是机制；它也不需要接收端配合，纯本地、按流。安全性落在执行面
有权威的地方：$d\le1$ 把流限在自己份额内，各份额之和按构造等于 root 容量。
公平保证的范围与 design.md §1.3 一致——边缘瓶颈，核心网不在其内。

`min(cc, level)` 作为对照臂保留（邮箱 `0xcca`）。

## 实现

| 步骤 | RDMA | TCP |
|---|---|---|
| ① 读并记录 CC 速率 | PCC 里的 DCQCN/ZTR **原样运行**，执行面只读它的 `cc_rate` | tc BPF 里 `bpf_tcp_sock()` 读 `snd_cwnd × mss_cache`，按流对增量累加成聚合窗口 |
| ② 合成 | 同一套比值合成 + 归因 | 同一套 |
| ③ 下发整形 | `results->rate`，硬件 pacing | EDT 时间戳，fq 出队 |

取 `cwnd` 而不是 `cwnd/srtt`：cwnd 是 CC 自己的决策变量，它的下降是 CC 在动作；
srtt 是测量量，会把抖动带进每个样本。窗口不是速率，但只读比值，那个换算因子在
跨越一次降速的比值里约掉。

## 拓扑与打流

- 常驻 VxLAN overlay，sgpu01→sgpu02，4 对 VF 直连；dpu2 的 p1 = 100G 是瓶颈。
- 8 个流集合全部 vf_n→vf_n：4 RDMA（`ib_write_bw`/`ib_read_bw`，每个 4 QP）
  + 4 TCP（`iperf3 -P4`，Cubic，**不开 ECN**）。READ 场景 server（responder，
  发数据方）在 sgpu01、client 在 sgpu02，数据方向仍 sgpu01→sgpu02。
- 政策：8 VM 等权，`max_rate=50G`，类权重 1:1，headroom=0.08 → c_root = 92G，
  **每流集合份额 11.5G**。交换机 swp37s0 绑 `motiv_default_ecn`。
- 每场 90 s，稳态窗 [40,85] s；停摆 = [5,84] s 内任一 RDMA 流集合 < 3G 的秒数。

| 臂 | RDMA 类 | TCP 类 | Jain | 停摆秒合计 |
|---|---|---|---|---|
| **观测器，DCQCN 原样（write ×8）** | **44.7G** | 44.6G | **1.000** | **0** |
| **观测器，READ ×2** | **44.7G** | 44.7G | **1.000** | **0** |
| **观测器，SEND ×1** | **44.6G** | 44.4G | **1.000** | **0** |
| **观测器，ZTR 原样（write ×2）** | **44.7G** | 45.3G | **1.000** | **0** |
| **观测器，两类都装（write ×2）** | **44.8G** | 44.8G | **1.000** | **0** |
| min(cc, level)，同一份代码（write ×4） | 41.7G | 46.3G | 0.991 | 11 |
| min(cc, level)，READ ×2 | 36.4G | 53.0G | 0.886 | 89 |

（每类应得 46G。观测器共 15 场，全部零停摆、每流 11.1–11.3G。）

**机制在探针里直接可见**（`fig_observer.png`）。观测器臂下那份未被改动的 DCQCN
**自由运行**：它不再是执行器，多数时间贴着线速，收到拥塞信号时下探——每场约
150 个采样点里有 2–36 个低于 0.99，最深到 0.000。在 `min()` 下**每一次下探就是
这条流当时的速率**，深的那几次正是 READ 臂丢 QP 的原因；在观测器下它们只是读数，
流全程稳在 11.2G。归因判据 144/144 判为"被我们卡住"，所以这些下降一次都没计入。

TCP 侧同样成立：BPF map 里读到聚合窗口 `cc_sum = 13.8 MB`（确实读到了内核 CC），
`d ≈ 1.0`，两场 Jain 1.000——正是设计的预测：TCP 在自有瓶颈上全程被我们卡住，
它的降速不计入，行为与改动前不可区分。

**ZTR 是归因规则最强的证据**：探针里 ZTR 自己的速率中位只有线速的 **0.138**
（它就是会一直往下压——这是 RTT-based CC 在异构类共享队列上的固有读数问题），
而流照拿满 11.2G 的份额，Jain 1.000。CC 完全没被改过，是归因把它那些"替 TCP
让路"的降速挡在了外面。

## 离线验收

- `tools/tests/couple_check.py` **9/9**：原样转录设备端整数算术（同样的 fxp20、
  同样的移位归一化除法、同样的钳位），钉住——原样 DCQCN 跑完 200 个 CNP 确实
  棘轮到线速的 1/1000 以下，而 d 回到份额的 99% 以上（同一 CC 状态下 `min()`
  只给出份额的 0.002%）；单次降速按比例复现；采样标定跨 1000× 时 d 落点相差
  0.03%；被我们卡住时 200 个 CNP 一次都不计入；规则自限；上限不可越。
- `tools/tests/law_check.py` **13/13**。

## 判定

- **耦合本身：正向，高信心。** DCQCN 完全未改动，8 场全部 Jain 1.000、零停摆；
  对照是同一二进制里的一个邮箱开关，min 臂在同样条件下 write 丢 11 s、READ 丢
  89 s。开销可忽略。
- **两类同一实现：正向，中等信心。** TCP 侧走完了同样的三步（读 `cwnd×mss`、
  同一合成器、EDT 整形），实测 d≈1、行为不变，符合设计预测。但这也意味着它的
  激活分支**还没有被真正跑过**：判别性证据要一场"整形器不是限制"的场景——把
  某个流集合的份额配到线速以上，EDT 戳就永远不在未来，归因判据判"不是我们"，
  它的 d 应当随内核 CC 的降速真的动起来。
- **两处已知不精确**（都可忽略，但记下来）：回升的整数不动点是 1048575 而非
  1048576，即稳态比份额低 0.0001%；TCP 的聚合窗口在连接消失而无最终更新时会
  残留（LRU 老化流表项但不减聚合），稳定连接下无影响，长期部署需要衰减。
