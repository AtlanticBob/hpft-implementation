# 余量 h 的取舍曲线（2026-09-09）

账本只把 $(1-h)C$ 分出去，$h$ 是设计里**唯一一个直接用吞吐换时延的旋钮**，其余的时延收益都是它的后果。这一组把交易的两端同时量出来：同一份满载负载下，24 个流集合的应用净荷，与一条穿过同一个出向队列的短流的完成时间。

## 环境

| 项 | 取值 |
|---|---|
| 拓扑 | sgpu01、sgpu03、sgpu04 三台各 4 个 VM 打 sgpu02 的 4 个 VM，单交换机 sn5600，接收端口 `swp37s0` 是 3:1 超订的瓶颈 |
| 负载 | `validation/scenarios/q_v1.spec`：24 个流集合，12 个 RDMA（每个 4 QP，WRITE，MTU 1024）+ 12 个 TCP（每个 4 条 Cubic 连接，不开 ECN），100 秒，五个 $h$ 完全相同 |
| 探针 | `ib_write_lat` 在一对空闲 VF（sgpu01/vf4 → sgpu02/vf4）上跑，`-H` 吐出每个样本；4 KB（几乎全是排队）与 64 KB（排队加一点串行化） |
| 每 VF 上限 | 50 G（发送端 devlink + 接收端 OVS meter） |
| 租户拥塞控制 | RDMA 是执行面里的 DCQCN，TCP 是 Cubic；执行面的律是令牌池 |
| 重传 | SR |

$h$ 在标准注册表里（`e_params.headroom`），所以每一档要改注册表、推到四台 DPU、重启代理——接收端只有这样才会读到新值。每一档都把**接收端 DPU 上实际的 headroom** 回读进 `results/h<档>/arm.txt`，记录的是设备上是什么，不是脚本要求了什么；跑完把 $h$ 放回 0.08 并核对。

## 结果

图：`fig/headroom.png`。左图是取舍本身——横轴短流完成时间、纵轴净荷，每个点是一个 $h$，越靠左上越好；右图是两个量各自对 $h$，拐点看得更直接。数据：`data/headroom.csv`。

| $h$ | 应用净荷 | 4 KB 中位 / 99 分位 | 64 KB 中位 / 99 分位 |
|---|---|---|---|
| 4% | 176.28 G | 12.22 µs / 45.88 µs | 236.2 µs / 410.0 µs |
| 6% | 176.29 G | 9.68 µs / 37.86 µs | 40.2 µs / 241.0 µs |
| **8%（设计点）** | **172.82 G** | **7.28 µs / 20.63 µs** | **23.1 µs / 88.6 µs** |
| 10% | 169.14 G | 6.40 µs / 15.91 µs | 22.2 µs / 71.7 µs |
| 12% | 165.41 G | 6.59 µs / 15.38 µs | 53.9 µs / 66.4 µs |

## 三件事

**4% 是被支配的，不该用。** 它和 6% 的净荷一模一样（176.28 对 176.29 G），时延却全面更差（4 KB 中位 12.2 对 9.7 µs，64 KB 中位 236 对 40 µs）。把余量压到 4% 是白白拿时延换了个零。原因大概是：余量太小时账本压不住端口，队列开始积，而积起来的队列反过来并不能让应用多送出字节。

**设计点 8% 正好在拐点上。** 6% 到 8% 花 3.5 G 换来 4 KB 中位快 2.4 µs、64 KB 的 99 分位从 241 µs 降到 88.6 µs（快 2.7 倍）；8% 到 10% 同样花 3.7 G，只换来 4 KB 中位快 0.9 µs、64 KB 中位几乎不动。**边际收益在 8% 之后掉下来。**

**12% 之后 64 KB 的中位反而回升**（22.2 µs 到 53.9 µs），打破了单调。每档只跑了一遍，所以这一点可能是噪声；但它的 99 分位仍在下降（71.7 到 66.4 µs），中位与尾巴走反方向，更像是余量大到某个程度之后流之间的相互调度变了，而不是单纯的抖动。**要把 12% 写进论文得先补几遍。**

## 对论文的意义

这条曲线把"HyperFront 牺牲 5.6% 吞吐"从一句需要辩解的话，变成一个有据可依的设计选择：**吞吐与时延的交换率不是常数，8% 处于边际收益的拐点**，往下走（6%、4%）时延变差得比吞吐涨得快，往上走（10%、12%）吞吐掉得比时延改善得快。同时它也说明这个旋钮是留给部署者的：时延敏感的集群可以调到 10%，吞吐优先的可以到 6%，但不该到 4%。

## 一个测量守卫

探针跑得比负载长会量到空端口，数字会好看得离谱（这一坑在 `results/fct_20260909/` 里踩过）。每一档都记下自己的起止与负载终点（`results/h<档>/windows.txt`），蒸馏对越界的档直接拒收。本轮五档十个探针全部在负载内完成，最紧的一个也还剩 77 秒。

## 复原

`run.sh` 不自己复原 $h$（它一档只做一档的事），复原在批量脚本里：跑完把注册表写回 `"headroom": 0.08`、`deploy_check --deploy` 推下去、`roles.sh all` 重启，然后回读核对。**漏掉这一步，lab 就停在最后一档的 $h$ 上，而每一层服务照常报健康。**
