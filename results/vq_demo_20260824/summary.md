# vq-sched demo：虚拟公平调度器 + 份额跳步 / 排队时长砍速律，四机 incast8 首验（2026-08-24）

分支 `vq-sched`（hpft-implementation），设计依据 `~/hyperfront/hyperfront_redesign_proposal.md` 加两条发送端优化（乘性增改为向 $(1+\varepsilon)\hat g$ 的对数一阶跳步；乘性减改为 $R=\hat g(1-d/D_r)$、地板 $\varphi_{\min}\hat g$）。一个 registry 开关 `e_params.law` 在 `vq`（新设计）与 `track`（design.md v2）之间切换，两臂共用同一份代码、同一条遥测格式 `{g, r, d}`。

## 拓扑与打流

| 项 | 值 |
|---|---|
| 接收端 | sgpu02（DPU hpft-dpu2），p1 200G，headroom 8% ⇒ 账本根 $C'=184$G |
| 发送端 | sgpu01、sgpu03、sgpu04，各 4 个 VF |
| 流集合 | 每发送端 4 对 RDMA（`ib_write_bw -q 4`）+ 4 对 TCP（`iperf3 -P4`），直连对 vf_n→vf_n，共 24 个流集合 |
| 政策 | 4 个目的 VM 等权、MaxRate 50G（根先绑）、类权重 1:1、per-sender 权重 1 ⇒ 每流集合应得 $184/24 = 7.67$G |
| 时长 | 90 s，稳态窗 40–85 s |
| 执行面 | RDMA 走 PCC RP（预算 13 ms 合并、3% 迟滞、水位赋值），TCP 走 host fq+EDT；CC 耦合 $d\cdot level$ 不变 |
| 运行器 | `tools/tests/incast8_regression.sh <tag> --receiver sgpu02 --senders sgpu01,sgpu03,sgpu04`，每场重启 RP 与 agent |

## 判断

**正向：新设计在真实四机拓扑上成立。**接收端只靠虚拟队列的积压做分配（没有需求估计、没有积压判别、没有滞回），发送端只靠 $\{\hat g, d\}$ 两个数，1 秒均值上的公平与 v2 完全一致（类内 Jain 1.000、每目的 VM 1.000、利用率 100%），而且**信号在均衡处是活的**——vqt 臂里每个流集合的虚拟队列在 56–67% 的时刻非空，平均排队时长 1–4 ms，这正是设计想要的"队列裁定均衡"的形态；v2 的账本在同一场景下恒为空。

**负向：毫秒尺度的平稳性明显不如 v2。**vqt 臂 RDMA 流集合的 20 ms 采样标准差是 0.30G（v2 是 0.03G），TCP 是 0.12G（v2 是 0.01G），发送端 $R$ 在 5.3–10.2G 之间摆动。这是设计里"目的地放在份额上方 $\varepsilon$"的直接代价，加上 RDMA 执行面自身的滞后（RP 13 ms 推送、3% 迟滞、逐步爬坡）把 $\varepsilon$ 的小过冲放大成更深的队列再换来更深的砍。v2 的平直线是靠信号失效换来的，两者不能都要；这一点在提案里已经预告，现在有了数字。

**值得深究。**信心：接收端信号正确性高（三臂稳态份额都对）；发送端律的参数还没定，$\varepsilon$、$D_r$、hold 三个都只试了一到两个值。

## 三个发现（每个对应一个组件是否需要改）

1. **发送端律的形式成立，但 $\varepsilon$ 和 $D_r$ 要往小和大取。**$\varepsilon$ 从 5% 到 2%、$D_r$ 从 60 ms 到 150 ms，把 RDMA 的抖动从 1.18G 压到 0.49G，公平与利用率不变。$D_r$ 的稳定下界（$>0.64\tau_{\rm eff}\approx 15$ ms）远低于实际需要的值，因为约束它的不是环路稳定性而是执行面滞后期间队列的累积。下一步应扫 $\varepsilon\in\{0,1,2\}\%$、$D_r\in\{150,300\}$ ms，并加一个"队列低于门限视为空"的死区试验。

2. **虚拟调度器需要"积压保持"，否则份额提示会被系统性抬高。**这是 demo 最重要的发现。提案里"兄弟的需求就是它排着的字节数"在流体模型里成立，在 lab 里不成立：一个刚被砍到份额以下的流集合队列立刻清空，调度器把它读成"想要得少"，把它没用的份额分进所有兄弟的 $\hat g$；24 个流集合时 $\hat g$ 平均 9.9G，比真实份额 7.67G 高 30%（vq_i8 臂），于是所有人按 30% 过冲、队列猛涨、砍到 $\varphi_{\min}$ 地板（3.83G），整个群体极限环。保持 50 ms 后 $\hat g$ 回到 8.0G（高 4%），抖动降 3–6 倍。这不是回到旧设计的积压判别——判据不再是"节点饱和"这种阈值，而是"这条流最近排过队且还在发"，没有滞回参数，只有一个时间常数。提案文档 §1.3/§1.4 需要按此修订。

3. **RDMA 执行面是剩余抖动的主要来源，TCP 侧已经接近平稳。**同一律、同一参数下 TCP 的抖动只有 RDMA 的 40%（0.12 对 0.30），且 TCP 的 $R$ 范围 7.3–9.7G 对 RDMA 5.3–10.2G。差别全在执行点：EDT 即写即生效，RP 有 13 ms 合并、3% 迟滞、12.5%/步爬坡。这是 ops_notes 已知的"收敛长尾在 RP 爬坡"同一件事，在新律下代价更高，因为队列在执行面滞后期间持续积累。设计侧可以考虑把 $d$ 的累积按执行面已确认的速率而不是线上速率计（对账 §6.4 的精神），或把砍速的参考从 $\hat g$ 改为上一拍已下发的预算。
