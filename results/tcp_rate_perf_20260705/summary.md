# TCP shaper 高频改速性能(2026-07-05)

问题:TCP shaper 执行高频速率变动时性能是否够好、频率能到多高。用类 RDMA
S4 的方法实测,分控制路径与数据面两层。环境:刷机后 DOCA 3.4 / fw 32.49,
host vf0(dpu1vf0)TC-BPF EDT + fq,iperf3 单流,tcp-shaper-controller 的
direct bpf() 后端。

## 层 1 — 控制路径(direct bpf() map 更新)

| 目标 Hz | 达成 Hz | deadline miss | 单更新 p50 | p99 | max |
|---|---|---|---|---|---|
| 100 | 100.0 | 0 | 48 µs | 0.35 ms | 2.0 ms |
| 500 | 500.0 | 0 | 47 µs | 0.34 ms | 1.8 ms |
| 1000 | 999.9 | 0 | 47 µs | 0.34 ms | 1.4 ms |
| 2000 | 1999.9 | 13 | 46 µs | 0.34 ms | 1.5 ms |
| 5000 | 4999.7 | 558 | 46 µs | 0.33 ms | 19.7 ms |
| 10000 | 9999.6 | 8079/20000 | 39 µs | 0.29 ms | 48 ms |

**单次 map 更新极快:p50 48 µs、p99 0.34 ms。控制路径无抖动上限 ~1000–2000 Hz**;
≥5000 Hz 才因单线程 python + OS 调度出现 deadline miss 与尾延迟(bpf 更新
本身不变)。对比 RDMA 的 mailbox RPC(13 ms/次、75 Hz 封顶),**TCP 控制路径
快约 270 倍**——控制路径完全不是瓶颈。

## 层 2 — 数据面收敛(阶跃响应)

host VF tx 速率 10 ms 采样,单次速率阶跃:

| 阶跃 | 收敛时间(±15%) |
|---|---|
| 降速 8G→2G | 196 ms |
| 升速 2G→8G | 213 ms |

**两个方向都 ~200 ms 且对称** → 瓶颈不是 fq 队列排空(那只影响降速),而是
**TCP 拥塞控制协议本身的收敛惯性**(cwnd 调整 + ACK 时钟 + pacing 爬升)。
EDT map 是即时生效的(下一个包即用新时间戳),但 TCP 端到端吞吐收敛到新速率
是协议固有的 RTT × 若干来回量级。shaper 实现无法根本消除这一项。

## 层 3 — 持续方波改速的效率(iperf3 goodput,交叉验证)

方波 8G/2G(平均 cap 5G),对照静态 5G cap 的 goodput 4.99G:

| 方波频率 | 半周期 | goodput | 损失 |
|---|---|---|---|
| 静态 5G | — | 4.99 G | 基准 |
| 2 Hz | 250 ms | 4.17–4.48 G | -10~16% |
| 5 Hz | 100 ms | 3.99 G | -20% |
| 10 Hz | 50 ms | 3.99 G | -20% |
| 20 Hz | 25 ms | 4.33 G | -13% |
| 50 Hz | 10 ms | 4.35 G | -13% |

**TCP 在任何改速频率下都不崩溃**,goodput 损失 13–20%。曲线非单调:最差在
**5–10 Hz**(半周期 ≈ 200 ms 收敛时间,流始终处于瞬态、从不稳定);>20 Hz
时改速被数据面平均化,损失反而回落。

## 结论(数据支撑)

1. **控制路径不是瓶颈**:48 µs/更新,能撑 1000–2000 Hz,比 RDMA 快 270×。
2. **shaper 数据面机制也不是瓶颈**:EDT map 即时生效。
3. **真正的限制是 TCP 协议固有的收敛惯性 ~200 ms**(双向对称)→ "有意义的
   独立改速"上限约 **5 Hz**;控制路径的 kHz 能力用不上,因为 TCP 吞吐跟不上。
4. **与 RDMA 瓶颈位置相反**:RDMA 慢在控制面(mailbox 13 ms),数据面硬件
   pacing 响应快(S4 里 10 Hz 双峰干净);TCP 快在控制面(48 µs),慢在数据面
   (TCP cwnd/ACK 惯性 200 ms)。这是两种协议的本质差异,不是实现优劣。

## 可缓解方向(不改 TCP 栈)

- 用**渐变**替代阶跃改速(多步小幅),减小每次 cwnd 扰动;
- 收敛期内不重复改速(≥200 ms 去抖),避免 5–10 Hz 的最差区;
- 若需更快响应,配合 BBR/pacing 感知的速率调整(fq 已在 pace,但 cwnd 仍是
  loss/RTT 驱动)。
- 根本上:TCP 的速率收敛惯性是协议特性,对"cap 高频变动"的需求,TCP 天然
  不如 RDMA 的硬件 dequeue-rate 敏捷。这是分协议实现下应接受的差异。
