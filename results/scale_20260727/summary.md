# 规模：控制环撑到多少流集合（2026-07-27）

回答一个此前没有数据的问题：**这套设计能带多少个流集合，Python 实现
在哪里开始撑不住。** 后者直接决定 C/C++ 改写值不值得、以及该改哪一段。

## 为什么必须离线做

流集合 = (src VM, dst VM, class)。本 lab 每端 4 个 VF、两个类，
**上限就是 4×4×2 = 32**，远低于有意思的区间。所以规模曲线只能在离线
跑，lab 的职责是确认曲线的小 N 端。

`bench_scale.py` 直接驱动**生产代码本身**（`rx_agent` 的 `Scheduler`、
`VQMarker`、`Telemetry`），不是模型，所以测出来的是 DPU 上真正在跑的
那段代码。

## 结果

每拍耗时（1 ms 周期 = 1000 µs 预算）：

| 流集合 | VM 数 | water-filling | VQ | 遥测打包 | 合计 | 占预算 |
|---|---|---|---|---|---|---|
| 32 | 4 | 415 µs | 49 | 35 | **500 µs** | 50% |
| 128 | 8 | 981 | 141 | 91 | **1213 µs** | **121%** |
| 288 | 12 | 2089 | 329 | 207 | 2626 | 263% |
| 512 | 16 | 3555 | 593 | 360 | 4508 | 451% |
| 1152 | 24 | 7845 | 1370 | 827 | 10041 | 1004% |
| 2048 | 32 | 13492 | 2543 | 1490 | 17524 | 1752% |

**Python 在约 100 个流集合处撑不住 1 ms 周期。**

两个结构性事实：

- **water-filling 吃掉 77% 的时间**，在每个规模上都是。C/C++ 改写要是
  只改一处，就改它；改别的都是零头。
- 增长接近线性而非二次：32→2048 是 64 倍流集合、35 倍耗时。单遍级联
  （`waterfill_ceilings`）的 O(N log N) 兑现了，**瓶颈是常数因子不是
  复杂度**——这恰恰是换语言能解决的那一类，而不是需要换算法。

## lab 确认（小 N 端）

`lab_confirm.sh`：20 个流集合（4×4 TCP 网格 + 4 条直连 RDMA），源端
限速使聚合远低于瓶颈（合计 54.7 G / 100 G）。

- **实测 944–945 ticks/s**（标称 1000），即控制环仍满速运行；
- 基准在 20 流集合处预测约 310 µs/拍 = 31% 预算，与"仍满速"一致；
- 差的 ~5.5% 是慢环（megaflow dump，`dump_ms` 1.8–1.9）摊到每秒的开销，
  与流集合数无关。

## 对设计文档 §7 的勘误请求

§7 现写"1 ms 周期下两端代理各占单核 < 9%，调度一遍 448 µs（20 流集合），
**舒适规模数百流集合**"。前半段与实测一致（20 流集合 ~310 µs、32 流集合
500 µs）；**"数百流集合"不成立**——128 个流集合就已经是周期的 121%。
现行实现的舒适规模是**几十个流集合**，上限约 100。已同步给设计侧。

## 顺带产出：实验守卫

`tools/lab-infra/flow_preflight.sh` / `flow_postflight.py`。存在的理由是
今天两次代价高昂的经历：QP 的 RC 错误完成是**终态**，被打死的流对不会
自己回来，而**每一层都还在报健康**——有一轮 incast8 因此读出 Jain=0.698，
差一点被当成公平性回归上报，而当时分配器其实完全精确。

- **preflight**：逐对（**顺序、不并发**）验证流对能起来，跑之前拦住。
- **postflight**：只把**无歧义的故障**判为失败——流表里有、线上恒零
  （被打死的 QP）；启动窗口链路持续 98% 饱和（过载特征）。
- **grant vs wire 表是信息，不是判据**：流集合跑在 pace 之下**本身不是
  故障**（目标是天花板不是授予，应用受限或发送端树绑定都会如此）。而且
  两个参照都不够——对 pace 比会对每条应用受限的流误报，对授予 e 比会
  漏掉被压垮的流（e 会跟着塌）。**"不想要"和"要不到"在接收端本质不可分**，
  这正是 §3.2.2 存在的理由，脚本不该假装能裁决它，所以只呈现、由分析者
  判断。

自测：故意限速的一轮 0 FAULT（信息表显示 ~50%，正确）；已知坏的一轮
报出 FAULT hot，信息表一眼可见 RDMA 35–39% / TCP 105%。

# C 改写（同日）

## 改了哪一段、为什么只改这一段

规模测量给出的靶子很明确：water-filling 占每拍开销 77%，且 64 倍流集合
只涨 35 倍耗时——**单遍级联的 O(N log N) 已经对了，剩下的是常数因子**。
常数因子是换语言能解决的，换算法不能。所以改写的范围就是这一段，不是
"把 agent 用 C 重写一遍"。

`tools/dpu/fastfill.c`，经 ctypes 加载（DPU Arm 只需要 gcc，不需要
Python 头文件）。`.so` 缺失时 `fastfill.py` 自动回落到纯 Python 路径，
所以没编译过的机器上 agent 照常能跑，只是回到旧的规模上限。

## 分两步做，第二步是被数据逼出来的

**第一步：只换两个原语**（`waterfill` / `waterfill_ceilings`），树结构
逻辑留在 Python。结果 500→394 µs（32 流集合），上限从 ~100 推到 ~180。
但 water-filling 仍占 72%——**瓶颈已经不是算术，而是 ctypes 编组**：
288 个流集合的一拍要跨边界约 37 次，每次都在几微秒的真实计算外面重建
Python 的 dict 和 list。

**第二步：整棵树进 C**（`hpft_entitlements`），每拍只跨一次边界。

| 流集合 | 纯 Python | 只换原语 | 整树 C | 相对 Python |
|---|---|---|---|---|
| 32 | 557 µs | 394 | **193** | 2.9× |
| 128 | 1256 | 885 | **462** | 2.7× |
| 288 | 2556 | 1461 | **973** | 2.6× |
| 512 | 4391 | 2376 | **1443** | 3.0× |
| 2048 | 17711 | 8805 | **5547** | 3.2× |

**1 ms 周期的容量上限：~100 → ~290 个流集合。** 设计文档 §7 的"舒适
规模数百流集合"由此成立——这本来就是实现该解决的问题，不是文档的错。

顺带一个不需要 C 的免费优化：遥测打包每拍都在重算 `fsid.encode()[:64]`，
而它对一个流集合终生不变，缓存后 2048 流集合处再省 17%。

## 正确性

改写动的是政策份额，"差不多对"不可接受——系统性偏差会表现成一个没人
解释得清的公平性结果。所以对拍做了两层：

- **原语层**（`fastfill_test.py`，4000 个随机用例，含全饱和 / 全不饱和 /
  零 cap / 等 cap 平局 / 1e-3–1e6 动态范围 / 三种 repl 模式）：x86 上
  最大偏差 **0.000e+00**（逐位相同）；DPU aarch64 上 **1e-10** 级
  （FPU 舍入差异，在容差内）。
- **整树层**（16296 个流集合样本，随机政策/权重/MaxRate/零需求流）：
  不一致 **0 处**，最大偏差 1.5e-5 bps。

对拍过程中抓到一个真 bug：C 里对"总需求为 0 的 VM"直接跳过，导致其下
流集合的 **ê 为 0**。但 ê 的定义是把自己的需求置无穷——**一个当前空闲
的 VM 天花板非零**，它的流集合应当拿到。16296 个样本里 143 处不一致
全部来自这一条。纯 Python 参照实现之所以留着，就是为了能这样对拍。

## lab 验证

DPU Arm 上重新编译、`rx_agent` 启动 banner 增加 `fill=C` 指示。同一个
incast8 场景：

| | Jain | 合计 | util | 每流 |
|---|---|---|---|---|
| Python 版（i8final_1）| 1.000 | 95 G | 98% | 11.6–12.1 G |
| **C 版（i8c_1）** | **1.000** | 94 G | 97% | 11.7–11.8 G |

postflight 0 FAULT，rx 实测 980 ticks/s。

## 下一步的靶子（有数字，不是猜）

288 流集合处的构成已经变了：water-filling 481 µs（49%）、**VQ 步进
312 µs（32%）**、遥测打包 180 µs（19%）。要再往上推，下一个该动的是
VQ 步进——但它**带跨拍状态**（每流集合的账本），把它移进 C 需要 C 侧
持有稳定的流集合索引，比纯函数的 water-filling 复杂得多。在有明确需求
（真的要撑 500+ 流集合）之前不做。

# 发送端与拍节尾部（同日，补测）

## tx 才是更紧的 agent

第一轮规模测量只测了 rx，这是分析的缺口。补测后结论改变：**tx 每收到
一条遥测就重算整棵发送端树**（1 ms 周期即 1000 次/秒），288 流集合处占
132% 预算，而 rx 只有 97%——**真实上限由发送端决定**。

发送端树与接收端是同构的三层天花板级联（src VM → 类 → 流集合，根容量
为本机上行、叶权重恒 1），因此复用同一个 C 入口。属性对拍 13287 样本
0 处不一致。

| 流集合 | 每报文（改前 → 改后）|
|---|---|
| 32 | 292 → **214 µs** |
| 128 | 664 → **567 µs** |
| 288 | 1315 → **1138 µs** |

## C 改写在哪里停，为什么

提升只有 24%（对照 rx 的 2.6×），而**原因比数字重要**：剩下的开销不是
任何单个函数里的算术，是 **Python 逐流集合触碰 N 个对象**——遥测解析
242 µs、逐流集合的律与执行 353 µs、每次 C 调用前的 dict→list 编组。
接收端剩下的是同一形态（VQ 312 µs、遥测打包 180 µs）。

这是**数据结构问题，不是语言问题**：要继续推，得把逐流集合状态改成
带稳定索引的数组而非 string-keyed dict，那是两个 agent 的结构性重构，
不是某个函数的改写。按本项目对自己的规则（没有证据能挣回自己的机制
就不建），现在不做：lab 物理上限 32 个流集合，当前上限约 200，**8 倍
余量**。

## 拍节尾部：没有 GC 问题

规模数字说的是**均值**，而决定"要不要把整个循环搬进 C"的是**尾部**
——停顿的 Python 循环不只是延迟决策，它可能让速率估计的字节与时间脱钩
（2026-07-11 有过"干净的 6G 读成 ±60% 噪声"的事故）。

给两个 agent 都加了直方图。接收端按"这一拍是否跑了慢环"分开统计，
因为把两者混在一起会让**可预期、可归因**的开销看起来像抖动：

| 接收端 | 拍数/10s | p50 | p99 | p999 | max |
|---|---|---|---|---|---|
| 普通拍 | 9800 | 164 µs | 280 µs | 331 µs | **479 µs** |
| 慢环拍 | 49 | 3784 µs | — | — | 18385 µs |

**超周期的拍数恰等于慢环执行次数**（49–50），一个不多。99.5% 真正干
控制活的拍最大 479 µs，**没有 GC 尾部**。

发送端（每报文）：p50 123 µs、p99 292–406 µs、max 2.2–3.1 ms，
**每 10 秒仅 1–2 个超周期（0.015%）**。

**结论：C 改写到此为止。** 判据是测量前就定好的——尾部干净、丢拍来自
慢环即停。

慢环本身（megaflow dump + 解析）中位 3.8 ms、最坏 18 ms、每秒 5 次。
这个代价**被设计吸收**：律以实测 `dt` 离散（$\alpha=1-e^{-k\,dt}$），
4 ms 的空洞被精确补偿。这是选精确解而非字面 $kT$ 的第一份硬证据——
后者无法补偿，会直接过冲。

两个直方图都留在生产里：每拍一次 append、每 10 秒一行，而它是下次
遇到同类问题时**直接给出答案而不是让人从 tick 率反推**的仪器。
