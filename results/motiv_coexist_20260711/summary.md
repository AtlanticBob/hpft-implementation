# Motivation 实验：lossy RDMA 与 TCP 的共存不公平（2026-07-10/11）

## 实验是什么

把若干条 RDMA 流和若干条 TCP 流同时打向同一个目的地，流数比例从 4:1
扫到 1:4，观察每一条流分到的带宽。瓶颈是交换机朝接收端的出口（接收端
链路降到 25G，发送端保持 200G，所以拥塞一定发生在交换机的出口队列上，
这正是 ECN/队列配置生效的位置）。RDMA 是 lossy RoCEv2（两端 PFC 与全局
pause 均关闭），拥塞控制为网卡固件原生 DCQCN；TCP 是 Cubic、未启用
ECN。每个数据点跑 60 秒，读数为每条流的自报 goodput；同时从交换机取
每队列的差分计数（发送帧数、ECN 标记数、丢弃数）作为机制证据。

丢包恢复维度通过两端 BF3 的 RDMA_SELECTIVE_REPEAT_EN 固件开关切换
（GBN ↔ SR，各需一次双端重启），队列配置维度在交换机上切换，共
2 × 3 × 7 = 42 个数据点。

## 三种队列配置与结果

**共享队列、无 ECN（noecn）**：两类流量挤同一个队列，队列纯 tail-drop。
结果是同归于尽：DCQCN 收不到任何拥塞信号，RoCE 以线速盲发把队列打爆，
GBN 下每轮出现约 5.8 万次乱序（整窗重传风暴，多流时部分 QP 直接死亡），
RDMA 每流只剩 ~0.9G，TCP 被压到 0.1-0.4G，25G 的链路总共跑出约 1.2G。
换成 SR 也无济于事（每流 ~0.45G）——没有拥塞信号的 lossy RoCE 是不可
用的，这一点与恢复算法无关。

**共享队列、RoCE 式 ECN（shared，主图上排）**：同一个队列，但按 RoCE
运营惯例开了 ECN（超过 156KB 即标记，概率 100%）。交换机对带 ECT 的
RoCE 包做标记（实测 99.996% 的数据帧被标记），对不带 ECT 的 TCP 包则
按同一条曲线直接丢弃。结果是**不公平反转**：DCQCN 温和地贴着阈值跑，
TCP 一冒头就挨丢、永远攒不起自己需要的队列，RDMA 每流稳定拿到 TCP 的
约 3 倍（1:1 时 17.3G 对 5.9G）。这说明共享队列没有公平的配置点：
不开 ECN 是双输，开 RoCE 式 ECN 则轮到 TCP 被系统性压制。

**按类分队列 + 60/40 WRR（split，主图下排）**：RDMA 打 DSCP 26 进独立
队列，与 TCP 队列按 60:40 加权轮询。类间隔离立竿见影——RDMA 类总带宽
精确钉在 60%（13.88G）、TCP 类 40%（9.6G）、类内各自均分。但 GBN 下
有一个刺眼的例外：4 条 RDMA 流时（4:1 点），RDMA 类内部爆发重传风暴
（1.9 万次乱序、线上约 75% 是重传字节），每流崩到 1.2G——**TC 隔离
保护得了类间，保护不了 RDMA 被自己的整窗重传拖垮**。换成 SR 后这个点
完全干净（每流 3.47G、零乱序），42 个点里 SR-split 是唯一全绿的组合。

## 给论文的叙事要点

第一，共享队列下不存在公平配置：ECN 开与不开只是换一个受害者（这比
"TCP 挤占 RDMA"的单向表述更强，且两个方向都有我们自己的实测数据）。
第二，QoS TC 队列确实能解决类间隔离——这正好承接正文对 TC 方案的
批评：它是静态的、队列数量有限，而云环境需要租户 × 类的双重隔离，
TC 只能保一头。第三，SR 是必要的（GBN 连自己队列里的多流场景都撑不住）
但不充分（共享队列的不公平在 SR 下原样存在）——堵住"上 SR 就够了"
的评审退路。
