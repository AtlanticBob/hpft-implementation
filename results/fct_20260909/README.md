# 短流的完成时间（FCT，2026-09-09）

排队那组实验证明了整形器把接收端口的队列压了两个数量级；那是机制。这一组问的是结果：**端口满载时，一条短流要多久才跑完。** 答案是快 66 到 332 倍，而且流越大差得越多。

## 环境

| 项 | 取值 |
|---|---|
| 拓扑 | sgpu01、sgpu03、sgpu04 三台各 4 个 VM 打 sgpu02 的 4 个 VM，单交换机 sn5600，四个 p1 口 200 G，接收端口 `swp37s0` 是 3:1 超订的瓶颈 |
| 负载 | `validation/scenarios/q_v1.spec`：24 个流集合，12 个 RDMA（每个 4 QP，WRITE，MTU 1024）+ 12 个 TCP（每个 4 条 Cubic 连接，不开 ECN），130 秒，两臂完全相同 |
| 探针 | `ib_write_lat` 在一对空闲 VF（sgpu01/vf4 → sgpu02/vf4）上跑，经过同一个出向队列，`-H` 吐出每一个样本 |
| 流大小 | 4 KB、16 KB、64 KB、256 KB、1 MB，五档在同一个负载窗口里顺序跑 |
| 每 VF 上限 | 50 G（发送端 devlink + 接收端 OVS meter） |
| 租户拥塞控制 | RDMA 是执行面里的 DCQCN（`0xccd 2`），TCP 是 Cubic |
| 重传 | SR |

**两个臂只差整形器。** `hpft` 是缺省态（账本 + 令牌池）；`cc` 是只有租户拥塞控制（执行面忽略预算、发送端代理停掉、TCP 速率表清空）。

## 口径：报的数就是完成时间，不要乘二

`ib_write_lat` 报的是一次往返的一半，而它的往返是**对称的**——两端写同样大小。所以它报的那个数就是"这么大的一次写单向送达要多久"，也就是 FCT，**不需要乘二**。排队那组实验里的往返图需要乘二，这一组正相反。

## 为什么会这样

**只有拥塞控制时，每一条短流都要把自己的字节拖过一个 62 MB 的常驻队列。** 排队实验量到那个队列在整个负载期间一次都没空过、中位深度 62.9 MB，在 200 G 上正好是 2.5 ms。所以 4 KB 的流也要 1.06 ms——它的字节量根本不重要，时间全花在排队上。这解释了两件事：小流的完成时间与大小几乎无关（4 KB 1063 µs 对 16 KB 1237 µs，大了四倍只慢 16%），以及分布极窄（99 分位只比中位高 2%，因为队列稳稳地满着）。

**加了整形器，完成时间回到由流自己的大小决定。** 4 KB 的 7.1 µs 基本是一个往返，1 MB 的 162 µs 接近 50 G 上搬 1 MB 所需的时间。右图里蓝线的斜率就是串行化，红线的斜率是队列——两条线的距离随流增大而拉开，因为无整形时每一条流都要重新排一次那个满队列。

**代价仍然是那 5.6% 的吞吐**（182.2 G 对 172.0 G），与排队实验同源：账本只分 $(1-h)C$。

## 对论文的意义

排队那组给的是"交换机队列短了"，这一组给的是"应用快了"，后者才是时延敏感工作负载能直接引用的数字。两组合起来支撑同一句话：**一个把总量压在容量之下的整形器，不改租户任何东西，就让共享这个端口的短流快两个数量级**，而且这是公平性机制自带的收益，不需要为时延单独划队列。

99 分位与中位的比值也值得写：无整形时是 1.02（队列稳定地满），有整形时在 2.6 到 7.5 之间（队列大部分时间是空的，偶尔有突发）。**整形不是把时延压成一条直线，是把它从"永远很差"变成"通常很好、偶尔一般"。**

## 一个测量上的坑

探针跑得比负载长会量到空端口，而且数字会好看得离谱：第一轮 `cc` 臂的 256 KB 一度报出中位 33 µs、99 分位 13.8 ms——一半样本是负载停了之后取的。现在每一档都记下自己的起止与负载的终点（`results/<臂>/windows.txt`），蒸馏对越界的档直接拒收而不是把两种状态平均在一起。`cc` 臂的 1 MB 还额外撞过每档 40 秒的超时（它要 42 秒），超时已放宽到 90 秒、该档次数减到 250。

## 复原

`run.sh` 每跑完一遍把四台发送端的执行面写回缺省臂（`0xccd 2`、`0xcce 0 22`、`0xcce 0 12`），只有拥塞控制那一臂另外重新拉起发送端代理。**这些不是自恢复的。**
