# §4.3 第一层接线 + 两层实证（2026-07-28）

设计的发送端政策分两层执行：第一层是 NIC 硬件限速器，类盲、静态、在
控制环之外，负责让**售卖原则**在软件失效时仍然成立；第二层是发送端加权
注水树，负责超售缩水、类间隔离与借用。第一层此前**没有接线**——`tx_max`
在活代码里的命中数为 0，registry 里八个 VM 的 MaxRate 只由软件执行，
两台 DPU 上八个 rate leaf 全都不带限速。本轮把它接上并验证。

## 结论

| | 结果 | 判断 |
|---|---|---|
| 政策 → 硬件同步 | 编辑 registry 后 ≤200ms 检出、再 14ms 写入 NIC | 成立 |
| 20× 降档 QP 存活 | **3/3**（软件限速器单独时 3/3，无限速器 2/3） | 硬件瞬时阶跃不构成新危险 |
| 硬上限压得住软件 | 软件给 30G、硬件 10G → 线上 **9.78G** | 售卖原则有硬件背书 |
| 硬件绑定时控制环 | pace/R/tree 全程纹丝不动 | 跟踪律不把执行面失效误读为拥塞 |

## 一、政策 → 硬件的同步

`tools/dpu/hw_maxrate.py`，由 tx_agent_e 在启动时和每次 registry mtime
变化时调用。同一份政策同时喂给两层，所以两层不可能被配置成不一致；每次
重载都重新断言，因为固件复位或一条手工 devlink 命令都会悄悄把它抹掉。

三轮实测，从 agent 检出政策变化到 NIC 开始执行新额度：**14 / 14 / 14 ms**。
检出本身受 200ms 轮询上界约束。

**单位是这个原语最大的坑，而且它有两个单位**（本机 iproute2 实测）：

```
set ... tx_max 30000000000   ->  show 显示 "tx_max 30Gbit"
                             ->  -j   报告  "tx_max": 3750000000
```

即**命令行入参是 bit/s，JSON 读回是 byte/s**，差 8 倍。第一次部署就栽在
这上面：要 30G，实际只给了 3.75G，而且两端毫无报错，是回读才发现的。两个
转换现在都锁在 `hw_maxrate.py` 一处，跨该模块 API 的值一律是 bit/s，并有
离线测试（`hw_maxrate_test.py`，10 项）钉住这个来回。另外绝不能用带后缀的
写法：同一固件上 `3gbps` 会被读成 3 GB/s = 24 Gbit/s。

## 二、20× 降档：硬件瞬时阶跃安全吗

§5.1 的过渡条款把外部阶跃摊到软件树上，其"不削弱售卖原则"的论证依赖第一层
立即执行新额度。接上第一层之后就出现一个之前问不出来的问题：**硬件上限不
会渐降**——不渐降正是它的意义——所以 20× 政策削减现在会作为一次瞬时节流
直达 NIC。M5d 当年在带载下只试过 ≤4× 的档（10G/5G/20G），20× 无记录。如果
瞬时硬件阶跃本身足以打死 RC 连接，那这条款的前提就把条款自己否了。

`downstep_run.sh`，单条 RDMA 流独占 root，MaxRate 30G → 1.5G → 30G：

| trial | 存活 | 硬件延迟 | 树 30→1.5G | 线上跟随 | 计数器 高/低 |
|---|---|---|---|---|---|
| 1 | yes | 14 ms | 47 ms | 47 ms | – |
| 2 | yes | 14 ms | 47 ms | 47 ms | 29.32 / 1.46 G |
| 3 | yes | 14 ms | 40 ms | 40 ms | 29.32 / 1.46 G |

**3/3 存活**。树的下降是 30G 起每 13ms 折半，约 4.3 次折半到位，实测 40–47ms
与之相符；线上跟随在同一时间尺度内，无停顿、无坍塌。升档一拍到位（1.5G →
30G 后线上 60ms 内回到 28G+）。

值得单独记一笔：整个降档过程中 **R 恒为 30.00G**。律根本没动，因为接收端给
的目标 u 没变（它管的是 dst VM 上限，与发送端 MaxRate 无关），`pace =
min(R, Tree)` 里绑定的一直是 Tree。这是 §5.1 结构性论证在硬件上的直接读数：
限速器只托住 Tree，律的动力学与它正交。

## 三、硬上限压得住软件吗

`backstop_run.sh`。让两层**故意不一致**——政策与软件树都说 30G，只把硬件
限速器手工压到 10G（正常路径做不到这件事，所以这里绕过政策）：

```
  t(s)     线上     pace        R     tree
  14.2    29.33    29.95    30.00    29.95
  16.2    12.16    29.95    30.00    29.95     <- 硬件 10G
  20.2     9.77    29.95    30.00    29.95
  35.4     9.75    29.95    30.00    29.95
  41.5    13.15    29.95    30.00    29.95     <- 硬件解除
  45.5    29.34    30.00    30.00    30.00
```

线上稳定在 **9.75–9.79G**，即 10G 额度的 97.8%（差额是帧开销）。软件层完整
地允许 30G，硬件照样只放 10G 出去——**售卖原则不依赖软件正确**。

比"压住了"更值得说的是控制面那三列：pace 29.95、R 30.00、tree 29.95，**全程
纹丝不动**。律命令 30G、线上只走 10G，控制面不被告知原因，而它正确地坐着
不动。搜索型的律会把这读成拥塞并退让，跟踪型的不会——目标由接收端给定，
发送端只跟踪它，执行面吃不下不是降低目标的理由。逃逸告警也正确地保持沉默
（r < pace）。解除后线上一拍回到 29.3G，没有需求闩锁。

QP 在 3× 硬件降档与升档下均存活（rc=0）。

## 四、测量口径

perftest 自报的 `BW average` **在 `-D` 模式下不可用**：trial 1 两端都报
7.27 G，同时段主机侧 RoCE 计数器与接收端遥测都是 29.3 G，且它自己的
`BW peak` 是 0.00，报告路径本身是坏的。本轮所有速率取两个互不相干的来源：
发送主机 `ethtool -S dpu1vf0` 的 `tx_vport_rdma_unicast_bytes`（1 Hz）与
接收端遥测 r（1 ms），两者一致。第一次采样用的是 netdev 的
`statistics/tx_bytes`，30G 传输期间读出全零——RoCE 不经过 netdev 软件计数器。

## 五、遗留

- 只有跑 tx agent 的那台 DPU（hpft-dpu / sgpu01）在执行第一层。反向发送
  （sgpu02 侧）没有 agent，也就没有硬上限。对称化是几行事，但当前实验拓扑
  用不到。
- 手工设置的 `tx_max` 会一直存活到下一次政策重载（agent 只在启动和 mtime
  变化时同步），本轮 backstop 实验依赖了这个性质。这也意味着一条手工命令
  能悄悄让两层不一致，直到下次重载。
