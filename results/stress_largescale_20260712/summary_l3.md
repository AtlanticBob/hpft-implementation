# 大规模 L3：QP 规模阶梯（2026-07-12，RDMA-only）

4 直连对,每对 ib_write_bw -q Q,总 QP = 4Q,阶梯 Q=64/256/1024 →
总 256/1024/4096 QP,每对 cap 20G。目的:把数据面/RP 规模轴与控制面
规模轴分开(控制面永远只看 4 个流集合)。

## 控制面开销与 QP 数无关(符合预期,正向)

| 总 QP | tick dt_p95 | 流集合数 |
|---|---|---|
| 256 | 1.000ms | 4 |
| 1024 | 1.000ms | 4 |
| 4096 | 1.000ms | 4 |

tick 周期全程 1.000ms、流集合数恒 4——**控制面调度开销与 QP 数无关**,
验证了"控制面看流集合、不看 QP"的架构判断。QP 规模压的是数据面/RP。

## 重大发现:高 QP 下 RP 预算逃逸(cap 失效)

阶梯里每对聚合 ~49G(总 195.8G≈线速),**远超 20G cap**。单对隔离实验
坐实:

| 二进制 | 1 QP | 1024 QP |
|---|---|---|
| 旧 bud>>7 | 19.1G ✓ | **145G** ✗ |
| 新 bud>>2(现默认) | 18.3G ✓ | **197G** ✗ |

**机制**:RP 的 level 是 **per-QP** 速率,挖掘地板 `floor=bud>>k` 也是
per-QP。QP 数 N 一大,聚合地板 = N × (bud>>k) 就远超预算,level 被地板
钳住无法收敛到 bud/N,流逃逸到线速。1 QP 完美、1024 QP 逃逸。

**两个层面**:
1. **预先存在的限制**:旧二进制 bud>>7 在 1024 QP 也逃逸(145G)——当
   budget≪线速时,per-QP 地板 × N 超预算。P2 曾报"1024 QP +0.3%"很可能
   是在 budget≈线速的场景(逃逸被线速掩盖);budget=20G≪200G 时暴露。
2. **我的 device 改动 bud>>2 让它更糟**(197 vs 145G):地板更高 → 逃逸
   更早、更多。这是"单流稳定性(要高地板防挖零)vs 高 QP 执行(要低地板)"
   的固有张力,是我那个授权改动的一个高 QP 回归。

**修复方向(设计,待用户裁决)**:把地板改成**聚合感知**——
`per_qp_floor = (bud>>2) / N_active_qp`,使聚合地板 = bud>>2 恒定、与
QP 数无关。这同时保住单流稳定(聚合地板 bud/4)和高 QP 执行(per-QP
地板随 N 缩小)。前提是 device 能拿到 per-flowtag 的活跃 QP 数——需查
DPA 是否可得。属 device 码设计改动,需授权。

数据:l3_rx_q*.jsonl、l3_runs.tsv、l3_cpu.txt、隔离实验见本文。
lab 已恢复新二进制(默认)+ 1-QP sanity 18.34G。

## 修复：聚合感知挖掘守卫（device，用户授权，2026-07-12）

把 per-QP 的 level 硬地板 `bud>>2` 换成**聚合速率挖掘守卫**：只在测得的
聚合 `rs > bud>>2` 时才允许下挖 level（`if (adj<0 && rs<=bud>>2) adj=0`）。
level 仍 per-QP，但地板作用在聚合上、与 QP 数无关。旧二进制备份
`~/bzx/doca_pcc.aggfloor`（新默认）+ `.new-bud2`（前一版）+
`.bak-20260711-floorlvl`（最初）。

**验证**：
- 高 QP cap 生效：1 QP 19.4G / 64 QP 18.3G / **1024 QP 19.05G**（修前
  197G）；L3 阶梯 256/1024/4096 QP 全收敛到 ~20G cap。
- 单流发作性崩塌**无回归**：240s repro 0 发作、min 1.69G、min lvl/bud
  1.00（单流 level 稳在 budget，守卫从不触发）。
- 3:1 类公平无回归（实测 ~2.7，近目标 3.0）。
- 控制面开销仍与 QP 无关（tick 1.000ms）。

**遗留（记录，非阻塞）**：256 QP 多对同时在线速下**收敛慢**（~28s 从
50G 降到 20G cap；单对快 ~7s；4 对耦合竞争线速拖慢）。旧二进制是永不
收敛（卡 49G），新的会收敛但慢。若要加速，方向是收敛期增大积分步长
或按聚合过冲比例前馈——属调优，另议。
