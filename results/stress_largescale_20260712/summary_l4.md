# 大规模 L4：控制面规模与多线程（2026-07-12，离线分析）

回答用户"scalability 也许多线程能解决"。L3 已证控制面开销 O(流集合)、
与 QP 数无关。L4 用离线 bench（接收端 Arm、生产同核、打生产调度器代码）
把流集合规模顶到硬件极限（32）之外，定位 1ms 墙、拆解瓶颈、量化多线程
潜力。

## 单线程墙与瓶颈拆解

| 流集合 | 全步 p50 | 调度(waterfill) | 标记 | 1ms |
|---|---|---|---|---|
| 32（硬件极限）| 505µs | 406µs | 37µs | ✓ 2× 余量 |
| 64 | 996µs | 855µs | 75µs | ✓ 临界 |
| 128 | 1883µs | 1598µs | 144µs | ✗ 超 |
| 512 | 7187µs | 6163µs | 583µs | ✗ |
| 4096 | 67535µs | 59662µs | 7804µs | ✗ |

- **单线程 Python 墙 ≈ 64-100 流集合 @1ms**。本 lab 硬件极限 32 流集合
  （4×4 VF×2 类）→ **2× 余量,现规模无压力**。
- **瓶颈 = 三层 water-filling,占 85-88%**；标记只占 ~10%。所以要 scale
  就得攻 water-filling。
- 增长近 O(N)（fastfill 是 O(N log N)）。

## 多线程潜力（回答用户）

**用户直觉对——瓶颈确实可并行**：三层 water-filling 的第 2/3 层（类层、
流集合层）**按目的 VM 独立**,dst VM 之间零依赖,是 embarrassingly
parallel。第 1 层（VM 层）是单次 O(nvm) 填充,小。

**但有个坎:Python GIL**。CPU 密集的 water-filling 在 Python 线程下不
并行（GIL）。接收端 DPU 有 **16 个 Arm 核,rx_agent 只用 1 个**（15 核
闲置）。要吃到这些核,三条路:
1. **C/Rust 重写快环**:去掉解释器开销（~50×）+ 真多核。墙从 ~64 流
   集合推到单核 ~3000-5000、多核再 ×（Amdahl 限,~4-5×）→ **万级流
   集合**。这是把控制面推到大规模部署的正解。
2. **numpy 向量化 fastfill**:数组运算释放 GIL,~2-5×,工程小,是中间
   档。
3. 多进程分片（按 dst VM 分片到多进程）:绕开 GIL 但 IPC/状态同步复杂,
   不如 C/Rust。

**结论**:多线程/多核**是**scale 控制面的正确方向,瓶颈天然可并行、
硬件（16 核）也在;但必须过 GIL 这道坎,实际落地是 C/Rust 重写（顺带
50× 解释器收益）。**当前 32 流集合硬件极限下单线程 2× 余量,不需要做;
它只在流集合上百上千（更多 VF/更大部署）时才必要。** 这也和 L3 呼应:
QP 数（数据面）由 RP 硬件扛,流集合数（控制面）才是这根轴,而它离墙
还有 2×。
