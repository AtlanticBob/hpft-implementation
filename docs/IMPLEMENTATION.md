# 实现位置与实现同设计的差异

设计在 `hpft-design/docs/design_v4.md`，这份文件说设计的每一条落在实现的哪里、实现在哪些地方与设计不一致、有哪些开关。它随实现更新，设计文档不随它变。

## 1 各部分在哪里

| 设计 | 实现 |
|---|---|
| 接收端（4 节）：物理容量、两次逐级填平分配、出借判定的平均、虚拟队列、只发 $q$ 的反馈 | `tools/dpu/rx_agent.py` 的 `law == "conf"` 分支 |
| 发送端（5 节）：相减得 $\Delta q$、三因子律、探涨与它的上限、起步值与起步窗口；只处理最新一条反馈 | `tools/dpu/tx_agent_e.py` |
| 发送端自己的上行链路树（5.5 节） | 同一文件里的 `SenderTree` |
| TCP 执行面（6 节）：限幅、置信度 | `tcp/bpf-opt3/hpft_tcp_edt_kern.c`（主机 fq+EDT），配置经 `tools/host/hpft_pace_shim.py` 写入 BPF 映射表 |
| RDMA 执行面（6 节）：限幅、置信度、四个 CC 项 | `tools/dpu/pcc/rp_rtt_template_dev_main.c`（DPU 上的 PCC），预算经固件邮箱下发 |
| 参数（7 节） | `config/lab-registry.json` 的 `e_params` |

## 2 同一个量在实现里的多处副本

**兑现容差 $\delta$ 有三处**：注册表里的 `delta_demand`（即 $\delta$）与 `tree_backlog_theta`（受压门槛，即 $1-\delta$），以及两个执行面里"额度低于围栏"那道门槛的编译期常量（RDMA `HPFT_TRUST_BELOW_FXP16`、TCP 同名，都是 $1-\delta$ 的 16 位定点数）。设计上它们是同一个量，三处必须保持一致，直到实现把它们合并。

**置信度的两个时间常数**：RDMA 执行面是邮箱旋钮（`0xcce <步长> 7` 上升、`0xcce <步长> 10` 过期，步长是每 1 毫秒的 16 位定点数，默认 66 与 13，即 $\tau_r$ 1 秒、$\tau_d$ 5 秒）；TCP 执行面是编译期常量 `HPFT_TRUST_STEP`、`HPFT_TRUST_DECAY`。改 TCP 的要重编 `.o` 并按 `hpft-design/docs/ops_notes.md` 的"EDT 重装"步骤在四台主机上重装。

## 3 设计里的规则在实现里怎么传递

**起步窗口（5.4 节）**：发送端代理在每条预算里带一位"还在起步窗口"——RDMA 走批量邮箱条目第四个字的第 16 位（低 16 位是队列分数 $q/D$），TCP 走执行面配置 `flags` 的第 30 位（第 31 位是限幅模式开关，低 16 位是队列分数）。执行面据此暂停采集丢包证据。

**第一个预算前的放行额度（5.4 节）**：RDMA 执行面对还不属于任何流集合的 QP 按邮箱 `0xccf` 下发的额度放行，由发送端代理算成 $R_0/$`rdma_qps_per_flowset`。

**丢包证据（6.3 节）**：RDMA 取设备上报的 `ROCE_NACK` 事件；TCP 取协议栈 `total_retrans` 的增量，按连接计，流集合的证据是名下各连接增量之和。TCP 整形器在欠账超过 200 毫秒上限时会丢包（防止一个永不让步的拥塞控制把欠账推到无限），设计里的"静默期"在实现里是 `HPFT_SHOT_QUIET_MS` = 300 毫秒：整形器丢过包之后这段时间里的重传不算证据。

**置信度的定点数（6.4 节）**：两个执行面都是 16 位定点数，乘性的升降在接近 0 和接近 1 时会取整成零步，实现规定每次升降至少走一个最小刻度，置信度才能真正到 0 和到 1。

## 4 实现与设计的已知差异

1. **反馈报文里还保留了一个速率字段。** 装的是接收端测到的该流集合到达速率，调速律不读它，只喂给 RDMA 执行面里一条旧的"是否被整形器限住"判断。要让线上严格只有 $q$，把这个字段置零即可，代价是那条判断退化为设备自己的估计。
2. **RDMA 执行面看不到超时重传。** DPA 的事件表里没有"请求方超时重传"这一类，只有 NACK（接收方发现序号缺口），后者也是拥塞丢包的主要形态。
3. **围栏送到 RDMA 执行面要走固件邮箱**，一次调用占 13 到 22 毫秒，设备拿到的预算总比律算出来的晚一到两个周期；TCP 走主机内核的映射表，没有这一段。这条路上不设迟滞，预算每周期原样下发。
4. **TCP 执行面在第一个预算送到之前不整形**，没有条目的流集合原样放行，与 5.4 节"按 $R_0$ 放行"不符。

## 5 开关

- `e_params.probe_cap_tree`：5.3 节的探涨上限是否含发送端树那一项。
- `HPFT_RDMA_TRUST_STEP=0`（runner 环境变量）：把 RDMA 执行面的置信度上升步长写成零，置信度冻结在零（V8 的对照配置）。
- `HPFT_RDMA_TRUST_DECAY=0`：关掉 RDMA 执行面的过期项，只剩虚拟队列一条下降路（V9 的对照配置）。
- `0xccd <0|1|2|3>`：RDMA 执行面的 CC 项，0 = AIMD、1 = ZTR、2 = 软件 DCQCN（编译期默认）、3 = Swift；设备端没有回读。
- `0xcce <切幅> 8`、`0xcce <微秒> 9`：CNP 驱动的两个 CC 项对丢包的 slow restart，切幅 65536 即关掉。
