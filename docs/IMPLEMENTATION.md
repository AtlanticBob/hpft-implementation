# 实现位置与实现同设计的差异

设计在 `hpft-design/docs/design_v4.md`，这份文件说设计的每一条落在实现的哪里、实现在哪些地方与设计不一致、有哪些开关。它随实现更新，设计文档不随它变。

## 1 各部分在哪里

| 设计 | 实现 |
|---|---|
| 接收端（4 节）：物理容量、两次逐级填平分配、出借判定的平均、虚拟队列、只发 $q$ 的反馈 | `tools/dpu/rx_agent.py` 的 `law == "conf"` 分支 |
| 发送端（5 节）：相减得 $\Delta q$、三因子律、上探与它的上限、起步值；只处理最新一条反馈 | `tools/dpu/tx_agent_e.py` |
| 发送端自己的上行链路树（5.5 节） | 同一文件里的 `SenderTree` |
| RDMA 执行面（6 节）：逐 QP 的租户拥塞控制、每流集合一个令牌桶 $r_i=c_i\min(1,R/\sum c_j)$、逐 QP 限速 | `tools/dpu/pcc/rp_rtt_template_dev_main.c`（DPU 上的 PCC，跑在 DPA 上）；流集合的水位与 QP 归属经固件邮箱下发，`tools/dpu/pcc/pcc_host.c` 是 FIFO 到邮箱的转发 |
| QP 归属（哪个 QP 属于哪个流集合） | 主机侧 `tools/host/qpn_resolver.py` 对每个对端 `rdma res show qp` 做配对，发给本机 DPU 的代理；代理用 `tools/dpu/vhca_of`（DEVX 查固件）把 VF 换算成执行面看到的 vhca_id |
| TCP 执行面（6 节）：同一个桶按连接下发 $r_i=R\,w_i/\sum w_j$、每连接一个发车时钟 | `tcp/bpf-opt3/hpft_tcp_edt_kern.c`（主机 fq+EDT），流集合的水位经 `tools/host/hpft_pace_shim.py` 写入 BPF 映射表 |
| 参数（7 节） | `config/lab-registry.json` 的 `e_params` |

## 2 同一个量在实现里的多处副本

**兑现容差 $\delta$ 有两处**：注册表里的 `delta_demand`（即 $\delta$）与 `tree_backlog_theta`（受压门槛，即 $1-\delta$）。执行面不再用它。

**桶的分母有两个节拍**：RDMA 执行面每 1 毫秒对最近 1 毫秒发过包的 QP 求 $\sum c_j$（`HPFT_EPOCH_US`、`HPFT_ACTIVE_US`），TCP 执行面每 10 毫秒由发过包的连接重建 $\sum w_j$（`HPFT_EPOCH_NS`）。两者都是实现量，不是设计参数。

## 3 设计里的规则在实现里怎么传递

**流集合的水位 $R$（6.2 节）**：发送端代理每 `rdma_push_ms`（5 毫秒）把所有流集合的 $\min(R,U)$ 写成一行 `0xb47f|n {流集合号, 水位}` 进 FIFO；`pcc_host.c` 只把最新的一行送进邮箱（一次邮箱 13 到 22 毫秒，比推送慢，多余的快照丢弃而不排队）。流集合号是注册表里那一对的 flowtag，只当名字用。TCP 的水位走 UDP 到主机的 pace shim，再写 `hpft_pair_cfg`，同一个数每 100 毫秒重发一次。

**QP 归属（6.4 节）**：解析器每 0.2 秒把本机全部已配对的 QP 表发给代理，代理每次按整表重建，键是 `vhca_id << 24 | qpn`，只把新的或变了的绑定以 `0xb48e|n {键, 流集合号}` 下发；执行面在 QP 的第一个发送事件上学到它的 QPN 与 vhca_id，查表绑定。PCC 框架交给算法的 per-flow 上下文不是严格一 QP 一份：实测同一份上下文里会轮流出现两个 QP 的事件（vf1 的 578 与 vf3 的 294；每个 VF 的 QP1 与它的数据 QP），所以执行面自己按 (vhca_id, QPN) 建 QP 记录表，上下文只当缓存提示，事件里的键与提示不符就查表、查不到才分配；沉默超过 2 s 的 QP 视为离开而解绑，代理的映射表里这个 QP 的流集合号变了也解绑（解析器对上一场残留的 QP 可能先给出错配，现在解析器只配对 RTS 态的 QP），下一个发送事件重新查表。执行面重启（每场实验前 `rp_service.sh start`）后设备内存清空，代理靠 FIFO 的 inode 变化察觉并把整表重发。校验绑定是否完整看 `0xded` 回读的在册数是否等于流集合的 QP 数（`validation/data/<tag>_executor.csv`）。

**第一个水位前的放行额度（5.4 节）**：还不属于任何流集合的 QP 按 `0xcce <单位> 21` 的额度放行，代理算成 $R_0/$`rdma_qps_per_flowset`，每 5 秒重申一次。TCP 在第一个水位前不整形（见 4 节第 2 条）。

**在场与消失（4.2 节）**：接收端把"有 OVS 卸载流表项、且最近一个 `mix_window_s`（2 秒）里有字节"当作在场，两者都不成立后再留 `fs_grace_s`（0.5 秒）的宽限才从账本里清掉。RDMA 执行面里 2 秒没有事件的 QP 退出流集合的分母；TCP 执行面里上一个 10 毫秒周期没发过包的连接退出分母。

**容量下限（4.3 节）**：`rx_agent.py` 把根容量卡在链路速率的 5%，写死在代码里。

**最低速率（5.4 节）**：`r_floor_bps` 同时作用在许可速率 $R$ 和交给执行面的 $\min(R,U)$ 上；`control.pace_floor_bps`（50 M）只是反馈中断时对数跟踪的数值下界。

**本机上限的下降限速（5.5 节）**：`tree_step_halving_s` = 13 毫秒，取的是 RDMA 固件邮箱一次下发的时长；限速加在树的输出上而不是预算上，所以它只可能让 $U$ 偏高，不会挡住律通过 $R$ 下达的下降。

**反馈中断（5.6 节）**：`n1_freeze_s`（0.25 秒）是通道存活判定，`n2_failopen_s`（2 秒）是保持期，`n3_evict_s`（30 秒）是清除期；退向 $U$ 用对数一阶跟踪，时间常数 50 毫秒。

**事件分派（框架层）**：DOCA PCC 送来的事件里约 96% 的 `algo_slot` 是 15（固件给内置 DCQCN 留的槽），它们全在流量口、类型是 TX/CNP/NACK，就是我们的数据 QP（PPCC 的算法协商没有把它们放到用户槽 0）。原厂模板把 slot≠0 交给 `doca_pcc_dev_default_internal_algo`，在本 lab 等于把这些流交给固件自己的 CC；执行面因此处理所有槽位的事件，只把槽位计数（`0xdf2` 回读：总数、按口、按类型、槽位值）。`0xccd 4` 是原厂 Swift 核心的参考臂（原厂 `algo/rtt_template.c` 编进本树，同样处理所有槽位），`quick.sh RP_BIN=` 可以换原厂二进制，但原厂二进制的成绩是固件 CC 的成绩。

**桶的模拟（6.2 节）**：RDMA 硬件没有跨 QP 的共享桶，执行面每个事件把 $c_i\min(1,R/\sum c_j)$ 写进这个 QP 的硬件整形器，$c_i$ 是它自己那份拥塞控制状态机此刻的速率（Swift 取窗口除以平滑往返）。TCP 靠每连接的 EDT 时钟，$r_i=R\,w_i/\sum w_j$。

## 4 实现与设计的已知差异

1. **反馈报文里还保留了一个速率字段。** 装的是接收端测到的该流集合到达速率，调速律不读它，执行面也不再读它。要让线上严格只有 $q$，把这个字段置零即可。
2. **TCP 执行面在第一个水位送到之前不整形**，没有条目的流集合原样放行，与 5.4 节"按 $R_0$ 放行"不符。
3. **RDMA 执行面的分母每毫秒重算一次，成员表不压缩**：退出的 QP 就地作废，每个 QP 每毫秒重申一次在册，追加与重算之间的竞争只会让一个 QP 缺席一毫秒，不会永久丢失。最近 1 毫秒没发过包的 QP 不进分母。
4. **账本按内层线上字节计**（VF 的 vport 计数器）。RoCE 在 1024 字节 MTU 下比应用净荷多约 7.3%，VxLAN 封装再多约 5%，所以份额 $X$ 对应约 $X/1.073$ 的 RDMA 净荷，余量 8% 时端口在线上约 97%；受管端口在这个负载下带常驻队列，见设计 6.6 节第一条边界的实测。
5. **接收端的 Python 回退分配忽略打到虚拟机上的不调度流量**（4.3 节第二段）；只在 `libfastfill.so` 缺失时走这条路，本平台不走。
6. **执行面里的 CNP 计数只能当有无看**：接收网卡生成 CNP 有速率上限，每台发送端 12 秒约 200 万就饱和，2000 万和 1.8 亿个标记读出来是同一个数。标记多少以交换机接收端口的 `ecn-marked-frames` 为准（`validation/run/quick_sw.sh`）。

## 5 开关

RDMA 执行面的旋钮都走 FIFO `/tmp/rp_fifo`，`validation/run/quick.sh` 用环境变量设它们：

- `0xccd <0|1|2|3>`：租户拥塞控制，0 = AIMD、1 = ZTR、2 = DCQCN（默认）、3 = Swift（`ALGO`）。
- `0xcce <0|1> 12`：只跑租户拥塞控制，水位忽略；对照臂，也是验证各拥塞控制模型的方式（`CC_ONLY`）。
- `0xcce <0|1|2> 22`：律（`LAW`）。0 = 桶（默认）；1 = 等额封顶 $r_i=\min(c_i, R/N)$，流集合内不共享；2 = 忽略拥塞控制的等分 $R/N$。1 和 2 是对照臂。
- `0xcce <单位> 21`：未知流集合的 QP 放行额度（代理自动下发）。
- `0xcce <值> 0..19`：DCQCN 参数（0 AI、1 HAI、2 速率定时器、3 F、8 丢包切幅、9 丢包间隔、10 丢包时是否连目标速率一起重置（默认 1，对固件 DCQCN 校准过：丢包型 meter 上 46.8 对固件 47.05）、11 CNP 时钳目标速率的语义（默认 0 每次都钳，1 只在上一次是定时器增速时钳）、16 g、17 alpha 定时器、18 字节计数、19 监视周期）；`0xcd1 <值> 0..8`：Swift 参数（0 基准目标时延、1 流缩放范围、2 alpha、3 beta、4 AI、5 乘性切幅系数、6 最大切幅、7 决策是否用平滑往返、8 窗口换算成速率用哪个往返：0 最新采样、1 平滑、2 两者中较大者（默认）、3 较小者）。Swift 默认值是本 fabric 按论文 3.5/5.1 节的做法调出来的：增量 256 B、流缩放范围 40 µs，其余论文值。
- 回读：`0xdef 0`（事件与绑定计数、算法、cc_only）、`0xded <槽>`（流集合：号、水位、逐 QP 限速之和、全部成员拥塞控制速率之和、取令牌 QP 的速率之和、在取的数、在册数）、`0xdee <槽>`（QP：QPN、流集合、拥塞控制速率、所在流集合的分母、限速、往返、CNP 数、vhca_id）。`validation/run/probe.sh` 把这些在一场实验中间读出来。

TCP 执行面没有旋钮：`hpft_pair_cfg` 里速率为零即不整形，`quick.sh` 的 `CC_ONLY=1` 会清空这张表并停掉发送端代理。
