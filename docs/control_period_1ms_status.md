# 控制周期 1ms 化：进展与现状（2026-07-11）

用户目标：控制周期从 50ms 压到 1ms 以下，且性能不劣化。本文记录目前
做到了什么、卡在哪里、下一步怎么走。诚实结论：**1ms 的控制环已经跑
起来（989 tick/s），一个隐藏很深的测量 bug 已根治，但两条执行路径
（RDMA 经 PCC、TCP 经 EDT）在 1ms 下各有一个尚未解决的问题，所以
"性能不劣化"这一条对 RDMA 还没达到。lab 已恢复到经过验证的 50ms
配置，1ms 代码作为可切换选项保留。**

## 已完成

**延迟预算实测（commit 5f620bb）**：整条环路每一段的延迟都测了。最大的
瓶颈是 PCC mailbox 的单次调用要阻塞 13.3ms（固件层，改不动），其次是
接收端每 tick 的 megaflow dump（0.9ms）。vport 计数器约每 0.87ms 才更新
一次，这是物理下限，决定了 1ms 可行、0.1ms 不可行。

**1ms 基础设施改造**：接收端拆成快慢两部分——快环每 1ms 只读 vport
计数器算速率、做水填充、发遥测；慢环每 200ms 才做一次 megaflow dump
更新类构成比（构成比本来就只有 1 秒新鲜度，不需要每 tick 拉）。遥测
从 JSON 改成定长二进制（1ms 下 JSON 编解码是真实开销）。发送端对 RDMA
预算的写入按 mailbox 能吸收的速率（约 75 次/秒）合并，控制律仍每 1ms
跑，两者解耦。所有随周期变化的参数（增量 A、超时 N1/N2、app-limited
窗口）都按周期自动缩放，保持墙钟行为不变。

**一个隐藏很深的测量 bug 根治**：改造初期，接收端测出的速率在稳定
6G 流量下抖动 ±60%。花了很久定位：慢环的 megaflow dump 落在两次 vport
采样之间时，把字节计数和时间戳解耦了——某个 tick 多算了 dump 期间的
流量，下个 tick 又少算。修复是两条：一，速率用固定样本数的窗口（不是
时间窗，时间窗对循环抖动不健壮）；二，把 vport 采样挪到每个循环的最
顶端、在任何慢工作之前，让采样节奏只由 sleep 调度决定。修复后 50ms
下的表现回到与旧系统一致（5.3G，旧 5.65G）。

## 未解决（1ms 下）

**RDMA 路径：约 84% 利用率（5.05G / 6G），50ms 时是 93%。** 根因是
已知的 grant-sag（接收端的应得速率 e_f = 测量速率×1.15，需求封顶在
真实 cap 之下），在 1ms 更快的锯齿下均衡点落得更低。叠加一个 PCC RP
内环的耦合：RP 的设备码只在我们喂的"接收速率"变化时才做一次控制步，
而 1ms 的测量平滑（正是为修 ±60% 噪声加的）恰好去掉了 50ms 时 RP
依赖的抖动。试过喂 0 让 RP 自测、把 R 上界钳在 grant，都没根治。这
需要针对 RP 内环动力学的专门工作（可能要碰设备码）。

**TCP 路径：DPU 重启后 host EDT 程序没重装，当前不限速（实测 24.5G）。**
这是 motivation 实验的两次 DPU 重启的遗留，重新 apply EDT（
tcp-shaper-apply）即可，属工程步骤，未做。

## 下一步建议

1. RDMA 的 grant-sag 在 1ms 下的表现需要专门处理——可能的方向：接收端
   e_f 的需求封顶改用短窗峰值（之前的 F1 思路，但只作用于单流不破坏
   类间公平），或给 RP 内环喂一个带小抖动的目标让它持续收敛。
2. 重装 host EDT，验证 TCP 在 1ms 下能干净限速（TCP 路径无 RP 耦合，
   预期能达标——这会是 1ms 环路本身有效的干净证明）。
3. 参数（A、V、β）在 1ms 下的重新整定 + M1b/M2 式不劣化验收。

## 代码位置

rx_agent.py / tx_agent_e.py 已含全部 1ms 改造，registry 的
period_ms 一键切换（当前 50）。切 1ms 只需改 period_ms=1 并重启两个
agent。

## 追加：TCP 路径验证与 V-scaling 洞察（2026-07-11 续）

按计划重装了 host EDT（DPU 重启后丢失），手工 3G 限速验证通过（TCP
2.76G），执行路径本身没问题。然后跑完整 1ms E 环的 TCP：

**结论一：1ms 的欠利用不是 RDMA/PCC 专有的，TCP 也一样。** TCP 在 1ms
完整环下只有 4.0-4.7G（6G cap 的 66-77%），和 RDMA 的 84% 是同一个病。
这排除了"PCC RP 内环耦合"是主因——两条执行路径（RP 与 EDT，机制完全
不同）都欠利用，说明病根在**接收端标记的动力学在 1ms 下过于敏感**。

**结论二：V 的缩放本来就是错的（已修，代码保留）。** V 是"标记饱和前
容忍的超额积分量"，单位是比特。虚拟队列累积的是 ∫(r−e)dt，这个时间积分
在给定墙钟窗口内与 tick 周期无关，所以 V 必须是**固定比特量**，不能随
周期缩放。原公式 V∝period 让 1ms 的 V 小了 50 倍，虚拟队列对测量尖峰
敏感 50 倍——接收端在 1ms 下测出的 r 有到 7G 的尖峰（TCP/EDT 的突发
结构，6ms 窗平滑不掉），这些尖峰把小 V 的队列打满、触发 6% 的虚假标记，
把流钳在 cap 下方约 20%。改成 V 锚定参考周期（固定 600Mbit）后 TCP
从 3.97G 升到 4.65G。

**结论三：一套参数不能同时适配两条执行路径。** V 改大后 RDMA 反而
脱管到 18G（标记太迟钝、R 跑到 tree）。RP（自带内环、突发平滑）和
EDT（直接债务延迟、突发结构不同）对同一个 V/β 的响应不同。要同时在
1ms 下让两者都达标，需要按执行路径分别整定标记灵敏度，或把测量尖峰
在源头压掉（更长的 r 平滑窗，但要权衡响应延迟）。

**下一步（需要专门的控制整定工作）**：①在源头把 r 的尖峰压掉——rate
窗口从 6ms 加到 ~20-30ms，用 VQ 的积分换取更平滑的 r（VQ 本就该吸收
尖峰，但前提是 V 够大）；②按执行路径分别标定 β/V；③retrans 异常
（TCP 1ms 下 10 万+）要查是不是 EDT 在 1ms 高频改 pace 下丢包。这些
都是 1ms 专门整定的活，量不小，建议作为独立一轮工作。lab 已恢复
50ms 正典（RDMA 18.36G@20G 正常）。

## 追加二：MD 剂量 bug 根治，1ms 反超 50ms（2026-07-11 下午）

这一轮把上面遗留的问题全部收掉了，结论比预期好：**M1b 场景下 1ms 现在
稳定跑 5.66G（稳态均值 5.97G，99.5% cap），反超 50ms 基线（当天新鲜
基线 5.07-5.18G）约 10%，且三轮完全可复现。** 关键是找到了两个此前
被混在一起的病根。

**病根一（主治）：MD 的剂量没按周期缩放。** 交接文档声称"β 按周期机械
缩放"，但代码里 `beta` 根本不在缩放清单里（registry 注释与代码一致，
只缩放了 A/N1/N2/m_al/hai）。MD 是逐遥测记录执行的 `R *= (1-β·s)`，
1ms 下每秒最多挨 1000 刀 β=0.3——剂量是 50ms 设计的 50 倍。一次
s≈0.5、持续 20ms 的标记突发就把 R 从 3G 压穿到 0.05G 的 pace 地板
（11 个 tick）。修复：`R *= (1-β·s)**(period/ref)`，50ms 时指数为 1
逐比特不变（当天回归实测 5.18G，与基线一致），1ms 时 50 个 tick 的
累积衰减恰好等于原来一次 50ms MD。cap 6G→3G 的阶跃在修复后 1.5s 进带
（比未修复慢 0.4s），下冲从压穿到 0 变成只到 1.29G，之后 2.99±0.02G
纹丝不动。

**病根二（混淆因子）：RP 的状态劣化污染了此前所有 1ms 数据。** 修复前
同配置连跑五轮出现三种形态：干净 5.3G、创伤 4.1G（前 12-15s 爬行，
正是 ops_notes 家族三"每周期爬 7%"的症状）、脱管 16.4G（R 被砍到
0.05G 但线上 19G——RP 完全不执行预算；预算写入本身经查是落地的，
RP 日志把批量消息头打印成 ft、把真 flowtag 打成 rate，是日志格式误导）。
每轮之间重启 RP 后，三轮 5.28/5.28/5.26 完全可复现。**"66-84% 欠利用"
的历史数据就是这两个病根叠加的产物，不是标记动力学的本征缺陷。**
机制推测：1ms 下未缩放的 MD 频繁把预算打到地板，地板附近的预算写入
正是触发 RP 家族三状态的诱因——β 修复后 60s 长跑两轮零压穿事件，
旁证了这个链条。

**组件一（rate 窗口）已定：20ms。** 修复 β 后归因对照：rw=6ms 也能到
5.63G（β 修复是主治），但 rw=20ms 把 r 的稳态离散压紧（p5 5.43→5.81，
p95 7.35→6.11），三轮 5.55G 机器般一致；30ms 只再多 0.03G，边际递减，
不值多付 10ms 测量延迟。registry 已定 `rate_window_s=0.020`（50ms 周期
下 nkeep 仍为 2，对旧系统零影响）。

**组件二（per-class V/β）当前证据下不需要。** β 修复后一套参数同时
喂住两条路径：RDMA 5.66G@6G cap，TCP 2.72G@3G cap（91%，cap 恰好
处于阶跃测试遗留的 3G 政策——见下）。"一套参数不能适配两条路径"的
旧结论是在 MD 过量 + RP 污染下得出的，不再成立。方案 E "一条传输
无关的响应律"的主张保住了。

**组件四（TCP 高重传）已定性：虚假重传，与 1ms 无关。** 判别实验：
停掉整条环、手工固定 3G pace，30s 重传 23.5 万次，与全环路（26.8 万）
基本相同——pace 高频改写被排除。nstat 显示 98% 的重传被 DSACK
（TCPDSACKRecvSegs 3959 万 / TcpRetransSegs 4040 万），即被"重传"的包
其实都到了：不是丢包，是**乱序**（TCPSACKReorder 331 万）。host fq
零丢包、接收端 VF 环 rx_out_of_buffer 零增量，与"债务延迟不丢包"自洽。
嫌疑在重装后 EDT/BPF 数据通路的时间戳非单调（per-CPU debt 状态？），
fq 按时间戳发包时打乱包序。这是独立的数据通路 bug，修它是单独一条线，
不阻塞 1ms 化。

**尚未做**：M2（类间 1:1 与借用）在 1ms 下的验收；TCP 在 6G cap 下的
完整环数据（当天误在 3G cap 下测的）；A/β 参数空间的精扫（现在的
机械缩放值已经够好，精扫是锦上添花）；EDT 乱序修复。另外注意 50ms
系统在 20G cap 下本来就在 12-18G 间波动（soak 日志：7-11 凌晨 03:45
未被触碰的稳定系统只跑 12.14G），"18G@20G"的恢复验收本质上是抽样，
不要拿单次结果当回归证据。

**实验协议教训**（已实践、建议固化）：①每轮实验之间重启 RP，不只是
每批——RP 状态劣化以轮为粒度出现；②`hpft-txagent-e`/`hpft-rxagent-e`
是 systemd-run 瞬态 unit，`systemctl stop` 会把 unit 定义一并回收，
重建用 `sudo systemd-run --unit=hpft-txagent-e /usr/bin/python3
/opt/hpft/tx_agent_e.py`；③本轮全部逐轮数据在
`results/rw_sweep_20260711/runs.tsv`，驱动脚本 `tools/run_m1b_once.sh`。

## 追加三：TCP@6G 补测、M2 饥饿死锁与两个修复（2026-07-11 晚）

**TCP@6G 全环补上了，同样反超。** 同日新鲜基线：50ms 下 4.87/4.95G，
1ms 下 5.35/5.32G，1ms 好约 9%。至此 M1（TCP）、M1b（RDMA）两条单类
线在 1ms 下都不劣化且反超，一套参数通吃。

**M2（类间竞争）暴露了一个新的死锁，已修。** TCP+RDMA 同发时，进入
竞争的转换期会让 RDMA 的 VQ 饱和、s=1 持续约 1 秒，墙钟剂量的 MD 也
足以把 R 打到 pace 地板；RP 把 QP 摁在 0.02G 之后，喂给它的实测速率
就恒定不变，而 RP 设备码只在喂入速率变化时才做控制步——于是预算涨到
12.6G 它也永远不迈步（实锤：`0xdeb` 查询 bud=66424、lvl=105）。RDMA
被饿死到 0 直到 TCP 离场。修复两条，都在 tx_agent_e.py：
①MD 下界锚在实测到达率（R ≥ 0.3·r）——预算砍到线上实际流量以下是
纯过冲，而地板附近的预算正是 RP 卡死的诱因；②给 RP 的喂率做交替
抖动（每次推送 ±max(3%, 一个 2^20 单位)），让设备码永远有变化可
步进（交接文档预留的方向，验证有效：修复后 lvl 与 bud 完全同步）。
两个修复对单流均无退化（1ms M1b 5.66G 持平；50ms M1b 5.29G 略升，
下界还顺带防了 50ms 测量尖峰的误砍）。

**M2 的"不劣化"达标，但暴露了一个跨周期的既有问题。** 修复后 1ms 的
M2：借用（TCP 退出后 RDMA 3s 内回 5.98G）和回收（TCP 进入 1s 内拿到
2.7G+）都干净；但竞争期两类互相追逐、秒级振荡，且**客户端真值的比例
不是 1:1**（1ms 约 0.40，rdma 1.4G/tcp 3.5G）。关键对照：50ms 同协议
更差（真实比例 0.25、借用恢复只到 5.42G、振荡幅度相当）——所以这不是
1ms 的退化，1ms 每项持平或更好，"不劣化"门票拿到。真正的问题是：
**rx 的类归因跟不上秒级振荡**（megaflow 类构成比是 2s 滑窗 + 1s 硬件
缓存，滞后的错误归因把 rdma 测成 3.7G 而真值 1.4G，rx 侧比例读数
1.06-1.15 全是假象），历史上 M2 的"通过"很可能就是在这个失真读数上
打的分；滞后归因耦合进公平环也可能正是振荡的助燃剂。这是测量架构层
的问题，任何周期下都存在，修它是下一条独立工作线（思路之一：TCP 的
线速 host EDT 侧自己知道，可从 vport 总量中减去得到 RDMA 真值，绕开
megaflow 滞后）。

**当前状态**：单类场景（M1/M1b）1ms 完整达标可并回；M2 相对 50ms
不劣化、绝对公平性两个周期都欠账（归因问题）。lab 已恢复 50ms 正典
（20G 验证 11.36G，在稳定系统自身 12-18G 波动带内；soak cron 已恢复）。
tx_agent_e.py 含三个新修复（β 指数化、MD 下界、RP 喂率抖动），
registry 的 rate_window_s=0.020，其余与正典一致。

## 追加四：类归因新路线的判别实验（2026-07-11 晚，通过）

归因失真的修复路线已经用实验定死：**接收端 host 的 per-VF netdev RX
计数器是一个新鲜的 TCP-only 字节源。** 判别数据：纯 RDMA 13.13Gbps
跑 10 秒（线上约 16.4GB），sgpu02 上 dpu1vf0 的 netdev rx_bytes 只动
2386 字节（ARP 级噪声）——RoCE 由 HCA 旁路消费、完全不过内核网络栈；
纯 TCP 下 netdev 增量速率与 iperf3 发送速率比值 1.059（帧头+重传开销，
吻合）。内核计数器读取无频率限制、无 1 秒硬件缓存。

由此下一步实现是：接收端 host 跑一个极小的速率导出 shim（模式仿照
发送端的 pace shim），把 per-VF 的 netdev RX 速率按 tick 级新鲜度推给
接收端 DPU 的 rx_agent；rx_agent 用 r_tcp = host 报告值、
r_rdma = vport 总量 − r_tcp 做类级拆分，megaflow mix 只用于同类内部
多发送方的细分（单发送方场景下类率即流集合率）。这把 M2 振荡的
主要助燃剂（类级 50/50 错误切分）从根上去掉。实现与 M2 复验是
下一轮的第一件事。
