# 控制周期 1ms 化：进展与现状（2026-07-11）

用户目标：控制周期从 50ms 压到 1ms 以下，且性能不劣化。本文记录目前
做到了什么、卡在哪里、下一步怎么走。诚实结论：**1ms 的控制环已经跑
起来（989 tick/s），一个隐藏很深的测量 bug 已根治，但两条执行路径
（RDMA 经 PCC、TCP 经 EDT）在 1ms 下各有一个尚未解决的问题，所以
"性能不劣化"这一条对 RDMA 还没达到。lab 已恢复到经过验证的 50ms
配置，1ms 代码作为可切换选项保留。**

## 已完成

**延迟预算实测（commit 5f620bb）**：整条环路每一段的延迟都测了。最大的
瓶颈是 PCC mailbox 的单次调用要阻塞 13.3ms（固件层，改不动），其次是
接收端每 tick 的 megaflow dump（0.9ms）。vport 计数器约每 0.87ms 才更新
一次，这是物理下限，决定了 1ms 可行、0.1ms 不可行。

**1ms 基础设施改造**：接收端拆成快慢两部分——快环每 1ms 只读 vport
计数器算速率、做水填充、发遥测；慢环每 200ms 才做一次 megaflow dump
更新类构成比（构成比本来就只有 1 秒新鲜度，不需要每 tick 拉）。遥测
从 JSON 改成定长二进制（1ms 下 JSON 编解码是真实开销）。发送端对 RDMA
预算的写入按 mailbox 能吸收的速率（约 75 次/秒）合并，控制律仍每 1ms
跑，两者解耦。所有随周期变化的参数（增量 A、超时 N1/N2、app-limited
窗口）都按周期自动缩放，保持墙钟行为不变。

**一个隐藏很深的测量 bug 根治**：改造初期，接收端测出的速率在稳定
6G 流量下抖动 ±60%。花了很久定位：慢环的 megaflow dump 落在两次 vport
采样之间时，把字节计数和时间戳解耦了——某个 tick 多算了 dump 期间的
流量，下个 tick 又少算。修复是两条：一，速率用固定样本数的窗口（不是
时间窗，时间窗对循环抖动不健壮）；二，把 vport 采样挪到每个循环的最
顶端、在任何慢工作之前，让采样节奏只由 sleep 调度决定。修复后 50ms
下的表现回到与旧系统一致（5.3G，旧 5.65G）。

## 未解决（1ms 下）

**RDMA 路径：约 84% 利用率（5.05G / 6G），50ms 时是 93%。** 根因是
已知的 grant-sag（接收端的应得速率 e_f = 测量速率×1.15，需求封顶在
真实 cap 之下），在 1ms 更快的锯齿下均衡点落得更低。叠加一个 PCC RP
内环的耦合：RP 的设备码只在我们喂的"接收速率"变化时才做一次控制步，
而 1ms 的测量平滑（正是为修 ±60% 噪声加的）恰好去掉了 50ms 时 RP
依赖的抖动。试过喂 0 让 RP 自测、把 R 上界钳在 grant，都没根治。这
需要针对 RP 内环动力学的专门工作（可能要碰设备码）。

**TCP 路径：DPU 重启后 host EDT 程序没重装，当前不限速（实测 24.5G）。**
这是 motivation 实验的两次 DPU 重启的遗留，重新 apply EDT（
tcp-shaper-apply）即可，属工程步骤，未做。

## 下一步建议

1. RDMA 的 grant-sag 在 1ms 下的表现需要专门处理——可能的方向：接收端
   e_f 的需求封顶改用短窗峰值（之前的 F1 思路，但只作用于单流不破坏
   类间公平），或给 RP 内环喂一个带小抖动的目标让它持续收敛。
2. 重装 host EDT，验证 TCP 在 1ms 下能干净限速（TCP 路径无 RP 耦合，
   预期能达标——这会是 1ms 环路本身有效的干净证明）。
3. 参数（A、V、β）在 1ms 下的重新整定 + M1b/M2 式不劣化验收。
