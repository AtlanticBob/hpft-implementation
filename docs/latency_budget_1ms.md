# 控制周期 1ms 化：延迟预算与优化计划（2026-07-11 实测）

## 目标

用户设定：控制周期从 50ms 压到 1ms 以下，且公平性/稳态精度等性能不劣化。
本文是第一步——把控制环从测量到执行的每一段延迟实测出来，按大小排序，
确定攻击顺序。所有数字都是本日在 testbed 上实测的。

## 延迟预算表（按瓶颈从大到小）

**① RDMA 执行：PCC mailbox 单次阻塞 13.3ms（最大瓶颈）。**
发送端代理把预算写入 FIFO 后，RP 宿主线程调用 doca_pcc_mailbox_send()
把它送进 DPA，这一次 RPC 实测阻塞 13.3ms（pcc.c 里的 send_ns 直接计的
就是这个调用的墙钟时间，日志里常年 13.3-13.7ms）。此前记忆中"mailbox
sub-ms 不是瓶颈"的结论有误。在 50ms 周期下它躲在暗处；1ms 周期下它是
天花板。修复需要动 pcc 宿主程序（调查为何 13ms：DPA 侧 mailbox handler
的调度延迟？是否有异步接口？能否降频批量？）——按项目规则动 pcc 前
需要你授权。

**② TCP 执行：tmfifo 一跳 1-4ms。**
发送端 DPU 上的响应律要经 tmfifo（慢速管理通道）把 pace 发给 host 上的
shim 写 BPF map。tmfifo 往返 1-4ms，本身就超预算。备选的 in-band 路径
（host 经 VF→eswitch→SF）实测 min 0.63ms 但均值 4.8ms、抖动大（疑似
SF 网卡中断合并）。**更好的解法是取消这一跳**：让接收端把遥测同时直发
host 上的 shim，TCP 类的响应律就在 shim 本地执行，pace 落地只剩一次
本地 BPF 写（实测 0.1-0.6ms）。

**③ 接收端测量：megaflow dump 0.9-1.3ms/tick。**
每 tick 经 unixctl 拉一次全量流表用于类构成比。但构成比的数据源本身
只有 1 秒级新鲜度（mlx5 fc 缓存），根本不需要每 tick 拉。解法是快慢环
分离：快环只读 vport 总量计数器（每次 6.4µs），慢环（~1s）维护构成比。

**④ vport 计数器新鲜度：p50 0.87ms、p99 3.7ms（物理下限，贴线可用）。**
以 15.5 万次/秒连续读实测：计数器值大约每 0.87ms 跳一次（尾部偶发
3-4ms）。这意味着 1ms 周期下单 tick 的速率估计是量化的、带尾部抖动
——但虚拟队列本来就是积分器，设计上就是靠积分吸收单周期测量噪声的，
数毫秒窗口内均值正确即可。这是整条链路上无法用软件优化移除的物理层，
也是"1ms 量级"可行、"0.1ms 量级"不可行的分界。

**⑤ Python 全流程开销：现状 ~2ms/tick，瘦身后实测 131µs/tick。**
现有代理每 tick 约 2ms（含 dump、JSON、旧调度路径）。在 DPU Arm 上用
目标形态做微基准——4 路 vport 读 + 8 流集合的单遍 ceiling 双填充 +
二进制打包 + UDP 发送——实测 131µs/tick（其中 ceiling 仅 30µs）。
结论：1ms 周期不需要 C 重写，Python 瘦身即可，有 8 倍余量。

**⑥ 遥测线路：SF 网往返 0.1ms ✓ 达标，无需处理。**

## 优化计划（按依赖排序）

**Phase A（无需授权）**：接收端快慢环分离（快环 1ms：vport×构成比缓存
→水位填充→VQ→二进制遥测；慢环 1s：megaflow dump 更新构成比+政策热
加载）；遥测双播（发送端 DPU 收 rdma 类、host shim 直收 tcp 类）；
TCP 响应律进 shim 本地执行。完成后 TCP 类端到端 ≈ 0.87(测量) +
0.13(快环) + 0.05(线路) + 0.3(律+BPF 写) ≈ **1.4ms 量级**，逼近
vport 物理下限。

**Phase B（需授权，RDMA 类的门槛）**：调查并修复 mailbox 13.3ms——
先只读 pcc 宿主与 DPA handler 代码定位，再定方案（异步化/轻量 handler/
预算旁路）。不解决它，RDMA 类的执行延迟被钉在 ~14ms。

**Phase C**：参数按时间语义重标定（A、V、N1/N2、m_al 均随 T 缩放），
用 M1b/M2 同款场景做"性能不劣化"验收（时间口径的收敛、稳态均值、
比例、利用率与 50ms 基线对比）。
