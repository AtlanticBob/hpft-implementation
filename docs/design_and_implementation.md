# HPFT：在 DPU 边缘用虚拟队列标记实现 RDMA 与 TCP 的租户间/类间公平

**设计与实现（统一版，2026-07-11）**

本文是 HPFT 系统的完整设计与实现说明。它把这个系统当前的样子从头讲
一遍——包括早期设计定型时定下的机制，也包括后来在实现和调优中改掉、
补上的部分——合成一份连贯的叙述，而不是"先讲最初方案再逐条打补丁"。
读完这一篇，应该能理解系统为什么这样设计、每个部件解决什么问题、以及
一台真实的 BlueField-3 测试床上它是怎么跑到 1ms 控制周期的。

历史演进（方案 A/C/D 的取舍、逐个决定的推导过程）不在本文，需要时查
`rd_fairness_design_c.md` 和决定日志；本文只讲最终成型的系统。

---

## 1. 问题

公有云的虚拟私有网络（VPC）正在从 TCP 转向 RDMA。把传输协议卸载到
网卡硬件能释放出 CPU 卖给租户，也能把 push/pull KVCache 这类关键任务
的带宽顶上去。但云上的 RDMA 不能照搬高性能计算集群那套无损（lossless）
方案：无损依赖 PFC，在多租户、大规模、长距离的环境里会带来 PFC 风暴、
死锁、以及大量 headroom buffer 占用。所以主流做法是有损（lossy）RDMA
——不开 PFC，靠拥塞控制算法（RoCEv2 上通常是 DCQCN）在丢包环境里维持
高带宽。

云厂商希望一套物理网络同时承载 RDMA 和 TCP，于是两类流量会在同一条
链路、同一个交换机队列里相遇。问题就出在这里：它们跑着**完全不同的
拥塞控制律**。RDMA 的 DCQCN 一收到 ECN 标记就毫秒级回退，宁可提前
让路也要避免丢包；TCP 的 Cubic 要等到真丢包了才降速。两者在共享瓶颈
上抢带宽时，"谁拿多少"完全是这两套算法碰撞的副产品，跟任何人的政策
意图无关，还会随交换机 ECN 阈值等配置任意摆动。实测中，不区分队列
直接混跑时，RDMA 每条流拿到 TCP 的三倍（开了 RoCE 式 ECN 时）甚至
两类同归于尽（不开 ECN 时）——无论哪种，租户间隔离这个云网络最基本
的要求都无法满足。

运营商真正想要的是两层公平：

- **租户间硬隔离**：每个租户买了一个带宽额度 $MaxRate$，谁都不能超过
  自己买的；同一瓶颈上多个租户竞争时，按权重分。
- **租户内类间软隔离**：一个租户的 TCP 和 RDMA 按类权重分这个租户的
  份额；其中一类空闲时，另一类可以临时借用它的份额（work-conserving）。

约束有两条，都来自公有云的现实：**租户透明**（不能要求租户改协议栈），
**不依赖交换机改造**（不能假设能在每个交换机上配 per-tenant 的 QoS）。

交换机的 QoS 队列（TC）是个看起来现成的方案，但它救不了这个问题。TC
是静态的、队列数量极其有限（通常 8 个），而云环境需要的是"租户 × 类"
两个维度的隔离——TC 顶多保一个维度。而且这两类流量从服务角度看是同一
个 service class（都是租户业务流量），本不该在物理队列上区分。所以
HPFT 走的是另一条路：不碰交换机，在 DPU 的边缘上做文章。

## 2. 核心思想

先看一个关键观察。假设一个 VM 只被允许发 20G，而物理链路有 100G 且
空闲——这是一个**政策瓶颈**：它物理上不产生任何拥塞信号，没有排队、
没有 ECN、没有丢包。既然物理世界不产生信号，那就**让资源的属主把信号
造出来**。

HPFT 的一句话主张是：

> 每个资源的属主在自己的 DPU 上，为自己的资源维护一个**虚拟队列**，
> 把政策编译成对每个流集合的**差分标记**；所有发送端跑**同一条不带
> 权重的响应律**去响应这些标记。这样一来，物理瓶颈（incast）和政策
> 瓶颈（份额争夺）在标记面前变得不可区分，TCP 和 RDMA 在响应律面前
> 也变得不可区分——两种异构性都在这两个层面被制度性地抹平。

这里有两个词要先解释清楚。**属主**是一个瓶颈资源的所有者：发送端的
上行链路归发送方，接收端的下行链路和 dst VM 的政策份额归接收方；属主
原则是"谁的资源，其内部怎么分由谁的政策说了算"。**虚拟队列**是一个
只存在于内存账本里的队列——没有真实数据包在里面排队，它只是对"到达
速率减去允许速率"这个差做时间积分。真实的物理队列长在交换机的缓冲区
里；虚拟队列长在属主 DPU 的一个变量里。这个想法的先例是 HULL（NSDI'12）
的 phantom queue，区别是 HULL 用它造 headroom、放在交换机上，而 HPFT
用它承载层级化的租户政策、放在边缘。

整个系统建立在两个不变式上：

- **属主不变式**：每个瓶颈上的分配比例，由该瓶颈属主的权重决定。权重
  住在标记点（属主的调度器里），不住在响应律里——这是响应律能够"无
  权重"的原因。
- **min 不变式**：一个流集合的速率不超过它经过的所有瓶颈各自裁定的
  应得份额里的最小值。它的实现方式不是去比较权重（两端的权重各自
  归一化、根本不可比），而是让多个标记源共用同一条响应律——谁的信号
  在响，谁就是当前 binding 的约束。

## 3. 系统模型与保证范围

**部署模型。** 每台主机配一块 DPU（BlueField-3）。租户 VM 通过 SR-IOV
的虚拟功能（VF）收发包，所有流量都过 DPU 的 eSwitch。DPU 属于基础
设施域，租户看不见也改不了。每个 VF 有唯一的 MAC，所以在 DPU 上一对
（源 MAC，目的 MAC）就唯一确定了一对（源 VM，目的 VM）。

系统操作和限速的最小单位叫**流集合**（flow-set），由三元组 $\{$源 VM，
目的 VM，类$\}$ 标识，类取 TCP 或 RDMA。比如 VM1 发往 VM5 的全部 RDMA
流量就是一个流集合，系统不再往下细分到单条流。

**保证范围。** HPFT 只对**边缘瓶颈**给公平性保证——所谓边缘瓶颈是指
有明确属主、且属主能看见其上全部竞争流量的瓶颈。这类瓶颈有三个：发送
端上行链路（所有流量都从本机发出，发送方全可见）、dst VM 的政策份额
（所有流量都落到本机，接收方全可见）、接收端下行链路（incast 就发生
在这里——N 打 1 的速率失配唯一物化的地方，是最后一跳交换机朝本机的
出口，本机 NIC 收到的永远不超过线速，所以接收方全可见）。在这三类
瓶颈上，HPFT 保证稳态分配收敛到政策定义的层级加权 max-min 份额。

明确**不保证**的：核心网瓶颈（spine、朝别的机器的口）的公平——那里
没有属主能看全，租户的 CC 按现状自行应对；丢包的消除；路径负载均衡；
以及亚控制周期（比一个控制周期还短）的突发精度——这种瞬时突发由租户
自己的 CC 兜底（DCQCN 的 CNP 响应是亚毫秒级的，始终跑在 pace 之下）。

## 4. 政策模型

运营商和租户配置的意图，归结为四类参数，每一类都有唯一的属主和唯一的
生效位置：

| 参数 | 含义 | 谁配 | 在哪生效 |
|---|---|---|---|
| $W_i$ | 租户 $i$ 的租户间权重 | 运营商 | 属主调度器的 VM 层 |
| $MaxRate_i$ | 租户 $i$ 买的带宽硬上限 | 运营商 | 发送端树（发出上限）+ 接收端调度器 VM 层（接收上限） |
| $W_{i,TCP}, W_{i,RDMA}$ | 租户 $i$ 的类间权重 | 租户 $i$ | 属主一侧生效：发送端树用源 VM 的，接收端调度器用目的 VM 的 |
| $u_{d,c,s}$ | 目的 VM $d$ 对类 $c$ 中来自源 VM $s$ 的 per-sender 权重 | 租户 $d$ | 接收端调度器的流集合层，默认全 1 |

## 5. 控制环总览

一圈控制环这样跑（周期 $T$）：

```
发送端 host              发送端 DPU                       接收端 DPU                接收端 host
┌────────┐  ┌───────────────────────────┐  wire  ┌───────────────────────┐  ┌────────┐
│租户 VM  │─▶│ pace_f = min(R_f, Tree_f) │──────▶│ ① 测 r_f（vport＋host  │─▶│租户 VM  │
│TCP/RDMA │  │ R_f ← 响应律(s_f, e_f,ê_f)│        │    速率导出器做类拆分）  │  └────────┘
│  自带 CC │  │ Tree_f ← 本地两层树       │        │ ② 层级 water-filling→e_f│
└────────┘  └──────────▲────────────────┘        │ ③ VQ 积分 → 标记 s_f    │
                       │  遥测 {f, s_f, r_f, e_f, ê_f} 每周期 └──────┬────────┘
                       └─────────────────────────────────────────────┘
```

接收端测出每个流集合的到达速率 $r_f$，用层级 water-filling 算出它此刻
的应得速率 $e_f$，更新虚拟队列得到标记 $s_f$，把这些回传给发送端；发送
端跑响应律更新速率上限 $R_f$，pace 生效，下一周期的 $r_f$ 反映出效果。
下面逐段展开接收端和发送端。

## 6. 接收端

接收端做三件事：测量每个流集合的到达速率、算出每个流集合的应得速率、
把超额编译成标记发回去。

### 6.1 测量：两个计数器拼出新鲜的类级速率

测量的难点是又要新鲜、又要能按类拆分，而硬件给的两种计数器各缺一半。

DPU 上的 OVS 打开硬件卸载后，megaflow（合并流表项）默认只按二层
（MAC 对）分流。在下行桥上装三条不改变转发的分类规则（RoCEv2 的
UDP 4791 一条、TCP 一条、其余 IP 一条，动作都是 NORMAL），megaflow
就细化到了（MAC 对，类）的粒度，每项带一个硬件字节计数器。这些计数器
**能按类拆分**，但**不新鲜**：mlx5 驱动对它们是每秒批量查询一次（内核
里硬编码），所以 1ms 周期下读到的是 1 秒前的缓存。

另一个计数器是 representor 的 vport 字节计数器，它**任意频率都新鲜**
（每约 0.87ms 更新一次），但只有每个 VF 的**总量**，不分类。

早期系统只用 megaflow：用一个 2 秒滑窗算类构成比，再乘 vport 总量拆分。
这在单类场景没问题，但在 TCP 和 RDMA 真正竞争时会出大错。竞争期两类
往往在秒级尺度上交替占优——某一刻 TCP 突发到 5G、RDMA 实际只有 1G，
下一刻反过来。2 秒滞后的构成比把每个瞬时总量都按时间平均（约 50/50）
切开，于是那个 TCP 5G / RDMA 1G 的时刻被错报成 3G / 3G。这个错误归因
喂进 water-filling 和标记，本身就是振荡的助燃剂；更隐蔽的是它把接收端
自己读出的比例糊成了漂亮的 1:1，让人误以为系统是公平的。

正确的类拆分来自一个判别实验的发现：**RoCE 完全绕过内核的 netdev
字节计数器**——实测 16.4GB 的纯 RDMA 流量只让 netdev 的 rx_bytes 动了
2386 字节。这意味着内核路径的字节计数器只看得见 TCP。于是测量架构变成：

- 接收端**主机**上跑一个轻量的**速率导出器**（`hpft_rate_exporter.py`），
  每 5ms 把各 VF 的 netdev rx_bytes 快照连同读取时刻的主机单调时间戳
  （两者一起打戳，保证对齐）经 tmfifo 推给同机 DPU 上的接收端 agent。
  这个数就是**纯 TCP 的到达字节**。
- 接收端 agent 每个控制周期读 vport 总量（新鲜），得到每个 VF 的总
  到达速率；再减去主机报来的 TCP 速率，剩下的就是 RDMA 速率。类级
  拆分从此是新鲜的，不再有 2 秒滞后。
- megaflow 的构成比降级为**类内**的多发送方细分（同一类里哪个源 VM
  占多少）和一个断流回退：如果主机的速率报告超过 0.1 秒没到（导出器
  挂了或 host 重启了），agent 自动退回 megaflow 归因，保证不会因为
  辅助通道故障而失去测量（fail-safe）。

vport 的速率是这样算的：保留最近若干个（时间戳，字节值）样本，用固定
**样本数**的窗口而不是固定时间的窗口。这一点很重要——固定时间窗对循环
抖动不健壮：如果某个周期稍微晚了一点，唯一的旧样本会掉出时间窗被丢掉，
留下一个除零、下个周期又是双倍间隔，把稳定的速率算成上下翻倍的噪声。
固定样本数则永远保留 N 个样本，1ms 周期下 N 个样本大约横跨 20ms
（这个窗宽由参数 `rate_window_s` 定，取 20ms），既平滑掉 0.87ms 的
计数器量化噪声、也平滑掉 TCP/EDT 那种几毫秒尺度的突发结构；50ms 周期
下它自然退化成相邻两个周期的差分。

还有一个实现上的坑值得记下来：vport 的采样必须放在每个循环的**最顶端**、
在任何慢工作（比如那个每 200ms 一次的 megaflow dump）之前。否则，如果
dump 恰好落在两次 vport 采样之间，它会把"读到的字节数"和"记下的时间戳"
解耦——某个周期把 dump 期间到达的流量也算进去了、时间却没算，速率虚高，
下个周期又虚低。我们曾因此把稳定的 6G 流量测成上下 ±60% 的抖动，定位
了很久。把采样固定在循环顶端、让采样节奏只由 sleep 调度决定，这个问题
就消失了。

### 6.2 调度器：层级 water-filling 算应得速率

拿到每个流集合的到达速率 $r_f$ 后，先做**需求估计** $D_f = r_f \times
(1+\delta)$。这个 $\delta$（增长余量，取 15%）的作用是：一条被抑制的
流集合当前 $r_f$ 很低，如果直接拿 $r_f$ 当需求，分配会把它锁死在低位；
乘上 $(1+\delta)$ 给它一点"想涨就能涨"的空间——它涨了，下个周期的 $D_f$
随之涨，直到顶到自己的公平份额为止。为什么这个余量必须小（不能靠它
加速恢复），第 9 节会讲。

然后做三层带上限的 water-filling。water-filling（注水）是带上限的加权
max-min 分配：按权重比例往各实体里注水，需求小的先被灌满、它省下的量
继续按权重分给还没满足的，直到容量用尽。三层是：

```
容量 C_root = 下行线速 × (1 − headroom)
第 1 层（VM 层）：把 C_root 在各目的 VM 间按权重 W_d 注水，
   每个 VM 的上限取 min(MaxRate_d, 它下面所有流集合的需求之和)；
   产出每个 VM 的份额 C_d。
第 2 层（类层）：把 C_d 在 {TCP, RDMA} 间按类权重 W_{d,c} 注水，
   某类需求之和小于它的权重份额时，余量归另一类——这就是借用，
   是 work-conserving 的直接产物，不需要任何显式协议；产出 C_{d,c}。
第 3 层（流集合层）：把 C_{d,c} 在各源 VM 间按 per-sender 权重
   u_{d,c,s} 注水；产出每个流集合的应得速率 e_f。
```

headroom（取 3%）是刻意让分配总额低于物理容量的余量，作用是让虚拟
队列在交换机的物理队列之前先报警。

调度器还算一个量，叫**公平上限** $\hat{e}_f$：同一棵树，把这个流集合
的需求设为无穷、其他流集合保持实际需求，water-filling 分给它的量。
恒有 $\hat{e}_f \geq e_f$。直觉上 $\hat{e}_f$ 是"这条流如果胃口无穷大，
它的份额天花板在哪"。它和 $e_f$ 的区别是：$e_f$ 是需求封顶的（受这条
流当前 $r_f$ 影响），$\hat{e}_f$ 与这条流自己的 $r_f$ 无关、只由政策
和别人的需求决定。这个区别在下面两个地方都是关键。为了 O(N log N) 地
一次算出所有流集合的 $\hat{e}_f$（而不是每条流各跑一遍 water-filling），
实现里用了一个单遍级联算法（`fastfill.py`），和逐条重算在数值上严格
等价（用上万个随机用例对拍验证过）。

### 6.3 标记：虚拟队列积分

每个流集合一个积分器。它按"超额"充入、按"未用的公平上限"排空：

$$vq_f \leftarrow \mathrm{clip}\big(vq_f + \Delta_f\cdot T,\ 0,\ V_{max}\big),
\quad
\Delta_f = \begin{cases}
r_f - e_f & r_f > e_f\ \text{（充入：真实超额）}\\
-(\hat{e}_f - r_f) & r_f \leq e_f\ \text{（排空：未用的公平上限）}
\end{cases}$$

标记就是队列长度归一化：$s_f = \min(vq_f / V,\ 1)$。这里 $vq_f$ 是虚拟
队列长度（比特，初值 0），$V$ 是标记满刻度——队列积到 $V$ 时标记饱和
为 1，$V_{max}$ 是防 windup 的积分上限（取 $V_{max}=V$，更深的积分仓
会让超额停止后乘性减多砍几拍、加深下冲）。用积分而不是瞬时比值，是为了
容忍单周期的测量噪声、只对**持续**的超额报警（这是 AVQ 一脉的思路）。

**为什么充入和排空要用不同的参照物，这是一个吃过亏才定下来的设计。**
最初两个方向都用 $e_f$：超过 $e_f$ 就涨、低于就以差值排空。这有一个
死锁。考虑一条被深度压制的流：它的 $r_f$ 已经很低，而 $e_f$ 是需求
封顶的（$e_f \approx r_f \times 1.15$），所以 $e_f$ 跟着 $r_f$ 一起塌，
两者永远只差 15%。于是无论这条流被压得多低，队列的排空速度都只有实际
速率的 15% 左右——一个积满 600Mbit 的队列，在流量只剩 50Mbps 时要
一百多秒才能排空。这段时间里标记一直是满的，发送端每周期都在被乘性减
打压，速率被永久钉死在地板上。我们完整复现过这个死锁：流量一旦被压穿
就再也回不来。修复就是把排空的参照物换成公平上限 $\hat{e}_f$——它与这条
流自己的 $r_f$ 无关、恒 $\geq$ 公平份额，所以被压制的流"没用掉的份额"
$\hat{e}_f - r_f$ 很大，队列很快排空、标记解除、流量恢复；而正好把份额
用满的流（$r_f \approx \hat{e}_f$）排空速度趋于零，不会平白得到解除标记
的机会。

还有一个边界：完全空闲（$r_f = 0$）的流既不充入也无从排空，队列会冻结
在旧值上。处理是让空闲流的队列每周期按 $V$ 快速清零——一条不再发包的
流放弃自己的拥塞主张，这跟 fail-open 的精神一致：陈旧的基础设施状态
不该在应用恢复发包时继续惩罚它。

**为什么这一个机制统一了三个场景。** 政策份额争夺（20G 场景）：物理
零拥塞，但 VM 层的 $MaxRate$ 上限让超额流集合出现 $r_f > e_f$，账本
合成了稀缺性。incast：root 容量被顶穿，短缺按权重摊进每个 $e_f$，
headroom 保证虚拟队列先于交换机物理队列报警。借用：类层 work-conserving
的直接产物。三个场景在标记面前长得一模一样。

### 6.4 遥测

接收端每个周期给每个（有流量或在场的）流集合发一条记录：$\{$流集合
标识，$s_f$，$r_f$，$e_f$，$\hat{e}_f$，序号$\}$。**$s_f = 0$ 也要发**
——它是"新鲜且无拥塞"的显式许可，发送端的加性增以收到它为前提（没有
它就会 fail-open）。带上 $r_f$、$e_f$、$\hat{e}_f$ 是因为发送端的响应律
需要它们（下一节）：$\hat{e}_f$ 用来给探测设上界，$e_f$ 用来给快速恢复
设目标，$r_f$ 用来做发送端树的需求估计。

记录用**定长二进制**（每条 header + 一个定长结构体）而不是 JSON。在
1ms 周期下，对每个流集合的 JSON 编解码是真实开销；定长结构体便宜一个
数量级、也小。遥测走接收端 DPU 到发送端 DPU 的一条带内路径（两块 DPU
的 PF SF 挂在同一个下行桥上，稳态往返 0.1ms），与被控数据路径逻辑上
同源但不额外依赖一张生产环境不存在的专用管理网。

**为什么保持"在场即发"很重要。** 一个只对 $r_f > 0$ 的流集合发遥测的
实现，会在流量瞬时读到 0 的时候把这条流从遥测里漏掉，发送端于是进入
fail-open、把速率冲到 tree 上限，等流量恢复又被打回来——1ms 下这会
形成死亡螺旋。所以只要一个流集合的 megaflow key 还在（说明它还在场），
就持续给它发 $s_f = 0$ 的许可，哪怕这一刻测到的速率是 0。

## 7. 发送端

发送端为每个流集合维护一个速率上限 $R_f$，每收到一条遥测就跑一次响应
律更新它，最后把 $pace_f = \min(R_f, Tree_f)$ 下发到执行器。

### 7.1 响应律

律的骨架是加性增、乘性减（AIMD），但**不带权重**——分配比例由接收端的
标记点（$e_f$）决定，律只负责收敛。$R_f$ 的初值取发送端树份额 $Tree_f$
（乐观起步：新流集合一上来就拿到发送端政策允许的全部额度，不做慢启动；
如果它落在拥塞资源上，一两个周期内标记就到、乘性减把它压下来，期间的
瞬态超额由租户 CC 兜底）。

基本律是：收到 $s_f = 0$ 就加性增，收到 $s_f > 0$ 就乘性减。但直接用
这个骨架在 1ms 下会出两个乱子，所以实际的律在两个方向上都做了加固。

**向上（探测）：加性增和 Hyper Increase 的上界锚在公平上限。** 连续
收到无标记遥测说明这条流长期低于可用份额，应该加快向上探测：加性增的
步长在连续无标记若干周期（取 10 个周期）后开始逐级放大，封顶 8 倍
（这是借来的 DCQCN Hyper Increase 结构）。但探测必须有上界，否则会
冲穿。早期版本让 $R_f$ 一路涨到 tree 上限（约 20G），一次瞬时下探就够
触发 HAI 把它以每秒 16G 的斜率直冲上去——冲穿 cap → 虚拟队列饱和 →
标记风暴 → 乘性减深砍 → 再来一轮，形成 15-25 秒周期的弛豫振荡。修复
是把加性增和 HAI 的探测上界锚在**公平上限** $\hat{e}_f \times 1.05$。
这里两个细节都有教训：一，锚必须是 $\hat{e}_f$ 而不是需求封顶的 $e_f$
——$e_f = \min(\text{fair}, r \times 1.15)$ 通过发送端自己的 $r$ 自指，
执行面一点松弛就把不动点拖向 0（和 6.3 的 VQ 排空死锁同构，实测流被
困在 0.27G 零标记），而 $\hat{e}_f$ 与自身 $r$ 无关、恒 $\geq$ 公平
份额，永不困人；二，那个 1.05 的余量必须小——试过 1.3，单流期 $R_f$
冲到 1.3 倍上限、超额 1.7G 把队列 350ms 打满触发深砍，借用期变成
7.56↔2.28 的新振荡；1.05 的超额（$\leq 0.29$G）队列只会温和滴几点标记。
一句话：**探测只能温和地贴着公平上限往上试，不能无上界地冲。**

这个固定的 $\hat{e}_f \times 1.05$ 上界后来被改成**兑现率感知的衰减
余量**（§12 修订一）。固定 5% 余量有个隐患：任何把 pace 兑现到 95.2%
以上的执行器（$1/1.05$）会稳态地坐在 grant 之上——虚拟队列持续对这
5% 超额充电、几秒内饱和、发一轮周期性标记风暴。余量存在的唯一理由是
补偿执行器的欠兑现，所以让它随 $r$ 逼近 $\hat{e}_f$ 而衰减到零：探测
上界改为 $\hat{e}_f + \min\big((\text{probe\_over}-1)\hat{e}_f,\
\text{probe\_gain}\cdot\max(0,\hat{e}_f-r)\big)$（probe\_over=1.05、
probe\_gain=2）。$r$ 远低于 $\hat{e}_f$ 时余量全额（保恢复速度），$r$
贴上 $\hat{e}_f$ 时余量趋零（兑现率 100% 的流稳态收敛到恰好 $\hat{e}_f$，
不再制造持续超额）。

**向下（乘性减）：单周期剂量按周期缩放，且设下界。** 乘性减是按比例、
一步到位的。如果标记持续（比如超额持续了十几毫秒），发送端在这十几毫秒
里会每个周期都乘性减一次。50ms 周期下这是几次，1ms 周期下就是几十次
复利——$R_f$ 被砍成微不足道的值。所以乘性减的单周期剂量必须按周期
缩放：让一段固定墙钟时间内的总削减量与参考周期（50ms）下一致，等价于
把每周期的削减指数乘以 $(\text{周期}/\text{参考周期})$。此外乘性减设两个
下界 $R_f \geq \max(0.3\,r_f,\ 0.3\,\hat{e}_f)$：类进入/退出的转换期会
有标记风暴，无下界会把 $R_f$ 打到 pace 地板，执行器（尤其 RDMA 的 RP）
被地板预算 wedge 后很难恢复。$0.3\,r_f$ 那个界会随着塌陷的线速一起下坠
（$r$ 跌、界跟着跌），把预算停在 0.9-0.95G——恰好是深 pace 的 QP 撞进
RC 停摆的 $\lesssim 1$G 区间。所以再加一个**政策锚的下界** $0.3\,\hat{e}_f$：
公平上限是政策量、不随线速塌陷，无论标记持续多久都把 pace 挡在停摆区
之外（§12 修订三）。

**快速恢复。** 一次深度乘性减之后，光靠加性增爬回来很慢。所以发送端为
每个流集合记一个"最近的正常速率" $R_{good}$：每次乘性减把砍之前的 $R_f$
存进去。此后只要收到无标记遥测，就执行快速恢复——每周期令 $R_f \leftarrow
(R_f + R_{good})/2$，二分逼近，约 5 个周期回到砍前水平。如果标记是转瞬
即逝的（测量噪声），流量很快弹回；如果标记是持续的（真实约束），下一次
乘性减会把 $R_{good}$ 更新为更低的砍前值，恢复目标自然逐步下移，不会
跟约束对抗。快速恢复的目标同样封顶在份额之内（用和探测**同一个**兑现率感知上界
$\min(R_{good}, \text{probe\_cap}(\hat{e}_f, r))$，§12 修订一/二）：接收端
给的 $e_f$ 有一两个周期的滞后，如果快速恢复把 $R_f$ 一步弹到远高于当前
份额，流量会立即超额、立即被标记、再次被砍，锁死在低位（实测两类比例曾
达 11.8:1）。早期这里用的是 $\hat{e}_f \times 1.15$——但当 $\hat{e}_f$
恰好落在公平份额上时，那 15% 就是被批准的超额，塌陷后的"反弹→过标→
再砍"循环正是骑在它上面；换成 probe\_cap 后反弹只送回份额之内。原则和探测一样：
**快恢复只把流量送回它的份额之内，份额之外交给慢速的加性增。** 还有
一个坑：快速恢复的跳变本身让实际速率 $r_f$ 滞后 $R_f$ 一两个周期，这个
落差会被下面的 app-limited 检测误判，所以快速恢复跳变时要清零它的
计数器。

**app-limited 冻结。** 如果一条流连续若干周期（取 10 个周期，即 500ms）
实际速率低于 $R_f$ 的 85%，说明应用自己没用满额度，就把 $R_f$ 冻结在
$r_f \times 1.1$、停止加性增；等 $r_f$ 回升贴近再解冻。作用是防止 $R_f$
虚高——虚高的 $R_f$ 在拥塞来临时要多砍几拍才生效。判别是否 app-limited
时，参照的是这条流填没填满自己的**份额** $\min(R_f, e_f)$，而不是虚高
的 $R_f$：一条已经用满份额、只是被 cap 限住的流不是 app-limited，不该
被钳。

**fail-open。** 连续 $N_1$ 个周期没收到某流集合的遥测就冻结 $R_f$（停止
加性增）；连续 $N_2 > N_1$ 个周期就把 $R_f$ 斜坡回升到 $Tree_f$。语义是：
接收端 DPU 故障时，流量退化成只受发送端本地政策约束——租户不被卡死，
也不失控（租户 CC 还在）。

**执行。** $pace_f = \min(R_f, Tree_f)$，落到两个执行器。RDMA 落到 PCC
的 per-pair 预算（DPA 硬件 pacing，租户透明）；TCP 落到 host fq+edt 的
pacing rate。租户自己的 CC 在 pace 之下照常跑，实际发送速率 = min(租户
CC 想发的，$pace_f$)。RDMA 侧就是已经长期验证的 min(DCQCN, budget) 组合。
RP 内部把预算按 per-QP 的 level 施加到每条 QP（聚合 = level × QP 数），
其防塌陷的挖掘地板必须作用在**聚合**上而不是 per-QP 上，否则高 QP 数
下 per-QP 地板 × QP 数会超过预算、把流放跑到线速——这个高 QP 预算逃逸
在压测里被发现并修复（§12 修订五）。

### 7.2 发送端的两层模型

发送端上行是发送方自己的资源，属主看得见全部竞争者，所以直接本地调度、
不走标记环。这里遵循一条**云售卖原则**：$MaxRate_i$ 是卖给租户的额度，
任何时刻任何 VM 都不能超过自己买的；某 VM 只用 5G 时，省下的量可以让
其他 VM 在各自 $MaxRate$ 之内多拿（超售场景），但不能让任何 VM 突破
自己的购买额度。例：线速 100G 超售 8 个 20G 的 VM，全打满时各 12.5G；
一个只用 5G 时其余各拿 95/7≈13.6G（仍 <20G）。

这条原则用两层实现：

- **第一层（硬上限，执行兜底）**：per-VM 的 $MaxRate_i$ 由硬件限速器
  执行（生产上用 devlink port function rate 之类；类盲、静态、与第二层
  解耦——在 VF 的视角里 $MaxRate_i$ 就是"线速"）。它的作用是防第二层
  软件失效时的失控。
- **第二层（分配语义，本方案）**：一棵软件树，跑和接收端调度器同一套
  water-filling，容量是上行线速×(1−headroom)，第 1 层每个 VM 的上限取
  $\min(MaxRate_i, \text{需求和})$（这个上限保证了售卖原则），VM 内类间
  按类权重软隔离。每个流集合的 $Tree_f$ 取它的公平上限 $\hat{e}_f$
  （和接收端同一个定义，作用在发送端树上）。取公平上限而不是需求封顶
  份额，是因为 $R_f$ 以 $Tree_f$ 起步、fail-open 又斜坡回升到 $Tree_f$，
  两处都要求 $Tree_f$ 是"政策允许的额度"；需求封顶下新流 $r=0$ 会得到
  $Tree \approx 0$，自相矛盾。$Tree_f \leq MaxRate_{src}$ 恒成立，所以
  乐观起步的突发和 fail-open 的上限都有界于售出额度。

原来设想的独立"预算仲裁器"不再需要：两个执行面（fq+edt 和 PCC）挂在
同一个发送端 agent 下，类间借用就是这棵树 work-conserving 填充本身。

## 8. 把控制周期做到 1ms

前面的机制在 50ms 周期下就能工作。把周期压到 1ms（快 50 倍）对政策变化
和拥塞的反应更及时，但需要在几个地方专门下功夫。这一节讲清楚为什么
1ms 可行、以及为了 1ms 做了哪些设计。

**延迟预算里哪些是硬地板。** 先实测了整条环路每一段的延迟。有两个硬
地板改不动：PCC mailbox 的单次调用要阻塞约 13ms（固件层的往返），
vport 计数器约每 0.87ms 才更新一次（物理下限）。第一个决定了 RDMA
预算不能每 1ms 都推一次 mailbox，第二个决定了 1ms 是可行的合理终点、
再往下（0.1ms）不可行——除非把测量搬进 DPA，那是另一个数量级的工程。

**接收端拆成快慢两环。** 每个周期都要做的是快环：读 vport 计数器算速率、
做 water-filling、更新虚拟队列、发遥测。megaflow 的 dump（约 1ms，用于
类内细分和断流回退）不需要每周期做——它的数据源本来就只有 1 秒新鲜度
——所以放进每 200ms 一次的慢环。慢环必须**内联**在主循环里按固定周期数
触发，不能放后台线程：Python 的 GIL 让 CPU 密集的 megaflow 解析仍然
占着 GIL，"后台线程"不但没隔离开、反而会抖动快环的采样节奏。

**参数按周期的时间语义缩放。** 所有随周期变化的参数都以 50ms 为参考
周期，按时间语义自动缩放，保持墙钟行为不变。加性增量 $A$（每周期一个
增量）和乘性减的指数按 $(\text{周期}/\text{参考})$ 缩小（保持每秒的
增速和一段墙钟内的总削减不变）；fail-open 的 $N_1$、$N_2$、app-limited
的窗口、HAI 的触发周期数（这些都是"多少个周期"的超时）按 $(\text{参考}/
\text{周期})$ 放大（保持墙钟超时不变）。这里有个曾经漏掉的教训：乘性减
的剂量一开始没进缩放清单，1ms 下每次砍的比例和 50ms 一样、但一段拥塞
里砍的**次数**多了 50 倍，复利砍成地板——这是 1ms 下欠利用的一个主因，
补进缩放清单后消失。

**标记满刻度 $V$ 是固定比特量，不随周期缩放。** 这一条容易搞错。虚拟
队列累积的是 $\int (r-e)\,dt$，这个时间积分在给定的墙钟窗口里和 tick
周期无关。所以 $V$（触发满标记之前容忍的超额积分量，单位比特）必须是
一个固定的比特数，锚在参考周期上（$V = v\_periods \times 50\text{ms}
\times \text{线速} \times \text{headroom}$，默认 $v\_periods=4$ 即
$1.2$Gbit；早期取 2 即 600Mbit，见 §12 修订六），**不能**正比于周期。
早期错误地让 $V$ 正比于周期，1ms 的 $V$ 就比 50ms 小了 50 倍，虚拟队列
对测量尖峰敏感了 50 倍——偶尔一个测量尖峰就把小队列打满、触发虚假标记、
把流钳在 cap 下方。$V$ 是固定比特量之后，队列在 1ms 下对尖峰的容忍度
和 50ms 一致，标记只对持续超额响应。

**RDMA 预算的合并写。** mailbox 每次阻塞 13ms（约每秒 75 次上限），
所以发送端不能每 1ms 都往 mailbox 写预算，否则积压、预算变陈旧。做法是
把控制律（每 1ms 跑）和 mailbox 写（按 13ms 合并）解耦：律每周期更新
每个流集合的最新预算，一个合并写把最新的一份快照按 mailbox 能吸收的
速率推下去。这样控制周期是 1ms，而 RDMA 政策目标的传播延迟被限在
约 14ms——但这只影响政策目标的传播，不影响拥塞响应本身：RDMA 的拥塞
响应在 DPA 的 per-QP 内环上，按事件速率（亚微秒）跑，从来不受 mailbox
限制。喂给 RP 的接收速率要带一点交替抖动，因为 RP 的内环只在喂率变化
时才迈一步；1ms 的测量平滑去掉了 50ms 时 RP 无意中依赖的抖动，需要
显式补回来。合并写还对**预算**本身做两件事（§12 修订四）：一是 3% 的
**滞回**——预算漂移小于 3% 就重发上一次的值，因为 RP 把任何预算变化都
当作 cap 阶跃、会重臂 settle-hold 冻结积分，滞回让预算准静态、积分得以
收敛；二是**下降斜率限制**（默认每秒最多降到 35%）——律的锯齿会让预算
以 ~1s 周期上下摆，RP 的积分带着约 100ms 回路延迟去追、每个波谷都过冲
到近零（VQ/律/RP 三环耦合的极限环），限制预算下降速率把 RP 要追的目标
放慢到慢于它的回路延迟，上升不限（恢复越快越好）。

这些做完之后，接收端实测跑到约 1000 周期每秒。M1b（单类 RDMA 6G cap）
在 1ms 下稳态 5.66G，反超 50ms 基线约 10%，三轮可复现。M2（类间竞争）
的数据见第 10 节。

## 9. 三条关于利用率的实测权衡

有一组关于"能不能把双类并发的合计利用率再往上顶"的实验，结论是**账本
本身不是利用率的瓶颈**，值得单独记下来，因为它划定了分配语义的改进边界。

**第一条：加性增量在"比例保真"和"利用率"之间没有全局甜点。** 把全局
$A$ 从 0.05G 提到 0.2G，双类比例始终精确（1.00 上下），但合计利用率
钉在 85% 附近；再提到 0.25G，利用率跳到 96%，比例却崩坏到 21:1——大
步长和恢复行为叠加会复利放大先领先一方的优势，需求封顶的账本又让它
守住地盘，系统进入赢家通吃的双稳态。按类分别标定能拿到 88-92% 利用率，
代价是比例漂到 0.81-0.92。最终选全局 $A$：它是唯一比例可靠的档位，
公平是本系统的第一承诺。

**第二条：给恢复中的流发放需求侧的增长余量是零和的。** 试过在流量低于
近期峰值时把 $\delta$ 临时放大到 50%，指望它复利收复失地。利用率不升反
降（81% < 85%）。原因是 water-filling 的账本是零和的：分给恢复流、但它
一时用不掉的那部分份额，恰好是从兄弟流本可以实际使用的份额里扣出来的，
兄弟流被标记压到可达速率之下。所以需求侧的余量只能小（就是那个 15%），
恢复加速必须在发送端做（就是第 7 节的快速恢复）。

**第三条：把份额"保底"给掉坑的流，会杀死掉坑期间的临时借用。** 试过
一个"份额保底"的需求估计（$D_f = \max(r_f(1+\delta), \text{纯权重份额})$）：
一条流掉坑时它的份额分毫不减，账面缺口消失（分配总量的 5 分位从 2.84G
提到满额 6.00G）。但合计利用率从 87% 降到 80%。这暴露出基线里一个此前
没识别的增益来源：TCP 每次丢包恢复的短暂掉坑期间，RDMA 会临时借走它
让出的容量、坑结束再还——份额保底恰好禁止了这种借用（掉坑的流速率不为
零，保底就一直生效，容量借不出去）。两者结构性互斥。

三条合起来指向一个结论：双类并发下 87% 左右的合计利用率不是账本的失误，
而是租户 TCP 自身丢包恢复期间发不出流量所致——把分配总量钉死在满额也
买不回来。按类标定 $A$ 和份额保底都保留为具名的配置模式（分别面向
"利用率优先"和"严格份额 SLA"两种场景），默认关闭。

## 10. 实现与验收

逐里程碑的实测数据在 `results/` 各目录的 summary.md，总索引见

**类间公平的验收（1ms、1:1 权重、三轮）。** 竞争段的 wire 口径比例
1.03-1.05（±10% 内），合计利用率约 100%，秒级振荡标准差 0.01-0.15

## 11. 性质、新颖性与边界

**为什么收敛到政策份额。** 在单个受控资源上，这是"AQM 按超额差分标记
+ 各源 AIMD"的经典设定：超出 $e_f$ 的流集合被持续标记、乘性减；低于
$e_f$ 的不被标记、加性增；均衡点即 $r_f \approx e_f$，而 water-filling
保证 $e_f$ 等于政策份额。借用是同一机制的自然产物：空闲类的需求小，
份额被 work-conserving 回灌给另一类，借用类不被标记地涨上去，需求回归
时份额重划、标记把借用者压回。锯齿幅度由 $A \cdot T$ 和 $V$ 决定，是
精度与响应速度的权衡旋钮。双环嵌套（HPFT 的律叠在租户自己的 CC 之上）
不互相激振的论据是 pace 只延迟不丢包，对租户 TCP 表现为平滑管道
（OnRamp 同型），RDMA 侧 min(DCQCN, budget) 已长期验证。

**一句话新颖性主张：把层级化的租户政策（含借用）编译进边缘虚拟队列的
差分标记，用一条传输无关的响应律同时驯服 TCP 与 lossy RDMA，租户透明、
零数据面改动。** 逐个先例的增量：HULL 用 phantom queue 造信号，但为
headroom 不为政策、且在交换机——HPFT 搬到边缘、承载层级政策；AFD 按
超额差分标记，但在交换机、平权、无层级——HPFT 层级化、政策化、作用于
虚拟资源；EyeQ 在边缘做 per-VM，但用显式速率反馈、类盲——HPFT 用标记
而非速率，无租约状态机、无需求协议；VCC/AC-DC 在 vSwitch 垫统一 CC 但
只管 TCP——HPFT 扩到 lossy RDMA + 政策层级 + DPU 硬件执行；EQDS 用
credit 准入并替换数据面——HPFT 是它的 rate-based 对偶，零数据面改动、
类粒度政策（EQDS 的隧道是 per 主机对、类盲）。不宜声称"首个 TCP/RDMA
共存"（EQDS 已占）。

**已知边界与开放项。** 环路总延迟约 1-2 个周期，这个窗口内的突发靠租户
CC 兜底。竞争期 RDMA 的 RC 重传和 TCP 的 EDT 乱序税是数据通路层的独立
工作线（app/wire 比值 0.946/0.962 是它的量化基线），与公平性和控制周期
无关。核心网瓶颈的公平不在保证范围，作为 discussion 用加权律扩展回应。
在线改权重、VM 迁移适配尚未系统验证。

## 12. 压测战役的设计修订（2026-07-11/12）

一轮系统性压力测试（规模、极端比例/权重、churn、incast、参数边界、
对抗时序、4×4 加权矩阵 + QP 规模）改动了六处**机制/算法本身**（区别于
纯配置与工程 bug）。前面各节已就地反映这些改动，本节集中列出，供追溯。

1. **兑现率感知的探测余量（probe\_cap，§7.1 探测）。** 探测/HAI 的上界
   从固定的 $\hat{e}_f\times1.05$ 改为随 $r\to\hat{e}_f$ 衰减到零的余量。
   动因：固定 5% 余量下，任何把 pace 兑现到 >95.2% 的执行器会稳态坐在
   grant 之上，VQ 持续充电、几秒饱和、发周期性标记风暴（D2 30 轮发作
   3 次、D3c 每个保持窗被穿）。

2. **快速恢复的反弹上界用同一个 probe\_cap（§7.1 快恢复）。** 原为
   $\hat{e}_f\times1.15$，那 15% 在 $\hat{e}_f$ 落于公平份额时是被批准
   的超额，塌陷后的"反弹→过标→再砍"循环骑在它上面；改用 probe\_cap
   后反弹只送回份额之内。

3. **乘性减增加政策锚的下界 $0.3\,\hat{e}_f$（§7.1 乘性减）。** 原下界
   $0.3\,r_f$ 随线速塌陷一起下坠，把预算停在 0.9-0.95G 的 RC 停摆区；
   $\hat{e}_f$ 是政策量不随线速塌，把 pace 挡在停摆区外。

4. **RDMA 预算合并写增加滞回 + 下降斜率限制（§8）。** 3% 滞回让预算
   准静态（否则 RP 把每次预算变化当 cap 阶跃、冻结积分）；下降斜率
   0.35/s 阻尼 VQ/律/RP 三环耦合的极限环（RP 积分追律的锯齿、每个波谷
   过冲到近零）。

5. **RP 执行器的挖掘地板改为聚合感知（§7.1 执行）。** level 是 per-QP，
   原挖掘地板 $bud\gg2$ 也是 per-QP，高 QP 数下聚合地板 = QP 数 × 地板
   超过预算、流逃逸到线速（1024 QP 在 20G cap 下实测 197G）。改为守卫
   **聚合速率**：只在测得的聚合 $rs>bud\gg2$ 时才下挖 level，地板作用
   在聚合上、与 QP 数无关（修后 1024 QP 收到 19G，单流稳定无回归）。
   这是唯一一处 PCC device 码改动。

6. **标记满刻度默认 $v\_periods$ 由 2 改为 4（§6.3/§8）。** 即 $V$ 从
   600Mbit 增到 1.2Gbit。动因：incast 的 root 短缺区出现四流同相的同步
   弛豫振荡（聚合掉到 ~48%），$V$ 加倍让虚拟队列更晚饱和、把同步硬砍
   软化成温和涟漪（root 区回到 ~98% 且四流 spread≈0）；参数扫描证明这
   不是机制矛盾而是参数问题，且 $V=4$ 在单对/借用/发作三个回归上都不
   劣化。

**未改设计、记录为边界或待议的：** 物理 incast 瓶颈下加权类公平是
work-conserving 软保证（被偏袒的类因自身 CC 顶不满其加权份额时，差额
被借走——share\_floor 张力）；高速率下 churn 重收敛比低速率慢（加性增
$A$ 锚线速、绝对步长恒定，容量摆动越大越慢）；混合流量下某类流集合从
非零突然归零宜回退 megaflow 归因而非直接 fail-open（观测脆弱性加固，
待议）。这些不改机制，作为已知边界。
