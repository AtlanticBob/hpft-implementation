## 0. 术语表（本文用到的词汇，先定义再使用）

| 术语 | 含义 |
|---|---|
| 流集合 $f$ | 一组流量的集合，键为 $\{src\ VM, dst\ VM, class\}$，$class \in \{TCP, RDMA\}$。是本设计限速和观测的最小单位（与现有 shaper 的 {src_vnic, dst_vnic} 粒度一致，多一个类维度） |
| pace / 整形 | 通过控制包的发出间隔来限制一个流集合的速率。只延迟、不丢包 |
| 控制律 | 一条根据反馈信号周期性调整速率的固定规则（一个公式），区别于"人为判断后下发命令" |
| AIMD | 加性增、乘性减：没有拥塞就每周期加一个固定量，出现拥塞就按当前速率的一个比例往下砍。TCP 的经典行为模式 |
| CE 标记 | 交换机队列长度超过阈值时，在支持 ECN 的包头上打的拥塞标记。RoCEv2 的包默认支持，租户 TCP 不一定支持 |
| RTT 探测 | 发送端 DPU 周期性地发一个小探测包给接收端 DPU（走和租户流量相同的交换机队列），接收端立即弹回，发送端测得往返时间。往返时间相对空载基线的增量 ≈ 路径上的排队延迟 |
| water-filling / 注水 | 一种分份额的算法：先让需求小的实体全额满足，省下的量在未满足者之间继续平分，重复直到分完 |
| 租约 | 带有效期 $\tau$ 的临时限速规则，需要持续续期才存续，不续期自动过期（过期后速率斜坡恢复） |
| min 合成 | 一个流集合同时受多个规则约束时，实际速率取所有约束中的最小值 |
| 均衡 | 控制律反复运行后速率稳定下来（或围绕一个中心小幅锯齿波动）的状态 |

## 1. 出发点：方案 A 的交换机部分为什么需要替换

方案 A 在交换机瓶颈上的做法是一套"侦探流程"：观测各类流量的比例是否偏离预期
→ 计数器累计嫌疑 → 主动把偏高的一类降速一小段时间（Probe），看偏低的一类是否
回升 → 回升则确认竞争、正式限速。这套流程有三个固有代价：

1. **Probe 本身伤害吞吐**：为了获取信息，必须周期性地人为压低某个租户的速率，
   即使最后判定无竞争。
2. **归因可能出错**：Probe 让出的带宽可能被第三方抢走而不是被受抑制类拿到，
   造成"看起来无竞争"的误判；TCP 回升慢，短观察窗口也会漏判。
3. **无收敛保证**：确认竞争后的限速是"每次砍一点、看看效果"的试探，最终停在
   哪里没有数学性质可言。

这三个代价的共同根源：**接收端看不见交换机瓶颈上的竞争者全集，所以只能靠"先
归因（是谁压了谁）、再动手（限谁、限多少）"的两步走，而归因这一步既昂贵又不可靠。**

方案 C 的问题意识是：能不能设计一个**根本不需要归因**的机制？

---

## 2. 核心思想

先问一个问题：在没有任何限速系统的今天（baseline），共享交换机队列上"每个流
拿多少带宽"是谁决定的？

答案是：**没有任何人决定，它是各条流自带的拥塞控制算法互相碰撞的副产品。**
RDMA 跑 DCQCN（对 CE 标记敏感，毫秒级反应），TCP 跑 Cubic（对丢包敏感，以
RTT 为周期反应）。两套不同的算法挤在同一个队列里，谁多谁少取决于 ECN 阈值
怎么配、RTT 多长这类偶然因素——**分配结果和任何公平政策无关**。这就是跨类
不公平的根因。

方案 C 的核心思想一句话：

> **在 DPU 上给所有流集合垫同一条"带权重的控制律"。因为大家跑的是同一条规则、
> 听同一种信号，在任何一个共享瓶颈上，速率会自动收敛到与权重成正比的份额——
> 不需要知道瓶颈在哪里，不需要看见竞争者是谁，也不需要归因。**

配合方案 A 中已经定案、继续保留的端侧机制，总原则是：

- **看得见全集的瓶颈（接收端下行）→ 直接计算**：接收端能看到该瓶颈上的所有
  流量，直接算出精确份额下发租约（方案 A 的端侧臂，原样保留）。
- **看不见全集的瓶颈（任意交换机口）→ 用控制律收敛**：谁也看不全，那就不看，
  让统一的控制律自动收敛出正确比例。

## 3. 组成部分

### 3.1 发送端 DPU：每流集合一个速率控制器

为每个活跃的流集合 $f$ 维护一个速率值 $R_f$（由第 4 节的控制律更新），并给它
一个权重 $w_f$：

$$w_f = W_i \times \frac{W_{i,class}}{W_{i,TCP} + W_{i,RDMA}}$$

其中 $W_i$ 是发送方租户（src VM）的租户权重，$W_{i,class}$ 是该租户为这个类
配的类权重。含义：**在基础设施拥有的网络内部（交换机），一个流集合的"话语权"
= 它的租户权重按类权重切分后的那一份**。（注意：这是一个新的明确定义——方案 A
的 Q4 只定义了发送端上行用 src 权重、接收端下行用 dst 权重，交换机瓶颈无属主，
此处明确定为用 src 侧权重，代表运营商政策。）

流集合的实际发送速率由三个约束取最小值（min 合成）：

$$pace_f = \min(\ R_f,\ \ Tree_f,\ \ Lease_f\ )$$

- $R_f$：控制律的输出（本方案新增的部分）；
- $Tree_f$：稳定规则树给它的本地份额（租户 $MaxRate$、类间借用，由本地预算
  仲裁器维护——方案 A 的 Q15，原样保留）；
- $Lease_f$：接收端下发的端侧租约（方案 A 的端侧臂，原样保留；无租约时视为 ∞）。

**与租户自己的拥塞控制的关系**：租户 VM 里的 DCQCN/Cubic 照常运行，DPU 不碰
它们，只是在其下方 pace。租户实际发出的速率 = min(租户 CC 自己想发的速率,
$pace_f$)。也就是说：租户 CC 保留"发多快才可靠"的职能，但"拥挤时谁让多少"这个
**分配职能被 $R_f$ 接管了**——这正是消除异构性的方式：分配由同一条律决定，
与租户跑什么 CC 无关。RDMA 侧的 min(DCQCN, cap) 组合在现有 shaper 中已实现并
验证；TCP 侧就是把 fq+edt 的 pacing rate 设为 $pace_f$。

### 3.2 接收端 DPU：遥测反射器 + 端侧仲裁器

**遥测反射器（新职能，替代方案 A 的判别表交换机分支）**：接收端不再做任何
判断，只按控制周期把每个流集合的拥塞信号原样回传给对应的发送端 DPU：

- $ce_f$：该周期内，流集合 $f$ 的包中带 CE 标记的字节比例（0~1）。只有
  RoCEv2 流量可测（租户 TCP 不一定支持 ECN）；
- $rtt_{path}$：DPU 对之间的 RTT 探测值相对空载基线的超出量（反映这条路径上
  的排队）。这是路径级信号，对该路径上的所有流集合（含 TCP）都适用——它补上
  了"租户只发 TCP 时看不到 CE"的盲区。

流集合 $f$ 的综合拥塞信号定义为：

$$s_f = \max\left(\ ce_f,\ \ \min\!\left(\frac{rtt_{path} - target}{target},\ 1\right)\ \right) \in [0, 1]$$

$target$ 是允许的排队延迟目标（参数）。$s_f = 0$ 表示这条路上没有拥塞。

**信号归因（2026-07-09 定案，Q18）**：接收端回传遥测时标注信号来源——本机
下行饱和期间观测到的 CE/RTT 标为**下行信号**，未饱和时的标为 **fabric 信号**。
发送端的控制律**只消费 fabric 信号**；下行拥塞完全由端侧租约（dst 权重）处理。
理由：最后一跳朝本机的 egress 口是**有属主的瓶颈**（就是接收方购买的下行），
按属主原则应由接收端决定的权重分配，src 权重的律用在这里是错误政策；归因让
两套权重在机制上不相遇，也避免双重压制。这是 Swift 的 fabric/endpoint 分解
思想在遥测通道上的应用。

**端侧仲裁器（2026-07-09 升级，Q18）**：接收端下行（= 最后一跳朝本机的 egress
口，**incast 的队列物理上就长在这里**——N 打 1 的速率失配唯一的物化点）的
所有分配由端侧仲裁器负责。**双触发**：
- **物理饱和触发**（incast）：$R_{total} \geq \beta \cdot LineRate$，去抖放宽到
  1-2 个周期；严重 incast（饱和且 CE 陡增）立即触发不等去抖；
- **政策超额触发**：某 dst VM 入流量超过其份额（如 $MaxRate_d$）——不需要
  物理饱和，纯政策事件，只有接收端账本可见。

分配算法：L1 各 dst VM 按 **dst 权重** 分下行 → L2 dst 的类权重 → L3 类份额内
按**接收端配置的 per-sender 权重**做加权 water-filling（默认等权，权重来源为
dst VM 政策配置；此为 Q17 的推广）。**incast 下需求估计只用 cap-hit 反馈，
不用观测速率**——交换机队列已把到达速率扭曲成"谁激进谁多"。分配总额留 2-5%
headroom（EyeQ 式，让稳态 incast 下交换机队列保持浅，参数进 eval）。

**突发 incast 最初几个 RTT 的兜底**：租约到位前（1-2 个控制周期内），即时背压
由底层租户 CC 提供（DCQCN CNP 亚毫秒级，min 合成里始终在场）。本系统提供的是
政策，不与 DCQCN 比反射弧；与 EQDS 对比时如实陈述：EQDS 用 credit 准入赢下
第一个 RTT，我们用"租户 CC 反射 + 快触发租约"把差距压到一两个控制周期。

## 4. 控制律

每个控制周期（几十毫秒量级），发送端 DPU 对每个流集合 $f$ 执行：

$$
R_f \leftarrow
\begin{cases}
R_f + w_f \cdot A & \text{若 } s_f = 0 \quad \text{（加性增，速度正比于权重）}\\[4pt]
R_f \cdot (1 - \beta \cdot s_f) & \text{若 } s_f > 0 \quad \text{（乘性减，比例与权重无关）}
\end{cases}
$$

- $A$：单位权重每周期的增量（参数，如 0.5 Gbps）；
- $\beta$：最大减速比例（参数，如 0.3）；$s_f$ 越强砍得越狠（和 DCTCP 按标记
  比例砍的思路相同）。

**为什么均衡份额正比于权重**（三行推导）：在一个稳定的锯齿周期里，涨的总量必须
等于跌的总量。设两次拥塞事件间隔 $n$ 个周期、平均信号强度 $\bar{s}$，则对每个
流集合：涨 $= w_f \cdot A \cdot n$，跌 $= R_f \cdot \beta \cdot \bar{s}$。同一
瓶颈上的流集合听到的是同一个信号（同一个队列产生的 CE / 同一段排队），所以
$n$、$\bar{s}$ 对大家相同。令涨 = 跌：

$$R_f = \frac{A \cdot n}{\beta \cdot \bar{s}} \cdot w_f \ \ \propto\ w_f$$

即：**不管瓶颈在哪一跳、有多少参与者、各自是什么协议，均衡速率之比 = 权重之比。**
这是有几十年理论与实践背书的经典性质（带权 AIMD / "权重为 w 的流等价于 w 条
单位流"）。

**数值例子**：流集合 $f_1$（租户 A 的 RDMA，$w=3$）与 $f_2$（租户 B 的 TCP，
$w=1$）在某个 100G 交换机口相遇，两者的接收端不同、互相看不见对方。$f_1$ 每
周期涨 1.5G、$f_2$ 涨 0.5G；口子一满，两者按同比例砍。跌与自身大小成正比、
涨与权重成正比，最终锯齿中心稳定在约 75G : 25G。全程没有任何组件知道"这两个
流集合在同一个口子上竞争"。

**需求受限（app-limited）的处理**：若流集合实际发送速率低于 $R_f$（比如租户
TCP 本来就只想发 2G），则 $R_f$ 冻结在实测速率 × (1+ε)，不再跟涨——否则
$R_f$ 会虚高，拥塞来临时砍好几拍才生效。

**为什么 Probe 不再需要**：方案 A 用 Probe 回答"偏低的类是被压制还是没需求"。
控制律根本不问这个问题：如果 $f_2$ 只想要 10G（低于它 25G 的应得份额），它的
$R_f$ 冻结在 10G 附近、不再参与涨，拥塞信号随之减弱，$f_1$ 的加性增会自动吃掉
剩余的 90G——**"借用"是均衡的自然结果**；哪天 $f_2$ 需求上来了，它恢复跟涨，
均衡自动回到 75:25。归因问题（谁压了谁、有没有需求）在均衡动力学里自动消解，
不需要任何实验去回答。

## 5. 三个竞争场景走查

| 场景 | 瓶颈属主 | 生效机制 | 过程 |
|---|---|---|---|
| 发送端上行竞争 | 发送方 | 稳定树 + 本地预算仲裁器（不变） | 本地全可见，直接调度 |
| 接收端下行竞争（**含 incast**：N 打 1 的队列物理上就在最后一跳朝本机的 egress 口） | 接收方 | 端侧仲裁器（Q18 升级：双触发+快触发+dst 权重） | 饱和或政策超额 → 加权 water-filling → per-sender 租约，1-2 个周期到位；首 RTT 由租户 CC 兜底 |
| 无主瓶颈竞争（核心网/uplink/朝别机的口） | 运营商 | **加权控制律（本方案）** | 各流集合独立响应 fabric 信号，均衡份额 ∝ 权重 |

方案 A 的三个老大难在这里的结局：

- **第三方压制**（A 中的 Q8"永不限速受害者"）：消解。受害流集合也会对信号做
  乘性减，但它基数小、减得少，而加性增按权重进行——均衡点保证它拿到应得份额。
  注意这是一个**语义变化**：保障从"对受害者不动作"变为"均衡份额 ∝ 权重"，
  后者其实是更强的承诺（前者只是不伤害，后者保证拿回来）。
- **Probe 的吞吐凹陷与误判**（A 中的 Q11）：消解，没有探测这回事。
- **多接收端同步振荡**（A 中的 Q13 jitter）：消解，连续、异步、各自为政的
  控制律取代了"集体离散动作"，不存在需要打散的同步时刻。

## 6. C 与 C-lite 的精确区别

两者用**同一条控制律、同一套信号、同一个端侧臂**，区别只在控制律"什么时候在场"：

| | **方案 C（常开律）** | **方案 C-lite（信号触发律）** |
|---|---|---|
| 控制器何时存在 | 每个活跃流集合**始终**有 $R_f$ 在跑（无信号时一路涨到被 $Tree_f$ 封顶） | 平时**没有** $R_f$，流量只受稳定树+租约约束；接收端信号越过阈值才回传，发送端此时才为该流集合创建控制器，$R_f$ 初始化为当前实测速率 |
| 控制器何时消失 | 不消失 | 信号静默 N 个周期后解散，速率斜坡回到树份额（复用租约到期的斜坡机制） |
| 遥测开销 | 常开，每周期回传所有活跃流集合的信号 | 稀疏，只在有拥塞时回传 |
| 无拥塞时的行为 | 与 C-lite 完全相同（$R_f$ 被树份额 min 掉，等效于只受树约束） | 只受树约束 |
| 论文叙事级别 | "**分配权收归基础设施**"：稳态下所有份额由基础设施的律立法，租户 CC 只管可靠性 | "**检测-响应系统**，但响应动作是一条有均衡性质的控制律，而不是侦探流程" |
| 相对方案 A 的 17 项决定 | Q7/Q8/Q11/Q13 作废，全文叙事重写 | 仅 Q7/Q8/Q11 作废（Q13 的 jitter 顺带不需要），其余全部存活 |
| 工程量 | 较大：全路径常开 pace + 完整的稳定性评估 | 中等：相当于把现有 shaper 的静态 cap 改成"信号驱动的动态值" |

一句话区分：**C 说"份额从此由我定"，C-lite 说"我还是出了事才管，但管的方式是
一条能证明收敛到哪的公式，而不是一套要归因的流程"。** C-lite 是 C 的工程保守版，
也是从方案 A 出发改动最小的强化路径：删掉判别表的交换机分支、$cnt_{sw}$、
Probe 协议、防同步 jitter，换进第 4 节那一个公式。

## 7. 风险与开放问题（两个方案共有）

1. **双环嵌套**：租户 TCP 跑在被 pace 的路径上，会把 pace 造成的短排队当作
   网络状况来反应。需要论证/实测两个环不互相激振（我们的有利条件：底层环更快
   且只延迟不丢包；RDMA 侧 min(DCQCN, cap) 已在现网验证；EDT 缓冲深度需设上限）。
   相关先例：OnRamp (NSDI'21) 在"边缘透明地对租户流量做拥塞控制"上有同型讨论。
2. **信号的队列一致性**：RTT 探测包必须与租户流量走相同的交换机队列（相同
   DSCP/TC 映射），否则测到的是别的队列的排队。部署时需验证（lab 待查证事实）。
3. **参数面**：$A$、$\beta$、$target$、控制周期、app-limited 的 ε、C-lite 的
   触发阈值与静默期 N。比方案 A 的参数面（8 个）小，但同样需要敏感性分析。
4. **评估负担**：这条路把论文带进"新拥塞控制律"的地界，评审会要求收敛性/稳定性
   证据，以及与 DCQCN/Cubic 原生行为的对比。这是相对方案 A 最大的额外成本。
5. **公平语义的覆盖范围**：控制律给出的是"经过同一瓶颈的流集合之间按 $w_f$
   分"。若运营商希望交换机瓶颈上先做租户间聚合公平、租户内再分类（严格两层），
   $w_f = W_i \times$ 类占比这个乘积形式是它的近似（当租户的两类都活跃时精确
   等价；一类空闲时另一类自动继承全租户权重——恰好就是"借用"语义）。这一点
   写论文时要说清楚。

## 10. 新颖性评估与相关工作定位（2026-07-09，EQDS 原文已核实）

**结论**：不能声称"首个解决 TCP/RDMA 共存"——EQDS (NSDI'22) 摘要原话即
"safely run TCP alongside RDMA on the same network"。C 的新颖性是**综合与实现**
级，不是原语级。可守阵地按强弱排序：

1. **核心网瓶颈上的政策级加权分配——恰好是 EQDS 自己声明的 future work**。
   EQDS 原文（§5 Oversubscribed networks）：核心网超额订阅时需要引入 ECN/延迟/
   INT 信号增强，"Developing such mechanisms is future work"；其评估在 400% 超订
   下"EQDS ends up behaving similarly to the native baseline"。C 的加权律恰好
   就是这个缺口的机制，且给的是政策加权份额而非仅"降 pull 率"。
2. **层级 tenant×class 政策的编译**：把两层公平政策（含借用语义）编译成逐流集合
   权重 + 端侧精确仲裁的组合；EQDS 的 credit 调度器只在端侧表达政策。
3. **零数据面改动的实现路线**：不换封装/无隧道协议/不需要 trimming 或包喷洒/
   不占 CPU 核，复用 NIC 硬件限速（PCC，µs 级延迟中性）。对照 EQDS：DPDK 版
   常驻 2 核、BlueField-2 版受 SmartNIC interconnect 瓶颈且增加延迟、需两端部署
   隧道端点。
4. Motivation 测量（租户级 DCQCN×Cubic 失衡的配置敏感性）+ T3.2 负结论。

**原语考古表**（誰先做过什么，related work 必须引）：

| C 的构件 | 先例 | C 的增量 |
|---|---|---|
| 租户透明的统一律垫在租户 CC 之下 | VCC、AC/DC TCP (均 SIGCOMM'16，vSwitch 下对租户 TCP 换 DCTCP 行为)；OnRamp (NSDI'21，边缘延迟门控) | 扩到 TCP+RDMA 双类、带权重、DPU 硬件执行 |
| 加权 AIMD → 份额 ∝ 权重 | MulTCP (1998)；Seawall (NSDI'11，per-source 加权隧道) | 权重编译自两层租户政策；流集合粒度 |
| 接收端算份额反馈发送端 | Gatekeeper；EyeQ (NSDI'13)；EQDS pull 调度器（可配 fair/比例/优先） | 表达力持平，优势仅在零数据面改动 |
| 多传输类共存 | **EQDS (NSDI'22)**：edge-queued + 接收端 credit，TCP/RDMA 安全共存 | 共存"安全"→ 政策级加权 SLO；核心网瓶颈政策分配（其 future work） |
| RDMA 公平 | Justitia (NSDI'22，intra-host 应用级) | 租户级、跨类、跨机 |

**诚实的反向短板**（论文须承认）：EQDS 的 credit 是**主动准入**——incast 第一个
RTT 就被控住、接收端零超载；C 是**反应式**——先拥塞、后收敛，有锯齿，极端突发
下依赖底层 DCQCN 兜底。EQDS 顺带给 lossy RoCE 提供近无损服务与包级负载均衡；
C 不做负载均衡、不消除丢包。写作对策：正面引 EQDS，定位为"同目标下的 rate-based
低侵入替代：牺牲主动准入的瞬态精度，换取零数据面改动 + 核心网政策分配"。
