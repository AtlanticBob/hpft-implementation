## 0. 术语表

读本文档前先过一遍。正文中这些词首次出现时也会就地解释，但所有定义以本表为准。

| 术语 | 定义 |
|---|---|
| 租户 / VM | 本项目语境中租户 = 实例 = 虚拟机，粒度相同 |
| 流集合（flow-set）$f$ | 三元组 $\{src\ VM,\ dst\ VM,\ class\}$ 标识的一组流量，$class \in \{TCP, RDMA\}$。是本系统**限速、测量、标记的最小单位**。例：VM1→VM5 的全部 RDMA 流量是一个流集合，不再细分到单条流 |
| 政策（policy） | 运营商/租户配置的分配意图的总称，具体为四类参数：租户权重、租户带宽上限、类权重、per-sender 权重（§3.1） |
| 属主（owner） | 一个瓶颈资源的所有者。发送端上行链路归发送方，接收端下行链路与 dst VM 的政策份额归接收方。属主原则：**谁的资源，其内部怎么分由谁的政策决定** |
| 边缘瓶颈 | 有属主且属主能看见其上全部竞争流量的瓶颈：发送端上行、dst VM 政策份额、接收端下行（含 incast，见 §2.2）。本文的公平性保证只针对边缘瓶颈 |
| pace / 整形 | 通过控制数据包的发出间隔来限制一个流集合的速率。只延迟发包、不丢包 |
| 虚拟队列（VQ） | 只存在于内存账本里的队列：没有真实数据包在此排队，只是对"到达速率 − 允许速率"的差做时间积分。物理队列长在交换机的缓冲区里；虚拟队列长在属主 DPU 的一个变量里。先例：HULL (NSDI'12) 的 phantom queue |
| 应得速率 $e_f$ | 属主政策对流集合 $f$ 此刻应得带宽的裁定值，由层级 water-filling（§3.3）算出。单位 bps |
| 公平上限 $\hat{e}_f$ | 流集合 $f$ 的份额天花板：同一棵树、把 $f$ 的需求设为无穷、兄弟流保持实际需求时 water-filling 分给 $f$ 的量。恒有 $\hat{e}_f \geq e_f$。用于 VQ 排空（§3.3）与发送端 $Tree_f$（§3.6） |
| 标记 / 信号 $s_f$ | 属主发给 $f$ 的发送端的拥塞信号，取值 $[0,1]$，语义为"$f$ 正在超出应得速率的程度"。$s_f=0$ 表示无超额 |
| 遥测（telemetry） | 接收端 DPU 每控制周期向各发送端 DPU 回传 $s_f$ 的消息通道（§3.4） |
| 响应律（response law） | 发送端根据 $s_f$ 周期性调整流集合速率上限的固定规则（一个公式，§3.5），区别于"人为判断后下发命令" |
| AIMD | Additive Increase / Multiplicative Decrease，加性增、乘性减：无拥塞时每周期加固定量，有拥塞时按当前值的比例削减。TCP 拥塞控制的经典结构 |
| water-filling / 注水 | 带上限的加权 max-min 分配算法：按权重比例注水，需求小的实体先被灌满，其省下的量继续按权重分给未满足者，直到容量用尽（§3.3 给出精确算法） |
| work-conserving / 借用 | 分配算法的性质：只要还有未满足的需求，容量就不会闲置。租户内"TCP 空闲时 RDMA 可用其份额"（借用）即类层的 work-conserving |
| headroom | 分配总额刻意低于物理容量的余量（本设计取 2-5%），作用是让虚拟队列先于交换机物理队列报警 |
| app-limited | 一个流集合的实际发送需求低于系统允许值的状态（应用自己不想发那么多） |
| 控制周期 $T$ | 测量→计算→标记→响应这个环路的节拍，本设计目标 20-50ms（具体值实现时定） |
| fail-open | 控制通道故障时系统退化为"不限速"而非"卡死在限速状态"，保证基础设施故障不长期伤害租户吞吐 |
| 树份额 $Tree_f$ | 发送端本地稳定规则树分给 $f$ 的份额（§3.6），即发送端上行政策的产物 |
| 收敛 / 均衡 | 响应律反复运行后速率稳定（或围绕中心小幅锯齿波动）的状态 |

## 1. 问题与核心思想

### 1.1 问题

公有云中，租户 VM 同时产生 TCP 与 RDMA（RoCEv2，lossy，无 PFC）流量。两类流量
都是租户流量，共享网络且不用交换机 TC 队列隔离。运营商需要两层公平：

- **租户间硬隔离**：每租户有带宽上限 $MaxRate$；同一瓶颈上竞争时按权重分。
- **租户内类间软隔离**：TCP/RDMA 按类权重分租户份额；一类空闲时另一类可借用。

难点：两类流量跑着**异构的拥塞控制律**（DCQCN 毫秒级响应 ECN；Cubic 以 RTT 为
周期响应丢包）。共享瓶颈上"谁拿多少"是这两套算法碰撞的副产品，与任何政策无关，
且随 ECN 阈值等配置任意摆动。约束：租户透明（不能改租户协议栈）、不依赖交换机
改造（公有云现实）。

### 1.2 核心思想

政策瓶颈（例：VM 只被允许 20G，物理链路 100G 且空闲）物理上不产生任何拥塞
信号——没有队列、没有 ECN、没有丢包。**那就让属主把信号制造出来**：

> 每个资源属主在自己的 DPU 上为自己的资源维护**虚拟队列**，把政策编译成逐流
> 集合的**标记**；所有发送端跑**同一条无权重的响应律**。物理瓶颈（incast）与
> 政策瓶颈（份额争夺）在标记面前不可区分，TCP 与 RDMA 在响应律面前不可区分——
> 异构性在这两个层面被制度性抹平。

两个不变式：

- **属主不变式**：每个瓶颈上的分配比例由该瓶颈属主的权重决定（权重住在标记点，
  不住在响应律里）。
- **min 不变式**：流集合的速率不超过它经过的所有瓶颈各自裁定的应得份额的最小
  值。实现方式不是比较权重（两端权重各自归一化、不可比），而是多个标记源共用
  一条响应律——谁的信号在响，谁就是 binding 约束。

## 2. 系统模型与目标

### 2.1 部署模型

每台主机一块 DPU（BlueField-3）。租户 VM 通过 VF（SR-IOV 虚拟功能）收发包，
全部流量经过 DPU 的 eSwitch。DPU 是基础设施域：租户不可见、不可改。每个 VF
有唯一 MAC，因此 DPU 上 (src MAC, dst MAC) 即 (src VM, dst VM)。

### 2.2 瓶颈分类与保证范围

| 瓶颈 | 物理/政策 | 属主 | 全部竞争流量属主可见？ | 本设计的机制 |
|---|---|---|---|---|
| 发送端上行 | 物理 | 发送方 | 是（都从本机发出） | 本地稳定树（§3.6） |
| dst VM 政策份额 | 政策 | 接收方 | 是（都落到本机） | 虚拟调度器标记（§3.3） |
| 接收端下行（**incast 即此**：N 打 1 的速率失配唯一物化点是最后一跳交换机朝本机的 egress 口，本机 NIC 收到的永远不超过线速） | 物理 | 接收方 | 是（都落到本机） | 虚拟调度器 root 层标记（§3.3） |
| 核心网（spine/uplink/朝别机的口） | 物理 | 运营商 | **否** | **不保证**；扩展见 §4.6 |
| host 内部（PCIe/内存） | 物理 | 接收方 | — | 不保证（PicNIC 范畴） |

**保证**：在三类边缘瓶颈上，稳态分配收敛到 §3.1 政策定义的层级加权 max-min
份额。**非目标**：核心网瓶颈上的公平（租户 CC 按现状自行应对）；丢包消除；
路径负载均衡；亚控制周期（< $T$）的突发精度——突发的即时背压由租户自己的
CC 提供（DCQCN 的 CNP 响应是亚毫秒级的，始终在 pace 之下运行，见 §3.5）。

## 3. 设计

### 3.1 政策模型

四类参数，各有唯一的属主与生效位置：

| 参数 | 含义 | 谁配置 | 在哪生效 |
|---|---|---|---|
| $W_i$ | 租户 $i$ 的租户间权重 | 运营商 | 属主调度器的 VM 层 |
| $MaxRate_i$ | 租户 $i$ 的带宽硬上限（购买量） | 运营商 | 发送端树（作为发出上限）与接收端调度器 VM 层（作为接收上限）各自生效 |
| $W_{i,TCP}, W_{i,RDMA}$ | 租户 $i$ 的类间权重 | 租户 $i$ | 属主一侧生效：发送端树用 src VM 的，接收端调度器用 dst VM 的。两端配置不同不冲突——binding 瓶颈的属主说了算 |
| $u_{d,c,s}$ | dst VM $d$ 对类 $c$ 中来自 src VM $s$ 的流量的 per-sender 权重 | 租户 $d$ | 接收端调度器流集合层。默认全 1（退化为等权分配） |

### 3.2 架构与控制环总览

```
发送端 host                发送端 DPU                      接收端 DPU               接收端 host
┌─────────┐   ┌──────────────────────────┐   wire   ┌──────────────────────┐   ┌─────────┐
│ 租户 VM  │──▶│ pace_f = min(R_f, Tree_f) │─────────▶│ ①逐流集合计数 r_f      │──▶│ 租户 VM  │
│ (TCP/    │   │  R_f ← 响应律(s_f)  §3.5  │          │ ②层级虚拟调度器 → e_f  │   └─────────┘
│  RDMA CC)│   │  Tree_f ← 本地树    §3.6  │          │ ③VQ 积分 → 标记 s_f    │
└─────────┘   └────────────▲─────────────┘          └──────────┬───────────┘
                           │        遥测：{flow_set, s_f} 每周期 │
                           └────────────────────────────────────┘
```

控制环一圈（周期 $T$）：接收端测 $r_f$ → 算 $e_f$ → 更新 $vq_f$ 得 $s_f$ →
回传 → 发送端更新 $R_f$ → pace 生效 → 下一周期 $r_f$ 反映效果。

### 3.3 接收端：层级虚拟调度器

**输入**：本周期每个流集合的到达速率 $r_f$（bps，从 DPU 流表硬件计数器差分
得到，见 §5.2）；政策参数（§3.1）；本机下行线速 $LineRate$。

**第一步：需求估计。** $D_f = r_f \times (1+\delta)$。$\delta$（增长余量，
10-25% 量级，实现时定）的作用：受抑制的流集合当前 $r_f$ 低，若直接拿 $r_f$
当需求，分配会把它锁死在低位；乘上 $(1+\delta)$ 给它一个"想涨就能涨"的空间——
它涨了，下周期 $D_f$ 随之涨，直到顶到公平份额。

**第二步：层级 water-filling 算应得速率 $e_f$。** 树结构与算法：

```
容量 C_root = LineRate × (1 − headroom)
第 1 层（VM 层）：把 C_root 在各 dst VM 间按权重 W_d 做带上限 water-filling：
   反复执行：对未冻结的 VM 按 W_d 比例注水；某 VM 的水位达到
   min(MaxRate_d, 其下所有流集合需求之和) 时冻结该 VM 并回收余量；
   直到容量用尽或全部冻结。产出：每 VM 的份额 C_d。
第 2 层（类层）：把 C_d 在 {TCP, RDMA} 间按 W_{d,c} 同法分配，
   某类的需求之和小于其权重份额时，余量归另一类（借用即此处的
   work-conserving）。产出：每类份额 C_{d,c}。
第 3 层（流集合层）：把 C_{d,c} 在各 src 间按 u_{d,c,s} 同法分配。
   产出：e_f。
```

不变量：$\sum_f e_f \leq C_{root}$；任何层未用满的份额都回灌（work-conserving）。

**第三步：虚拟队列积分与标记。** 每个流集合一个积分器（**v2.1 修订，Q22**）：

$$vq_f \leftarrow \mathrm{clip}\big(vq_f + \Delta_f\cdot T,\ 0,\ V_{max}\big),\quad
\Delta_f = \begin{cases} r_f - e_f & r_f > e_f \quad\text{（充入：真实超额）}\\
-(\hat{e}_f - r_f) & r_f \leq e_f \quad\text{（排空：未用的公平上限）}\end{cases}
\qquad s_f = \min\!\left(\frac{vq_f}{V},\ 1\right)$$

符号：$vq_f$ = 虚拟队列长度（bit，初值 0）；$T$ = 控制周期（s）；$V$ = 标记
满刻度（bit）——$vq_f$ 积到 $V$ 时 $s_f$ 饱和为 1；$V_{max} \geq V$ = 积分
上限（防 windup；实测取 $V_{max}=V$）。用积分而非瞬时比值的原因：
容忍单周期测量噪声，只对持续超额报警（AVQ 一脉）。

**为什么排空要用公平上限 $\hat{e}_f$，而不能用应得速率 $e_f$（Q22）。**
最初的公式（v2）在充入和排空两个方向都使用 $e_f$：流量超出 $e_f$ 时队列
增长，低于 $e_f$ 时队列以两者之差的速度排空。实现后我们在 M1 实验中
发现这个公式存在一个死锁。考虑一条被深度压制的流：它的实际速率 $r_f$
已经很低，而 $e_f$ 是按"实测速率乘以增长余量"估计的需求封顶的，所以
$e_f$ 会跟着 $r_f$ 一起塌下去，两者始终只差 15%。这样一来，无论这条流
被压得多低，虚拟队列的排空速度都只有实际速率的 15% 左右——一个积满
600 Mbit 的队列，在流量只剩 50 Mbps 时需要一百多秒才能排空。在这段
时间里标记始终是满刻度，发送端每个周期都在被乘性减打压，速率被永久
钉死在地板上。我们在实验中完整复现了这个死锁：流量一旦被压穿就再也
回不来。

修复的思路是把充入和排空的参照物分开。充入仍然用 $e_f$：只有真正超出
自己应得份额的流量才积累欠账。排空则改用**公平上限 $\hat{e}_f$**——即
"假如这条流想要无穷多、而其他流保持当前需求时，它能分到多少"。直觉
上，$\hat{e}_f - r_f$ 就是这条流"没有用掉的份额"：一条被压制的流没用掉
的份额很大，队列会很快排空，标记随之解除，流量得以恢复；而一条正好
把份额用满的流（$r_f \approx \hat{e}_f$）排空速度趋于零，不会平白获得
解除标记的机会。修复后死锁消失，且均衡行为与原设计意图一致。

还有一个边界情况：完全空闲（$r_f = 0$）的流。它既不充入也无从排空
（份额上限对不发包的流没有意义），队列会冻结在旧值上。我们的处理是让
空闲流的队列以每周期 $V$ 的速度快速清空——一条不再发包的流放弃自己的
拥塞主张，这与 fail-open 的精神一致：基础设施状态的陈旧残留不应该在
应用恢复发包时继续惩罚它。

为什么三个场景在此统一：**政策份额争夺**（20G 场景）——物理零拥塞，但 VM 层
上限 $MaxRate_d$ 使超额流集合 $r_f > e_f$，账本合成了稀缺性；**incast**——
root 容量被顶穿，短缺按权重摊进各 $e_f$；headroom 保证 VQ 先于交换机物理队列
报警。**借用**——类层 work-conserving 的直接产物，无需任何显式协议。

### 3.4 遥测通道

接收端 DPU → 各发送端 DPU，UDP，每周期每活跃流集合一条记录：
$\{$流集合标识, $s_f$, 序号$\}$。**$s_f = 0$ 也发送**——它是"新鲜且无拥塞"的
显式许可，发送端的加性增以收到它为前提（见 §3.5 fail-open）。走 DPU 间管理
路径（lab 中为 dpu0 直连网），与被控数据路径（dpu1/交换机）物理分离，拥塞
不会反噬控制通道。（user批注：请不要用dpu0直连网，生产环境中并不存在这样的网络）

### 3.5 发送端：统一响应律

每流集合维护速率上限 $R_f$（bps）。**初值 $R_f = Tree_f$**（Q20 定案：树份额
起步）——新流集合起步即获得发送端政策允许的全部额度，不做慢启动；若它落在
拥塞资源上，1-2 个周期内标记到达、乘性减把它压下来，期间的瞬态超额由租户 CC
的即时反应兜底。选择乐观起步的理由：短流不付爬坡税，且"平时不干预、出事才
介入"与整个设计的哲学一致。

每收到一条遥测（周期 $T$）：

$$
R_f \leftarrow
\begin{cases}
\min(R_f + A,\ Tree_f) & s_f = 0\\[2pt]
R_f \cdot (1 - \beta \cdot s_f) & s_f > 0
\end{cases}
$$

符号：$A$ = 每周期加性增量（bps）；$\beta \in (0,1)$ = 最大乘性减系数——
$s_f$ 饱和时单周期最多砍掉 $\beta$ 比例。**律中没有权重**：分配比例由
$e_f$（标记点）决定，律只负责收敛。

**统一性的准确表述（v2.1，Q24）**：两类流量共用**同一律式**（同一公式、
同一标记语义）；速率常数 $A$ 允许 per-class 标定（M4 实测：RDMA 宜
0.125% 线速——硬件 pacing 忠实跟随、深跌恢复快；TCP 宜 0.025-0.05%——
pace 上推过快会诱发租户 CC 超冲丢包塌陷）。类比同一拥塞控制算法在不同
链路上取不同常数。后续实验可能重试全局单一 $A$（记录在案）。

**恢复行为（v2.2 新增，Q26）。** 上面的基本律有一个动态短板：乘性减
是按比例的、一步到位的，而加性增每周期只加固定的 $A$。一次深度的减速
（比如政策阶跃或一阵误标记把 $R_f$ 从 6G 砍到 2.5G）之后，流量要靠
每周期 0.1G 的加性增一步步爬回来，需要三十多个周期。为了缩短这条
恢复尾巴，我们借鉴 DCQCN 速率恢复的三段式结构（Fast Recovery、
Additive Increase、Hyper Increase），给律加上恢复行为：

发送端为每个流集合记住一个"最近的正常速率" $R_{good}$——每次乘性减
发生时，把砍之前的 $R_f$ 存入 $R_{good}$。此后只要收到无标记的遥测
（$s_f = 0$），发送端不做普通的加性增，而是执行快速恢复：每个周期令
$R_f \leftarrow (R_f + R_{good})/2$，用二分逼近的方式在约 5 个周期内回到
砍之前的水平。如果标记只是转瞬即逝的（例如测量噪声），流量很快弹回原位；
如果标记是持续的（真实的政策约束），下一次乘性减会把 $R_{good}$ 更新为
更低的砍前值，恢复目标自然逐步下移，不会与约束对抗。在快速恢复完成之后，
若继续收到连续的无标记遥测（我们取连续 10 个周期），说明这条流长期
低于它的可用份额，加性增的步长开始逐级放大（每多一个无标记周期加一档，
封顶 8 倍），这就是 Hyper Increase，用于加快向上的份额回收。

实现这条恢复行为时我们踩过两个值得记录的坑。第一个坑：快速恢复的目标
如果不设上限，会造成饥饿。接收端分给一条流的份额 $e_f$ 是按它的近期
实测速率估计的，有一到两个周期的滞后；如果快速恢复把 $R_f$ 一步弹回
远高于当前份额的位置，流量会立即超出自己滞后的份额、立即被标记、再次
被砍——如此循环，这条流被锁死在低位（我们实测到两类流量的比例达到
11.8:1）。因此快速恢复的目标必须取 $\min(R_{good},\ e_f(1+\delta))$，其中
$e_f$ 就从遥测里带回。一句话概括这条原则：**快速恢复只把流量送回它的
份额之内，份额之外的探测交给慢速的加性增**。第二个坑：快速恢复的跳变
本身会让实际速率 $r_f$ 落后 $R_f$ 一两个周期，这个瞬时落差会被 app-limited
检测（见下）误判为"应用没用满"，触发钳制，把恢复退化成每周期约 7% 的
爬行（实测从地板爬回 6G 需要 19 秒）。修复很简单：快速恢复主动造成的
落差不应计入 app-limited 的证据，跳变时将其计数器清零。

**app-limited 冻结**：连续 $m$ 个周期 $r_f < \theta_{al} \cdot R_f$（应用没用满
额度）→ $R_f$ 冻结在 $r_f(1+\varepsilon)$；$r_f$ 回升贴近后解冻。作用：防止
$R_f$ 虚高——虚高的 $R_f$ 在拥塞来临时要砍多拍才生效。$\theta_{al}$（取 0.85）、
$m$（取 10 个周期，即 500ms：更短会把 TCP 自身的慢启动误判为 app-limited，
M1 实测会把乐观起步退化成线性爬坡）、$\varepsilon$（取 0.1）。

**fail-open**：连续 $N_1$ 周期未收到 $f$ 的遥测 → $R_f$ 冻结（停止加性增）；
连续 $N_2 > N_1$ 周期 → $R_f$ 斜坡回升至 $Tree_f$。语义：接收端 DPU 故障时，
流量退化为只受发送端本地政策约束——租户不被卡死（fail-open），也不会失控
（租户 CC 仍在）。

**执行**：$pace_f = \min(R_f, Tree_f)$。RDMA 落到 PCC per-pair 预算（DPA 硬件
pacing，租户透明）；TCP 落到 host fq+edt 的 pacing rate。租户自己的 CC 在
pace 之下照常运行：实际发送速率 = min(租户 CC 想发的, $pace_f$)。RDMA 侧即
已验证的 min(DCQCN, budget) 组合。

### 3.6 发送端：两层模型（v2.1 重写，Q23）

**云售卖原则**（本节的公理，2026-07-10 用户定）：$MaxRate_i$ 是卖给租户的
额度，任何时刻任何 VM 的发送速率不得超过它——某 VM 只用 5G 时，省下的量
可以让**其他 VM 在各自 $MaxRate$ 之内**多拿（超售场景），但不能让任何 VM
突破自己的购买额度。例：线速 100G 超售 8×20G，全打满时各 12.5G；一个只用
5G 时其余各 95/7≈13.6G（仍 <20G）。

- **第一层（硬上限，执行兜底）**：per-VM $MaxRate_i$ 由硬件限速器执行
  （生产：devlink port function rate 等；类盲、静态、与第二层解耦——在
  VF 视角里 $MaxRate_i$ 就是"线速"）。作用是防第二层软件失效时的失控。
- **第二层（分配语义，本方案）**：软件树 = §3.3 同一 water-filling，容量 =
  上行线速 ×(1−headroom)，第 1 层 cap = $\min(MaxRate_i,$ 需求和$)$（该
  cap 保证售卖原则），VM 内类间按类权重软隔离，需求 = 实测速率 ×$(1+\delta)$
  + cap-hit 修正（$r_f \geq 0.85 \cdot pace_f$ 时按 $pace_f(1+\delta)$ 报）。
  **$Tree_f = f$ 的公平上限 $\hat{e}_f$**（同 §3.3 定义、作用于发送端树）——
  取上限而非需求封顶份额的原因：Q20（新流以 $Tree_f$ 起步）与 §3.5
  fail-open（斜坡回升至 $Tree_f$）都要求 $Tree_f$ 是"政策允许的额度"；
  需求封顶下新流 $r=0 \Rightarrow Tree \approx 0$，自相矛盾（Q23）。
  $Tree_f \leq MaxRate_{src(f)}$ 恒成立，故 Q20 起步突发与 fail-open 上限
  均有界于售出额度。
- 原"预算仲裁器"不再是独立组件：两个执行面（fq+edt / PCC）挂在同一
  发送端 agent 下，类间借用即树的 work-conserving 填充本身（M5 实证）。

min 不变式实测：发送端 $MaxRate$=5G、接收端政策 6G 时，紧者（4.95G，含
headroom）生效（M5a）。

### 3.7 性质论证（写论文时展开）

**为什么收敛到政策份额**：单个受控资源上，这是"AQM 按超额差分标记 + 各源
AIMD"的经典设定。超出 $e_f$ 的流集合被持续标记、乘性减；低于 $e_f$ 的不被
标记、加性增；均衡点即 $r_f \approx e_f$，而 $e_f$ 由 water-filling 保证等于
政策份额。借用场景：空闲类的 $D_f$ 小 → 其份额被 work-conserving 回灌给另一
类的 $e_f$ → 借用类不被标记地涨上去；需求回归时 $e_f$ 重划、标记把借用者
压回——回收速度由 $\beta$ 与 $T$ 决定。**锯齿幅度**由 $A \cdot T$ 与 $V$
决定，是精度-响应速度的权衡旋钮（eval 量化）。**双环嵌套**（律叠在租户 CC
之上）不互相激振的论据：pace 只延迟不丢包，对租户 TCP 表现为平滑管道
（OnRamp 同型论证）；RDMA 侧 min(DCQCN, budget) 已在本 lab 长期运行验证。

### 5.4 参数终裁与三条实测权衡（v2.2 重写，Q27）

经过 M4 的敏感性扫描和后续两天的参数实验，最终推荐值如下：控制周期
$T$ = 50ms；加性增量 $A$ = 0.1 Gbps/周期（线速的 0.05%，全局统一，见下）；
乘性减系数 $\beta$ = 0.3；标记满刻度 $V$ = 600 Mbit（即 2 个
$T \times$ 线速 $\times$ headroom），积分上限 $V_{max} = V$（更深的积分仓
会让乘性减在超额停止后多砍数拍，加深下冲）；增长余量 $\delta$ = 15%；
headroom = 3%；app-limited 三参数 $\theta_{al}=0.85$、$m=10$ 周期、
$\varepsilon=0.1$；fail-open 门限 $N_1=5$、$N_2=40$ 周期。恢复行为
（§3.5）默认开启。

值得单独说明的是 $A$ 的选择，因为它牵出了我们在参数空间里实测到的
三条结构性权衡。

**第一条：加性增量在"比例保真"与"利用率"之间没有全局甜点。**
把全局 $A$ 从 0.05G 提到 0.2G，双类并发的类间比例始终精确（1.00 上下），
但合计利用率钉在 85% 附近纹丝不动；继续提到 0.25G，利用率跳到 96%，
比例却灾难性地崩坏到 21:1——大步长与恢复行为叠加会复利放大先领先一方
的优势，而需求封顶的账本又让它守住地盘，系统进入"赢家通吃"的双稳态。
按类分别标定（RDMA 0.25G、TCP 0.1G）可以拿到 88-92% 的利用率，代价是
比例漂移到 0.81-0.92 之间且方差大。我们最终选择全局 0.1G：它是唯一
比例可靠的档位，公平是本系统的第一承诺。按类标定保留为一个具名的
"利用率优先"配置模式。

**第二条：给恢复中的流发放增长余量是零和的。**
我们曾尝试在流量低于其近期峰值时把 $\delta$ 临时放大到 50%，期望它
以复利速度收复失地。结果利用率不升反降（81%，低于基线 85%）。原因是
water-filling 的账本是零和的：分给恢复流、但它一时用不掉的那部分份额，
恰好是从兄弟流本可以实际使用的份额里扣出来的，兄弟流因此被标记压到
它的可达速率之下。基线 $\delta=15\%$ 中同样的税负已经存在，只是小三倍。
结论：需求侧的余量只能小，恢复加速必须在发送端（§3.5 的恢复行为）做。

**第三条：把份额"保底"给掉坑的流，会杀死掉坑期间的临时借用。**
我们实现过一个"份额保底"的需求估计（$D_f = \max(r_f(1+\delta),\
\hat{s}_f)$，其中 $\hat{s}_f$ 是纯权重份额）：一条流掉坑时它的份额分毫
不减，账面缺口彻底消失（分配总量的 5 分位从 2.84G 提到满额 6.00G）。
但合计利用率反而从 87% 降到 80%。这暴露出基线里一个此前没有被识别的
增益来源：TCP 每次丢包恢复的短暂掉坑期间，RDMA 会临时借走它让出的
容量，坑结束后再还回去——份额保底恰好禁止了这种借用（掉坑的流速率
不为零，保底就一直生效，容量借不出去）。两者结构性互斥。份额保底
保留为一个具名的"严格份额 SLA"配置模式，适合把"账面份额永不缩水"
作为租户承诺的场景。

这三条权衡共同指向一个结论：双类并发下 87% 左右的合计利用率不是账本
的失误，而是租户 TCP 自身丢包恢复期间发不出流量所致——把分配总量钉死
在满额（第三条实验）也无法把它买回来。分配语义的改进空间到此探明。

## 7. 新颖性定位（写作用，详细考古见 C 文档 §10）

一句话主张：**把层级租户政策（含借用）编译进边缘虚拟队列的差分标记，用一条
传输无关的响应律同时驯服 TCP 与 lossy RDMA，租户透明、零数据面改动。**
逐先例增量：HULL（phantom queue 造信号，但为 headroom 不为政策，在交换机）→
搬到边缘、承载层级政策；AFD（按超额差分标记，但在交换机、平权、无层级）→
层级化、政策化、作用于虚拟资源；EyeQ（边缘 per-VM，但显式速率反馈、类盲）→
标记而非速率：无租约状态机、无需求协议；VCC/AC-DC（vSwitch 垫统一 CC，仅
TCP）→ 扩到 lossy RDMA + 政策层级 + DPU 硬件执行；EQDS（credit 准入 + 数据面
替换）→ rate-based 对偶：零数据面改动、类粒度政策（EQDS 隧道 per 主机对、
类盲）、核心网政策分配是其明文 future work（本方案 §4.6 扩展回应）。
**不可声称**"首个 TCP/RDMA 共存"（EQDS 已占）。
