# V2 加入事件的时间预算（2026-08-31）

V2 的加入事件长期收敛不过（旧口径 1222–1823 ms，判据 1000 ms）。这份报告把那段时间逐块拆开，记下查到的三件事、修掉的两件事，以及剩下的一件。

**结论。** 加入事件的时间由三块构成：接收端接纳新流约 230 ms、打流器启动约 1000 ms、新流许可速率爬升约 620 ms。**打流器那一块已经消掉**（换成带绝对起始的 `tcp_blast`，首字节从事件后 1086 ms 提前到 22–35 ms）。**接纳那一块查清了但没修掉**——它由 megaflow 表项的出现时刻决定，而我们自己装的 OVS meter 会让它偶发地劣化五倍。**爬升那 620 ms 跑在设计上限上，动它要改设计文档 5.4 节。**

## 一、环境

除下列各项外同 `README.md` 的共同环境。

| 项 | 取值 |
|---|---|
| 场景 | V2（改短后 10+10+10 s）：sgpu01 的 8 个流集合常驻，sgpu03 的 8 个在 t=10 s 加入、t=20 s 退出 |
| 被测对象 | `law=conf`（设计 v4），E 版参数，`probe_cap_tree=true`，含本日两处修复（RDMA QP 计数单向化、接收端归因封顶） |
| 接收端 OVS | `doca-openvswitch-switch 3.4.0040-1`，内核数据面（`system`），`hw-offload=true`，卸载与 revalidator 参数全部默认 |
| 每 VF 上限 | 上行 devlink `tx_max` 50 G；下行 OVS drop meter 50 G（`vf_caps.sh`，8 个 meter、24 条带 meter 动作的规则） |

## 二、时间预算

以新流 `sgpu03/vf0>sgpu02/vf0` 为例，事件在 t=10.000 s。

| 环节 | 修复前 | 现在 | 怎么测的 |
|---|---|---|---|
| 事件 → 打流器首字节（TCP） | 1086 ms | **22–35 ms** | 接收端硬件计数首次非零 |
| 事件 → 接收端接纳流集合 | 153–1169 ms | 未改 | `rx.jsonl` 里该 fsid 首次出现 |
| 首字节 → 进入 ±10% 带 | — | 约 620 ms | 许可速率从 2 G 爬到 11.5 G |
| 事件 → 进带（TCP） | 1736 ms | **650–662 ms** | |

## 三、打流器不准点（已修）

`iperf3` 3.20 没有绝对或延迟起始选项，所以 runner 只能"睡到事件时刻再 exec"，它 **521 ms**（单实例实测）到约 1.1 s（八实例同时起）的启动全部落在事件之后。那段时间接收端**一个字节都没收到**，新流的许可速率钉在 2 G 地板上没有任何可探的依据，而收敛是从名义事件时刻起算的——这一秒完全记在系统头上。

修法是 `tools/host/tcp_blast.c`：**先建连、等到绝对时刻、再发**，和 RDMA 侧 perftest `--start_at` 同一个做法。建连安排在起始前 2 秒，不是进程启动时——VF 与 representor 的 MTU 不一致会让空闲超过 10 秒的 TCP 连接丢大段（`ops_notes`），而 runner 提前约 20 秒就拉起客户端。保留 `-C <cc>` 供 V6 换 BBR。

三遍验证：TCP 首字节 35 / 22 / 27 ms，进带 661 / 662 / 650 ms，散布极小；稳态贴合三遍全过，说明它和 iperf3 一样能打满带宽。

顺带修了一个隐患：`udp_blast.c` 与 `tcp_blast.c` 都不在 `deploy_check` 的主机同步清单里，其他三台主机上根本没有源码。两个都已纳入。

## 四、接纳延迟：查清了，没修掉

接收端的流集合成员表来自 `dpctl/dump-flows type=offloaded`，在慢循环里每 200 ms 查一次。四种配置都试过，**没有一种改善，一种明显变坏**：

| 配置 | 接纳延迟 |
|---|---|
| offloaded + 200 ms（基线） | 233 / 215 / 267 ms |
| offloaded + 20 ms | 1124 / 196 / 204 ms |
| 不过滤 dump + 200 ms | 347 / 401 / 242 ms |
| 不过滤 dump + 40 ms | 1118 / 1122 / 1169 ms |

两个单独的事实都成立却不能相加：**新流在不过滤的 dump 里比在 offloaded dump 里早约 200 ms 出现**（轻量轮询下实测 207 对 238 ms；一次重轮询下是 130 对 491 ms——探针自己会放大这个差距），而成员表的刷新又被 200 ms 的慢循环挡着。放开慢循环之后接纳延迟反而劣化五倍，这一点**不是 dump 成本**（16 条流下两种 dump 净耗时都只有 1.2–1.4 ms）**也不是 CPU**（代理循环频率只从 98 掉到 91–93 次/秒），机制未查明。全部改动已回滚。

## 五、OVS meter 让接纳延迟偶发劣化五倍（已坐实，未解决）

vswitchd 日志里有一种错误：`tc|ERR|Failed to parse police action options`，只在有流量时出现。"police" 就是限速器，而接收端网桥上正有 8 个 meter、24 条带 meter 动作的规则。

三对三对照（改短的 V2）：

| | police 错误 | 接纳延迟 | 新流进带 |
|---|---|---|---|
| meter 在 | 60 / 60 / 60 | 1111 / 1101 / 229 ms | 1728 / 1224 / 853 ms |
| meter 撤 | **0 / 0 / 0** | **257 / 153 / 268 ms** | **348 / 153 / 399 ms** |

police 错误完全由 meter 造成，没有例外。**meter 不是让接纳整体变慢，而是让它偶发地卡住四到五倍**——这正是"同一配置下接纳延迟从 153 ms 到 1169 ms"那种不可复现散布的来源。撤掉 meter 时 TCP 收敛三遍全过（meter 在时三遍挂两遍）。

**一个必须同时记的反例**：`dpif_flow_put_error` 没有跟着消失（meter 在 +45，撤掉后 +69 和 +17）。那个约 43% 的流表安装失败率**不是 meter 造成的**，另有原因，未查。

两条尝试都失败了。**调 burst**：显式给 500 Mbit（内核里确认 `3063225600b` → `93132000b`，rate 不变），错误数 61 → 60 / 59，无效。**换 OVS 版本**：仓库里只有已装的 3.4.0040-1，没有其他候选。另外那个"50 Gbit/s 超过 32 位字段（4.29 GB/s）需要 RATE64"的猜想**既没证实也没证伪**——隔离环境里 25 G 和 50 G 的 meter 都触发不了错误，对照等于没做。

撤掉 meter 不是方案，那个 50 G 下行上限有它的用途，而 devlink 只有 `tx_share`/`tx_max`、做不了收方向。剩下的方向是把下行限速挪出 DPU 的 OVS meter（例如接收主机的 tc ingress）。

## 六、还剩下的：620 ms 的爬升

新流许可速率从地板 2 G 爬到 11.5 G，实测每条反馈的对数步长**中位正好 3.00%**，就是 $\alpha_{\max}$ 的设计封顶——律已经跑在允许的最快速度上。这 620 ms 加上判据要求进带后再稳住 1 秒，是现在唯一还挡着 V2 的东西。

三遍十二个收敛值：`639/661/663/690/720/812/842/866/1004/1107/1174/1699 ms`，**十二个里八个进了 1 秒**（旧版本对应位置全部 1222–1823 ms 超标）。

要压下去只能抬高新流的起步许可速率（从 2 G 抬到 5 G 可把爬升砍掉约一半），那属于设计文档 5.4 节，按流程先改文档。
