# V8 信任度：账本管不到的瓶颈（2026-09-02，两条臂各一遍）

**结论。** 信任度在两条臂里都没有动过一下，两条臂的结果逐项相同。原因在执行面的 CC 项里：信任度上涨要求"租户 CC 要得比围栏少"，而这次跑的 CC 项**对 NACK 不做任何反应**——设备码在 NACK 事件里只记 `loss_ts` 和 `n_nack`，然后 `if (ZTR || SWIFT) ztr_flags |= 2`，四项里只有 ZTR 和 Swift 会因丢包降速，CNP 驱动的那两项（AIMD、DCQCN RP 状态机）记下就算完。于是 `cc_rate` 全程 200 G 线速，远在 12.5 G 的围栏之上，闸门永远打不开。

更根本的一层与 CC 项无关：执行面的限幅是 $r=\operatorname{clip}(c,(1-T)R,R)$，下界只在 $c<R$ 时才起作用。这里 $c=200$ G、$R=12.5$ G，所以对任何 $T$ 都有 $r=R$。**信任度只能在 CC 自己已经退让的时候起作用，它没有能力让一个不退让的 CC 退让。** 这一版设计能承诺的是"不去覆盖一个正在退让的拥塞控制"，不是"在隐形瓶颈上保护租户"。

两条臂的运行记录：`reports/V8a_trust_20260902_rep1.md`（信任开）、`reports/V8b_frozen_20260902_rep1.md`（信任冻结）。

## 二、信任度为什么没动

执行面每 1 ms 判一次，三条要同时成立才涨（design v4 §6.3）：虚拟队列为零、租户 CC 要得比围栏少 2% 以上、最近 100 ms 出现过丢包。设备读回（`rp_sgpu01.jsonl`，每秒一次）给出的是：

| 量 | 30–60 s 里的实测 |
|---|---|
| 丢包证据 `nack` | 0 → 585,694，约 **每秒 1.9 万次**，持续整个窗口 |
| 围栏 `level` | 12.50 G/QP（= 50 G ÷ 4 QP），纹丝不动 |
| 租户 CC `cc_rate` | **200.00 G**，全程线速 |
| `loss_ep`（丢包快路径批准涨信任的周期数） | **0** |
| 信任度 `trust` | **0.000** |

第一条和第三条都成立，卡在第二条：丢包每秒近两万次，而 `cc_rate` 一动不动。

设备码里 NACK 事件的处理是这样的（`rp_rtt_template_dev_main.c`）：

```c
if (a.ev_type == DOCA_PCC_DEV_EVNT_ROCE_NACK) {
        c->loss_ts = now;
        c->n_nack++;
        if (g_hpft_cc_algo == HPFT_CC_ZTR || g_hpft_cc_algo == HPFT_CC_SWIFT)
                c->ztr_flags |= 2u;
}
```

四个 CC 项里**只有两项对丢包降速**：Swift（`0xccd 3`）的丢包切窗是无条件的（`cwnd *= 1 − max_mdf`，只有"距上次降速至少一个 RTT"这一层节流）；ZTR（`0xccd 1`）降，但它的 NACK 分支还要求 `rtt ≥ ZTR_MAX_DELAY`（70 µs），而丢包 meter 只丢不排队、时延不会涨上去，所以 ZTR 在这个场景里大概率也不降。另外两项 AIMD（`0xccd 0`）与 DCQCN RP 状态机（`0xccd 2`，也是设备码的编译期默认值）都是 CNP 驱动的，把 NACK 记下就算完。

**所以"看不见丢包"是这一项的实现选择，不是 DCQCN 这一族的性质。** 固件 DCQCN 走的是完全不同的代码路径（`lab_env plain`、UPCC=0，motivation 的基线就是它），那条路上有 `roce_slow_restart` 这类丢包后压低重启的机制，RP 的参数确实会改变降与恢复的形状。validation 全程 UPCC=1，跑的是我们自己的 PCC，两者不能互相推断。

**还有一层缺口值得单独记下：闸门读的是 CC *声称* 的速率，不是它 *实际达到* 的速率。** 一条流可能因为一直在 NAK 后重传而实际吞吐很低，同时 RP 的速率变量一个字没变——这恰恰是隐形瓶颈下最常见的形态。想让信任度覆盖这种情况，判据得换成实际达到的速率，或者要求 CC 项本身把丢包反应暴露出来。

**运行记录的一个短板**：设备端没有 `g_hpft_cc_algo` 的回读，runner 也没有记它，所以"这次跑的到底是哪一项"只能从"启动路径里没有任何地方写 `0xccd`、因此是编译期默认值 2"推出来，不能从记录里读出来。每份报告的环境表都写着 CC 项，而没有任何东西校验它。这一条要补。

## 三、这不只是"闸门没开"

即使强行让信任度涨起来，也救不了这一格。执行面的限幅是

$$r=\operatorname{clip}(c,\ (1-T)R,\ R),$$

下界只在 $c<R$ 时才起作用。这里 $c = 200$ G、$R = 12.5$ G，$c\ge R$，于是对任何 $T$ 都有 $r=R$。**信任度只能在 CC 自己已经退让的时候起作用，它没有能力让一个不退让的 CC 退让。** 这是限幅形式的直接推论，不是实现的取舍。

写进设计里应当是这样一句：信任度承诺的是"不去覆盖一个正在退让的拥塞控制"，而不是"在隐形瓶颈上保护租户"。后者需要租户的 CC 本身能看见那个瓶颈。

## 四、代价有多大

臂 B（信任冻结，等价于当前的实际行为）在 30 秒里持续以 50 G 往一个只能过 20 G 的口子里推，每秒约 1.9 万次 NAK。接收端拿到的 20.2 G 是**线上口径、含重传**，其中有多少是有效载荷，现有的三路测量都答不上来——perftest 的 BW average 只有整段一个数，而且它的统计窗（`[margin, 时长−margin]` = 22.5 到 67.5 s）横跨三个阶段。**这正是要把 `--report-per-qp` 接进 runner 的理由**：每 QP 的完成事件时序能直接给出 30–60 s 这一段的应用 goodput。

## 六、下一步

1. **用 Swift 项（`0xccd 3`）重跑这两条臂。** 它的丢包切窗是无条件的，第二条闸门因此可以成立，三条闸门第一次能同时打开。这一步不改任何机制、不换类，直接测的就是要测的东西，是最该先做的一件。
2. **顺带把 ZTR（`0xccd 1`）也跑一遍**：它的 NACK 分支挂着 70 µs 的时延门槛，而丢包 meter 不排队，预期它不降。如果实测确实不降，那就是"丢包证据被时延门槛挡住"的一个具体例子，值得写进设计的边界。
3. **给 runner 补 CC 项的记录与校验**：设备加一个 `g_hpft_cc_algo` 的回读，run.sh 跑前读一次写进 `results/<tag>/`，report 的环境表照抄实测值。现在这一格是照着 README 抄的，没有任何东西校验。
4. **把 `--report-per-qp` 接进 runner**，否则"过驱动的代价"永远只能用 NAK 计数间接说：接收端拿到的 20.2 G 里有多少是有效载荷、多少是重传，现有三路测量都答不上来。
5. 设计侧两条：§6.3 的"额度低于围栏"这条前置条件隐含要求租户的 CC 对丢包有反应，要么写进边界要么改判据；以及闸门读"声称的速率"而不是"达到的速率"这个缺口。
