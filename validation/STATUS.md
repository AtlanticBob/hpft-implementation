# Validation 状态（2026-08-31）

本文件随每轮验证更新，是设计文档（`hpft-design/docs/design_v4.md`）之外的活动记录。场景与判据的定义在同目录 `README.md`，跑法在 `EXECUTION.md`。

参数取设计文档第 9 节的值。四个必跑场景各跑三遍，判据按"三遍里通过几遍"记，收敛时间记 min / 中位 / max。

| 场景 | 贴合 | 队列 | 收敛 | 不塌 | 健康 |
|---|---|---|---|---|---|
| V1 稳态 incast | 3/3 | 1/3 | 3/3 | 3/3 | 3/3 |
| V2 加入/退出 | 3/3 | 2/3 | 0/3 | 3/3 | 3/3 |
| V4 需求变化与借用 | 2/3 | 3/3 | 2/3 | 2/3 | 3/3 |
| V7 与租户 CC 共处 | 3/3 | 0/3 | 1/3 | 3/3 | 3/3 |

收敛时间（毫秒，判据 1000）：V2 加入 1090/1168/1619（RDMA）与 905/922/1150（TCP），退出 706/779/987 与 779/865/889；V4 需求涨回 586/630 与 530/566（另有一遍 7 秒，见下），回落 870/911/921 与 270/279/280；V7 根缩 359/841/938 与 924/1075/1568，背景停 408/417/533 与 377/479/493。稳态贴合的偏差在 V1 与 V7 是 0.1% 量级，V4 是 2.5% 以内。

三条不通过各有确定的来源，都不是同一个问题。

**队列判据的失败全部是尾部擦线**，幅度在 30% 以内（1.0 到 1.4 秒对 1 秒的门槛），队列均值与最长不回零的中位数都没有变化。它的直接来源是探涨上限把树纳入之后围栏贴份额更紧（设计文档 10.3 节"树上限与队列判据的尾部"），判据本身用的是最坏值口径、对偶发长尾没有余量。

**V2 加入事件稳定在 1.1 到 1.2 秒**，散布很紧，是可复现的结构性延迟而非噪声。构成是接收端发现新流约 110 到 310 毫秒，加上围栏在最大步长下的爬升；两者都已经压到设计允许的极限，再快需要改 $\alpha_{\max}$ 的定法或接收端的发现路径（设计文档 10.3 节"加入事件的结构性延迟"）。

**V4 那一遍 7 秒的离群是探涨上限的自指死结**（设计文档 10.3 节），六遍中发生一次，整段只交付了应得的 3%。它同时把 V4 的贴合与不塌拖成 2/3。

还没跑的场景：租户加入与退出（V3）、单目的额度零物理拥塞（V5）、换 Swift 和 BBR（V6）。

**方法论。** 判据 3 的轮间散布很大（同一个 V7 根缩事件的 TCP 在历史九轮里从 896 到 2293 毫秒），所以单轮之间几百毫秒的差别不能用来判定优劣，只有量级变化才可以。本文所有数字都来自三遍；此前版本的单轮结论已经作废。

**队列判据在 2026-08-30 改过一次**：原来是"均值不超过 1 毫秒，且超过 2 毫秒的样本不超过 5%"，现在是"均值不超过 1 毫秒，且每个流集合至少每秒把账清到零一次"。改的理由是这套设计的稳态本来就是锯齿，账周期性出现是构造使然，按出现频率打分等于要求围栏 95% 的时间待在份额之下；而设计真正承诺的是账能清掉。
